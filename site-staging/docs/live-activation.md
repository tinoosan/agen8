# Agen8 Dev activation proposal and test runbook

This is a proposal, not an installed service or approved deployment. The implementation and draft PR can be reviewed now. Security audits and real-host disconnection verification remain release blockers. No host, network rule, credential, owner grant or live subscription has been created by this work.

## Mugiwara runtime proposal

Use the existing Mugiwara Linux homelab first. A read-only assessment through the verified `mugiwara` SSH alias on 2026-10-04 found Ubuntu 24.04.2, x86_64, four CPUs, Docker 29.1.3, Compose 2.40.3, approximately 57 GiB free disk at 75% used and 7,124 MiB available memory. Existing containers and Kubernetes workloads were only inspected, never modified or restarted. No cleanup/pruning was performed.

The prepared `event-companion/compose.yaml` creates a separate `agen8-events` project containing relay and dispatcher containers. Each has a 128 MiB memory limit, 0.25 CPU limit, 64-process limit, read-only root filesystem, no Linux capabilities, no-new-privileges and bounded logs. Only the relay publishes `127.0.0.1:8788`; the dispatcher publishes nothing. Neither mounts the Docker socket, other applications' storage or Kubernetes credentials. A shared small heartbeat directory is writable only by the dispatcher. D1 remains the durable queue; the container dispatcher revisits it every thirty seconds and Docker supervises restarts. No new host systemd service is required.

The proposed host directory is `/home/tinoosan/agen8-events`, verified unused. Proposed numeric owners 10001 and 10002 and group 10000 have no existing host entries. Relay runs as 10001:10000 and dispatcher as 10002:10000. The `state` directory needs 10002:10000 mode 0750; heartbeat files are 0640. Compose secrets are protected bind-mounted files, not secret environment values. Local `docker compose config` validation passes. Container build/runtime and image security are CI checks; this is not a Mugiwara deployment.

## Exact public endpoint

Current Mugiwara HTTPS routes are **tailnet-only**, and its Kubernetes ingress load-balancer address is private. Those do not give the Sites Worker public access. Mugiwara already reports the `funnel`, `https` and Funnel-port 10000 capabilities; no Funnel is active and port 10000 is unused. Ports 443 and 8443 already have private services and must not be converted to public access.

Propose only `https://mugiwara.tail9aaa00.ts.net:10000`, forwarded through Tailscale Funnel to the new loopback relay. [Funnel supports this port and is available on all plans](https://tailscale.com/docs/features/tailscale-funnel). The proposed action, after approval, is `tailscale funnel --bg --https=10000 http://127.0.0.1:8788`. Verify before/after that only port 10000 has AllowFunnel enabled and existing Serve routes remain private. Do not reset the Serve configuration or grant Funnel to other users/devices. Stop if the CLI requires a broader tailnet-policy change, new identity or authentication key. No new DNS API credential, domain purchase, router port forwarding, Kubernetes ingress or paid VM is needed for this option.

The prepared adapter accepts port 10000 only for its fixed trusted relay origin. Subscription callbacks still require standard public HTTPS port 443 and connection-time public DNS validation/pinning. [Workers supports custom subrequest ports](https://developers.cloudflare.com/workers/configuration/compatibility-flags/#allow-specifying-a-custom-port-when-making-a-subrequest-with-the-fetch-api), default since 2024-09-02. This does not prove actual Sites-to-Funnel reachability; test HTTPS and unauthenticated 401 behavior before configuring any graph subscription. If Sites cannot reach this endpoint, stop and return the exact result before proposing another hostname/network change.

Funnel exposes only the new authenticated relay endpoints to the internet. TLS terminates at the existing Mugiwara Tailscale process. Signed bytes then travel through loopback to the relay container; bearer auth, bounded requests and callback defenses still apply. Existing private application routes stay private. Public ChatGPT callback hosting belongs to ChatGPT; the homelab needs outbound DNS and HTTPS to its verified public callback, not a new public receiver for normal use.

Expected incremental provider/subscription cost is **$0** using the existing host and Tailscale plan. Electricity and existing internet costs remain. Funnel has bandwidth limits and beta status, so verify reliability on the intended workload. Reassess disk/memory immediately before approved deployment; do not prune images or workloads to make room. A paid VM is a separately approved fallback only if the existing-host option fails measured requirements.

## Approval scope and credentials

Approve the specific new Docker project/directory, resource limits, public Funnel endpoint above, dev-only schema migration/publication, and the named credential actions below. The SSH and Docker permissions already exist; this proposal creates no new login, SSH key, Docker-group membership or Kubernetes grant. Docker access is privileged, so approved commands must target only project `agen8-events`. Preserve owner-private Site policy and production unchanged. No D1 credential or connected-app/OAuth grant is required for this companion.

| Existing dev Sites service bearer | Host `secrets/sites-service-bearer`, owner 10002 mode 0400 | Reuse existing bearer only for `https://agen8-dev.tinoosan.chatgpt.site/api/events/dispatch`; no new OAuth grant |
| Finite D1 owner grant ID | Dev D1 plus `AGEN8_EVENT_GRANT_ID` | Owner signs into the existing private Site; keyed grant action lasts at most 24 hours and never self-renews |
| ChatGPT-issued synthetic subscription signing key and genuine test sessions | Encrypted dev D1 / local ignored account files | Approved actual Dev plugin monitoring test; never manually guess a callback or grant |

Host secret files live only under `/home/tinoosan/agen8-events/secrets`, in a root-owned mode-0755 directory with individually protected mode-0400 files and the owners above. No broad group-readable credential store is needed. Configure the same two matching bearer values in dev server settings through the supported Sites environment interface after approval. Generate values locally and transfer through protected files/stdin/tool arguments without displaying them. Never put values in source, command arguments, prompts, PR text or logs. The companion never receives the AES key or webhook signing keys. It receives signed minimal event bytes. Existing service credentials must be configured only after approval; do not mint replacement OAuth grants or assume account metadata IDs are Site principals.

Site runtime settings are `AGEN8_EVENTS_ENABLED` (default off), `AGEN8_EVENT_RELAY_URL`, `AGEN8_EVENT_RELAY_TOKEN`, `AGEN8_EVENT_ENCRYPTION_KEY`, `AGEN8_EVENT_GRANT_ID`, `AGEN8_EVENT_DISPATCH_KEY`. Host settings are documented in [the companion README](../../event-companion/README.md). Use the exact dev `/api/events/dispatch` URL and a common protected heartbeat path.

Apply schema-only migrations through `0005` to dev D1 after approval. Configure the dispatch key while Events remain off. An owner-signed-in request plus that key can POST `{ "action": "grant", "ttlMs": 86400000 }` to `/api/events/access`; it captures the genuine Site principal and returns the finite grant ID. Configure that ID in the Site runtime. Service access alone cannot create/refresh the grant. Grant replacement clears subscriptions and retries, so unattended monitoring stops within 24 hours unless the owner deliberately renews and resubscribes. This limitation is explicit; subscription refresh never expands the grant.

Do not expose existing private services to obtain one. Local real HTTP/container retry tests are prepared; real-host receiver-based fault tests remain blocked until a separate exact endpoint is approved.

The current implementation has no native Sites cron/queue assumption: the Worker exports only `fetch`. Until real hosting and disconnection checks succeed, report the feature as implemented for review with live Events disabled, not as operational monitoring.
