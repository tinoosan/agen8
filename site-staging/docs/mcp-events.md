# Agen8 Dev MCP Events

This implementation prepares `work.status_changed` and `decision.created` for Agen8 Dev's shared graph. Live subscriptions remain disabled pending approved deployment and runtime verification. Sites supports hosted MCP and owner-private service access. Nothing in this change deploys a Site, provisions callback credentials, subscribes a Work chat or changes production.

## Committed events

`Work` writes a minimal outbox record in the same D1 batch as the node and its history. The history ID is the stable event ID. Optimistic updates that lose their version check emit no event; outbox failure rolls back the node and history. Decision creation emits once; revising a decision and changing a relationship do not emit either event. Relationships remain deferred because each link change writes history for both endpoints.

`work.status_changed` covers transitions to blocked, done or stopped and reopening done/stopped work into planned, working or blocked. The optional `status` filter selects the transition, including `reopened`. A done-to-blocked change has transition `reopened` and resulting status `blocked`. Initial work creation emits no status event.

Both events require an owned `project_id` and optionally filter by `node_id`. Only work accepts `status`. Each delivery has `eventId`, `name`, occurrence `timestamp`, `cursor: null` and `data`. Data contains project/node IDs, version, current status at occurrence, a summary of at most 360 characters and the existing plugin graph deep link. Work events also carry previous status and transition. Bodies, blockers, outcome details and artifacts stay in authoritative records.

Consumers should deduplicate by event ID and reread with `work`, `decision` or `graph_query` before acting. Versions identify stale/out-of-order notifications. Existing `expected_version` checks reject stale writes. At-least-once delivery cannot guarantee exactly-once execution of a consumer's actions. This implementation does not add replay or promise idempotent creation of arbitrary follow-up records.

## Subscription lifecycle

The methods use the same Sites-authenticated MCP endpoint and require MCP 2.0, version `2026-07-28`. Event name header mirrors use the existing protocol validation. The authenticated catalog is private and contains no project data.

Subscription identity hashes the principal, callback URL, event name and canonical filter JSON. Repeating the same identity refreshes one durable subscription. Filters are checked against account-owned records before callback verification. Signing keys must use `whsec_` and canonical base64 decoding to 24–64 bytes.

A verification POST contains only a fresh challenge, with a unique webhook ID and Standard Webhooks HMAC-SHA256 signature. Activation requires a successful response and constant-time challenge comparison within ten seconds. Response reads are bounded to 4 KiB. Verification caches for five minutes per owner, callback and signing key; a replacement key must verify again. The host must enforce the abort signal on the complete exchange.

Signing secrets use AES-GCM encryption with the owner and subscription ID as authenticated associated data. They never appear in logs or MCP responses. The deployment encryption key must survive restarts, remain outside source, and be configured server-side in the prepared runtime adapter. Replacements sign with both keys for five minutes. Expiration/unsubscribe clears stored key material; dispatch clears expired rotation keys. A subscription defaults to 24 hours, caps all requests including `ttlMs: null` at 24 hours, and applies a one-minute minimum. There are no indefinite subscriptions.

Subscription creation starts after the current outbox sequence. Refresh of an active subscription preserves that sequence and pending retries. Refresh after expiration or unsubscribe resets the sequence, so old missed events are excluded. Responses return a finite `refreshBefore`, `cursor: null`, `truncated: false`; there is no protocol replay. Unsubscribe is owner-scoped, idempotent and cancels pending retries, including when project access has been lost. A request already sent cannot be recalled.

## Delivery and retry storage

`dispatchEvents` fans matching committed events into uniquely keyed subscription/event delivery rows. Each dispatch run is restricted to the Site principal bound to its stored application grant. Every send rechecks active subscription, expiration, project ownership, node existence and the current application grant. A claim and one-minute lease prevent overlapping dispatchers from taking the same attempt. A process crash recovers after lease expiration with the same event ID. An accepted callback whose local acknowledgment was lost can receive a duplicate.

The dispatcher serializes one event per request and signs those exact UTF-8 bytes. It requires HTTPS and rejects redirects. Bodies are limited to 256 KiB. Network/transport errors, HTTP 408, 429 and 5xx use exponential backoff with six attempts. The base delay is one second. Each retry has a fresh signing timestamp/signature. HTTP 410 disables the subscription; 413 and other permanent HTTP errors stop that delivery. This code does not send a callback from a graph mutation or rely on request traffic to revisit failed deliveries.

D1 stores the outbox, subscriptions and delivery attempts across process restarts. A host dispatcher must run independently of requests, revisit due rows and expired leases, and clean up expired secrets. Owner-scoped cleanup retains 30 days of minimal event data and deletes at most 250 old rows per table per dispatch. Pending/sending events and matching events not yet materialized for active subscriptions are protected. Delivery deduplication rows remain while their outbox event exists. Expired grants/subscriptions clear secrets and cancel attempts, even when delivery is denied. Migration `0005` preserves existing rowid cursors as explicit AUTOINCREMENT sequences; pruning and restart cannot reuse a sequence. Cleanup depends on the approved timer continuing to run; this is an age policy with bounded batches, not a fixed database-size cap. No Worker timer or unsupported queue/cron binding is added. The owner-scoped dispatch route returns 503 while runtime Events are disabled. No long-lived credential is provisioned.

## Sites service access and owner grants

Sites officially supports [hosting MCP servers](https://help.openai.com/en/articles/20001547-hosting-a-plugin-with-chatgpt-sites). Current Sites authentication guidance permits shared update endpoints on confirmed owner-private Sites to rely on the platform service-access boundary. A read-only check on 2026-10-04 confirmed Agen8 Dev is owner-private: its custom policy contains only the owner, with no other viewers, groups, editors or external visitors, and `requires_byop=false`.

The companion sends the existing, separately approved Sites service credential only to the exact Site dispatcher as `OAI-Sites-Authorization: Bearer <token>`. Sites validates and consumes that header. It supplies no visitor identity or connected-app consent. The dispatcher additionally requires its separate dispatch key, then derives the owner only from the configured grant ID in D1. Request headers/body cannot select an owner. No user ID is manufactured, and account metadata IDs must never substitute for the Site-specific authenticated principal. Preserve the confirmed private audience.

`createDispatchGrant` is a privileged helper behind `POST /api/events/access`, absent from MCP tools and the graph UI. This operational route defaults to 503 until the separate dispatch key is configured. After action-time approval, call it with the actual Sites-authenticated owner session and that key on this same Site: `{ "action": "grant", "ttlMs": 86400000 }`. The body cannot select a principal. A service caller without visitor identity cannot create or renew grants. Revoke with `{ "action": "revoke", "id": "<grant ID>" }` and the same authenticated owner/key requirements. It stores the actual Site principal with a random grant ID and a finite lifetime of one minute to 24 hours. The prepared runtime binds `grantOwnerAccess(db, grant.id)` to the configured grant ID shared by MCP and dispatch. No grant is created or activated by this PR. Grant creation/replacement cancels old subscriptions and pending attempts and clears signing secrets. `events/subscribe` cannot renew or revive a grant. Deliberate, approved grant renewal requires a fresh authenticated owner request and resubscription.

`revokeDispatchGrant` checks the original owner and grant ID, disables the grant, cancels pending/sending deliveries and clears stored signing keys atomically. Missing, expired, revoked or replaced grants deny subscribe and dispatch. Every send also rechecks the current grant and authoritative project/node ownership. An already-sent network request cannot be recalled. Authenticated MCP subscribe/refresh/unsubscribe keep their existing owner-scoped authorization; service access does not confer graph mutation or connected-app permissions through this route.

The [MCP Events contract](https://developers.openai.com/plugins/build/mcp-events) requires checking access throughout the subscription lifetime and testing account disconnection. Immediate Site-plugin disconnect notification/introspection and whether ChatGPT calls unsubscribe on disconnect remain unverified. Application-grant revocation works independently; finite grant/subscription lifetimes bound unattended access but do not prove immediate platform disconnection revocation. Keep live Events disabled until the intended disconnection policy is verified end to end. Do not invent an OAuth token-refresh or platform introspection contract.

## Runtime activation requirements

The supplied [Node companion](../../event-companion/README.md) implements connection-time public DNS validation/pinning with original TLS hostname and redirect rejection. Its supervised Docker dispatcher loop revisits D1 delivery rows independently of traffic; D1 retains retries and leases across restarts. The code is unprovisioned. Native Sites linked cloud schedules do not establish a queue/cron binding or a connection-pinning transport; absence of those interfaces is not proof that such support is impossible. The current Worker exports only `fetch` and adds no undocumented bindings.

Before activation, verify the approved independent scheduler, restart recovery, relay ingress/TLS/DNS and abort behavior, finite owner grant, disconnection/revocation policy, stable server-only AES-GCM key and bounded retention. A boolean readiness mock is not evidence of operational retries. Keep the Site origin and relay origin fixed in trusted deployment configuration and credentials out of source, prompts and logs.

The MCP and dispatch routes use `configuredEvents`, which returns no host unless `AGEN8_EVENTS_ENABLED=true` and all five server-only settings are present: `AGEN8_EVENT_RELAY_URL`, `AGEN8_EVENT_RELAY_TOKEN`, `AGEN8_EVENT_ENCRYPTION_KEY`, `AGEN8_EVENT_GRANT_ID`, `AGEN8_EVENT_DISPATCH_KEY`. Malformed enabled configuration fails closed with 503. Disabled discovery omits Events, the catalog is empty, subscribe returns `host_unavailable`, and dispatch returns 503. The environment declarations add no undocumented hosting binding. The operational access route needs only the separate dispatch key and genuine Sites owner session to bootstrap the finite grant. See the concrete [activation proposal and test runbook](live-activation.md). No settings, credentials, grants or subscriptions have been provisioned live.

## Validation and release

`tests/events.test.ts` uses in-memory SQLite/D1 and synthetic local callback functions. No real graph content leaves the machine. It checks filtering, isolation, rollback, independent HMAC signatures, challenge failures, URL/secret validation, cache/refresh/rotation, expiration, unsubscribe, retry backoff and terminal errors, leases/crash recovery, duplicate IDs, out-of-order versions, revocation and unchanged tools. The companion tests connection-time DNS pinning, mixed addresses, rebinding, TLS options, redirects and timeout/size defenses with mocks. Four additional integration tests run the actual routes and migrations against real D1 in workerd, including restart, rollback, tenant isolation, grant lifecycle and retention. A real loopback HTTP receiver test checks signatures, two transient failures and stable-ID deduplication using synthetic data. Real-host TLS, dispatch and SSRF validation remain unverified.

Run `npm run typecheck`, `npm run lint -- --max-warnings 0`, `npm test`, `npm run build` and `npm audit --audit-level=low`. The added `site-staging` CI job runs these checks; `event-companion` runs its tests and audit separately. Existing Go, web and container security gates remain mandatory. Staging dependencies received compatible security patches; root/legacy-web/Go manifests remain unchanged. The separate companion package pins one new dependency, `ipaddr.js@2.5.0`, with a clean audit. Pre-existing Go x/crypto/toolchain, npm and container OpenSSL findings still block release. Full staging source lint now passes with zero warnings. The staging audit decreased from 28 findings including one critical to eight high findings, all from the unpatched braces chain. Drizzle's legacy esbuild is narrowly overridden to its compatible API version 0.25.12; the actual TypeScript config/generator and existing schema snapshots validate unchanged. Root tooling decreased to seven high braces-chain findings, and legacy web audits are clean. Go 1.26.8/x/crypto 0.56.0 pass existing application tests, vet and a fresh clean vulnerability scan. Container OpenSSL is patched in the Dockerfile; exact-head CI scanning verifies the result. No gate was bypassed or force downgrade applied.

After runtime verification and security gates pass, the owner must authorize and perform the staging deployment and migration, plugin rescan, and a real Work/Cloud subscription test. User-requested monitoring supplies the callback and signing key through `events/subscribe`; developers do not hard-code a receiver or provision a live subscription during implementation. Verify callback challenge, filtered delivery, refresh, revocation and unsubscribe on the real host before describing events as available. Production merge/deployment requires separate authorization.
