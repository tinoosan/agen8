Architecture - Logging

Logging

Logging is process infrastructure. The daemon reads log configuration, the application composition root builds one root logger, and each service receives a scoped child logger.

On this page
  1. Ownership
  2. Configuration
  3. Service logger shape
  4. Rules

1. Ownership

Logging is not a domain service and it is not owned by any business service. It lives under internal/logging because logger construction is application infrastructure, not a public package contract. Services depend on the resulting *slog.Logger, not on config, environment variables, or process setup.

2. Configuration

The daemon reads AGEN8_LOG_LEVEL and passes it through daemon.Config.Logging into app.Config.Logging. NewApplication builds the process root logger once from that config and passes scoped loggers into services as they are constructed. Valid levels are debug, info, warn, and error. Empty means info. 

type Config struct {
    Level string
}

3. Service logger shape

The application composition root passes scoped loggers into services. Services use the logger they are given; they do not read environment variables, parse config, or build process loggers. A rebuilt service constructor accepts its logger directly, next to its real service/repository dependencies. 

root, err := logging.NewLogger(cfg.Logging)
taskSvc, err := taskapp.NewService(
    repo,
    clock,
    caller,
    members,
    projects,
    root.With("service", "task"),
)

Text output includes stable service context:

time=2026-06-05T15:42:10.124+01:00 level=INFO msg="task transition" service=task action=create task_id=task_123 project_id=project_1 status=pending assigned_to=member_worker claimed_by_member_id="" caller_user_id=user_1 caller_member_id=member_coordinator

The task service writes an INFO log after each successful lifecycle transition. Returned validation and persistence errors are not logged by the task service; the boundary that handles the returned error owns that log line. Mission and other rebuilt services should follow the same rule: log successful domain-significant transitions with stable ids, and let protocol/process boundaries log returned errors. 

time=2026-05-17T15:42:10.124+01:00 level=INFO msg="task transition" service=task action=create task_id=task_123 project_id=project_1 status=pending assigned_to=member_worker claimed_by_member_id="" caller_user_id=user_1 caller_member_id=member_coordinator

4. Rules

RuleReason
Logging config lives in internal/logging.Logging is app infrastructure, not a public package contract.
Services accept *slog.Logger.The composition root controls formatting and level.
Services receive scoped loggers.Every service log line includes service=<name>.
Logger construction happens once in NewApplication.Config stays in the process/application layer, while services receive ready-to-use dependencies.
Services do not log and return the same error by default.Returned errors are logged at the boundary that handles them.
Logging failures do not affect business behavior.Missing business dependencies still fail loudly; logger nil falls back to slog.Default().
