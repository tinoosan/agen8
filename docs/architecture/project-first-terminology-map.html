Project-First Terminology Map

This document defines the naming contract for Agen8's project-first coordination model. Runtime, API, schema, and UI language use project and member for coordination identity. External harness vocabulary remains isolated to harness-specific surfaces.

Hard cutover. space, SpaceMember, space_id, and related terms are removed, not aliased. The coordination boundary is the project. This document supersedes the retired space-first terminology map.

1. Canonical terms

ProjectDurable workspace and live coordination/context boundary (location + root).Not a chat thread and not a template instance. This is the team boundary for now.
MemberOne live harness session registered into a project, identified by (project_id, harness_kind, native_session_ref).Not a role and not a bare external session id.
MemberTypeCompatibility metadata retained by current APIs and storage.Not the public permission model, persona, or domain capability.

GroupReserved future term for an additive sub-team aggregate within a project.Not built yet; not a coordination boundary today.

2. Member ownership

A project is the coordination and context boundary. A Member is the Agen8 actor record for one connected harness session when the harness exposes a stable reference. Agen8 records member work; it does not own the external harness session.

Do not introduce run-backed projects. Member behavior derives from the Member record, harness kind, and optional native session reference. It does not derive from hidden containers, compatibility member type metadata, or role-owned runs.

3. Member type compatibility

Member type is compatibility metadata in the public baseline. Authorization is based on active same-project membership, not coordinator/worker categories.

TypeCurrent meaningNotes
coordinatorCompatibility value returned by older contracts.Does not grant unique permissions in the public baseline.
workerCompatibility value accepted from older callers.Normalized to the flat member-rights model.
reviewerTransitional compatibility value.Prefer explicit task review responsibility or future review policy.

Member type does not imply a domain role such as backend engineer or market analyst. Use member display names and future role snapshots for human-readable responsibility.

4. Roles

Role answers: what capability, persona, or domain expertise does this member bring?

Examples
Domain capability
Backend engineer, market analyst, product strategist, artist manager, macro researcher.
Sources
Managed or ad hoc
A role can come from an Agen8-managed role definition, an ad hoc capability declaration, or no role at all.

When a role exists, registration captures an effective snapshot and preserves source metadata.

5. Configuration terms

Member-facing contracts avoid ambiguous model or reasoning fields. They identify whether settings are defaults, desired settings, actual runtime settings, or harness constraints.

TermMeaning
template_default_settingsReusable settings from a project template.
project_default_settingsDefaults for new members in a project.
role_default_settingsPersona or capability preferences from a role.
member_desired_settingsSettings Agen8 or the user wants for this member.
harness_actual_settingsSettings reported by the external harness when available.
harness_capabilitiesControls and observations supported by the selected harness.

6. Lifecycle terms

LifecycleStates
Projectdraft, open, paused, closed, archived, deleting
Memberpending, active, inactive, disconnected, left, removed, expired

Member lifecycle and harness lifecycle are related but not identical. A member can remain registered after the external harness session stops exposing active metadata.

7. Naming rules

  1. Keep member_type only where compatibility with existing contracts or storage requires it.
  2. Use role only for capability, persona, or domain function.
  3. Use project_template for reusable project setup.
  4. Use project for the live coordination/context boundary.
  5. Use member for actor attribution.
  6. Use harness_session for external execution metadata.
  7. Use desired_* and actual_* prefixes for execution settings.
  8. Avoid introducing agent as the primary domain noun unless it means a broad product actor. Prefer member in project coordination APIs.
  9. Do not expose run_id as the main actor identity in new APIs.
  10. Reserve group for the future additive sub-team aggregate. Do not use it for the project boundary.
