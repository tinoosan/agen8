Architecture · Auth Service

Auth Service

The auth service owns credentials, sessions, API keys, and bearer-token validation. It does not own account identity. Account records live in the user service; auth receives a user.ID and proves that a request belongs to that account.

1. Architecture layers

Auth is a security boundary around credentials. It answers whether a credential is valid and which account it belongs to. It does not decide whether a user account exists, is active, or owns a project; those checks belong to the user and project services.

Protocol handler
Extract bearer tokens, login payloads, logout requests, and API-key commands. The handler stamps authenticated identity into context after auth validates a credential.
Service (credential orchestration)
Hash passwords, verify login attempts, create and revoke sessions, issue and revoke API keys, and validate bearer tokens.
Domain (auth subdomains)
password.Credential, session.Session, and apikey.Key are credential records keyed by user.ID. They never replace the user record.
Repository
Persist credential records only. It does not create users, members, or projects.

2. Auth subdomains

Auth is split into small subdomains so each package owns its names. Password credentials live in password, browser sessions live in session, and programmatic credentials live in apikey. User identity is imported as user.ID because the user service owns the account.

// internal/services/auth/password
type Credential struct {
    UserID       user.ID
    PasswordHash string
    CreatedAt    time.Time
    UpdatedAt    time.Time
}

// internal/services/auth/session
type Session struct {
    ID        ID
    UserID    user.ID
    TokenHash string
    ExpiresAt time.Time
    RevokedAt *time.Time
    CreatedAt time.Time
}

// internal/services/auth/apikey
type Key struct {
    ID        ID
    UserID    user.ID
    Name      string
    Prefix    string
    TokenHash string
    ExpiresAt *time.Time
    RevokedAt *time.Time
    CreatedAt time.Time
}

The raw session token and raw API key are returned only once, at creation time. The repository stores only hashes and prefixes.

The service struct

The constructor names each credential store explicitly. The user service is passed in as a loader so auth can validate that login and bearer-token results still point to an active account.

type Service struct {
    passwords password.Repository
    sessions  session.Repository
    apiKeys   apikey.Repository
    users     UserLoader
    clock     auth.Clock
    logger    *slog.Logger
}

func NewService(
    passwords password.Repository,
    sessions session.Repository,
    apiKeys apikey.Repository,
    users UserLoader,
    clock auth.Clock,
    logger *slog.Logger,
) (*Service, error)

3. Credentials

Password credentials are an auth concern. The daemon setup route and login RPC pass raw passwords only to auth methods. User service methods receive account fields and never receive raw passwords.

type CreatePasswordParams struct {
    UserID   user.ID
    Password string
}

func (s *Service) CreatePassword(ctx context.Context, params CreatePasswordParams) error
func (s *Service) VerifyPassword(ctx context.Context, userID user.ID, password string) error
RuleEnforced by
Raw passwords never enter user service or repositories.Daemon and RPC call auth credential methods first.
Password hashes are never returned in RPC responses.Auth RPC DTOs omit credential hashes.
Login requires an active user account.Auth validates the credential, then loads the user account.

4. Browser sessions

Browser sessions are the normal UI credential. Setup and login create sessions. Logout revokes the current session. HTTP daemon identity stamping validates the bearer token and stamps rpc.Identity{UserID, Role} into context.

type CreateSessionParams struct {
    UserID    user.ID
    UserAgent string
    RemoteAddr string
}

type CreateSessionResult struct {
    Session session.Session
    Token   string
}

func (s *Service) CreateSession(ctx context.Context, params CreateSessionParams) (CreateSessionResult, error)
func (s *Service) ValidateSession(ctx context.Context, token string) (user.User, error)
func (s *Service) RevokeSession(ctx context.Context, token string) error

5. API keys

API keys are programmatic credentials for CLI, MCP clients, automation, and hosted-style integrations. First-run daemon setup creates one initial daemon API key after the first user account is created so local MCP clients can connect immediately. Later API keys are explicit auth flows.

type CreateAPIKeyParams struct {
    UserID    user.ID
    Name      string
    ExpiresAt *time.Time
}

type CreateAPIKeyResult struct {
    APIKey apikey.Key
    Token  string

func (s *Service) CreateAPIKey(ctx context.Context, params CreateAPIKeyParams) (CreateAPIKeyResult, error)

6. First-run setup

Setup is daemon orchestration across user and auth. The user service creates the first account. Auth creates the password credential, browser session, and initial daemon API key for that account. The setup token belongs to the daemon and is never persisted by auth.

7. RPC adapter

Auth RPC exposes credential flows. User profile and account lifecycle methods live on user RPC. Auth RPC results return user-facing identity projection, session state, and API-key metadata, never password hashes or token hashes.

RPC methodService callBoundary rule
auth.loginService.LoginVerifies password and creates a browser session.
auth.logoutService.RevokeSessionRevokes the current browser session.
auth.sessionService.ValidateSessionReturns current authenticated account projection.
auth.apiKey.createService.CreateAPIKeyReturns the raw API key exactly once.
auth.apiKey.revokeService.RevokeAPIKeyRevokes a programmatic credential.

8. Persistence

Auth persistence is separate from user persistence. Tables are keyed by user_id, but the canonical user record remains in the user service table.

TablePurposeImportant columns
auth_passwordsPassword credential per accountuser_id, password_hash, created_at, updated_at
auth_sessionsBrowser bearer sessionssession_id, user_id, token_hash, expires_at, revoked_at
auth_api_keysProgrammatic bearer credentialsapi_key_id, user_id, name, prefix, token_hash, revoked_at
 
// internal/services/auth/session
type Repository interface {
    Reader
    Writer
}

type Reader interface {
    GetByTokenHash(ctx context.Context, tokenHash string) (session.Session, error)
}

type Writer interface {
    Create(ctx context.Context, record session.Session) error
    Update(ctx context.Context, record session.Session) error
}

password.Repository and apikey.Repository follow the same subdomain-owned reader/writer composition pattern.

9. Repository builder

The application composition root does not choose concrete auth repository types directly. Auth has three credential subdomain repositories, so its infra package builds them as one repository bundle from the configured storage handle.

// internal/services/auth/infra/repository_builder.go
type Repositories struct {
    Passwords password.Repository
    Sessions  session.Repository
    APIKeys   apikey.Repository
}

func NewRepositories(handle *storagedb.Handle) (Repositories, error) {
    if handle.Driver() != storagedb.DriverSQLite {
        return Repositories{}, fmt.Errorf("auth repositories require SQLite storage")
    }
    return newSQLiteRepositories(handle)
}

internal/app.NewApplication calls only authinfra.NewRepositories(handle), then passes the returned subdomain repositories into authapp.NewService. It does not import concrete SQLite repository types directly.

10. Code layout

internal/services/auth/
  password/
    credential.go        # Credential and password credential validation
    repository.go        # Reader / Writer / Repository

  session/
    session.go           # Session, ID, expiry and revocation state
    repository.go        # Reader / Writer / Repository

  apikey/
    key.go               # Key, ID, prefix and revocation state
    repository.go        # Reader / Writer / Repository

  auth/
    token.go             # token generation and hash contract
    clock.go             # Clock interface and system clock
    errors.go            # shared auth-domain errors

  app/
    service.go           # login, sessions, API keys, password credentials
    service_test.go      # service behavior with repository spies

  infra/
    repository_builder.go # storage strategy selection from configured handle
    sqlite_repository.go # SQLite auth credential repositories
    repository_assertions_test.go

  rpc/
    handler.go           # auth.login/session/logout/apiKey.* adapter
    types.go             # auth RPC params/results/views

internal/daemon calls auth for setup session creation and request identity stamping. Normal auth RPC lives under internal/services/auth/rpc. Auth does not live under pkg, and no application method wraps it.

11. Logging

Auth logs credential lifecycle events without writing raw tokens, token hashes, passwords, password hashes, session ids, API key ids, or API key prefixes.

level=INFO msg="session created" service=auth user_id=user_... source=login
level=INFO msg="api key revoked" service=auth user_id=user_...
level=WARN msg="credential rejected" service=auth reason=invalid_password email_hash=...

12. Invariants

InvariantEnforcement point
Auth never creates user accounts.Daemon and RPC create users through the user service only.
Raw bearer tokens are returned only once.Auth service creation methods return raw tokens; repositories store hashes.
Credential secrets and credential record identifiers never appear in RPC responses or logs.Auth RPC DTOs and logging helpers omit raw tokens, hashes, prefixes, session ids, and API key ids.
Setup creates a browser session and one initial daemon API key.Daemon setup calls CreateSession and CreateAPIKey after user setup.
Bearer validation returns a user account projection.Auth validates the token, then loads the user through UserLoader.
Closed or suspended accounts cannot authenticate.Auth rejects credentials when the loaded user is not active.
