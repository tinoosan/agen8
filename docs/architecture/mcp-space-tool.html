Architecture · MCP Space Tool

MCP space tool

The agent-facing coordination tool for spaces and the members registered inside them.

Purpose

space is an MCP tool, not a service API. It exposes one product-facing coordination contract to member harnesses and maps each action to typed application service calls. The handler owns request decoding, role-aware tool policy, cross-service orchestration, and deterministic result shaping.

Boundary. Space tool behavior lives in internal/mcp/tools/space. The space tool lists spaces and exposes member roster CRUD through composite actions. Message sending belongs to the separate message MCP tool. The space service owns space records, lifecycle, and the member roster subdomain. No service accepts raw space(...) tool JSON, and no service package defines a space-tool-specific service or port.

Control flow

Application wiring

The application composition root constructs SpaceSvc once. The same concrete service exposes space lifecycle methods and member roster methods. When the runtime supervisor spawns a managed harness, it registers an MCP session token that carries that concrete service as narrow handler-owned interfaces. The MCP server stores the session and supplies those interfaces to the native space handler when the agent calls space(...).

// MCP session bootstrap
tokenStore.Register(token, agen8mcp.Session{
    SpaceID:         spacedomain.SpaceID(spaceID),
    MemberID:        memberID,
    SpaceReader:     app.SpaceSvc,  // typed as space.SpaceService
    MemberDirectory: app.SpaceSvc,  // typed as space.MemberService
    MemberRegistrar: app.SpaceSvc,  // typed as space.MemberRegistrar
    ProjectID:       strings.TrimSpace(projectID),
})

// internal/mcp/server.go
space.NewHandler().Handle(ctx, space.CallContext{
    Spaces:        session.SpaceReader,
    Members:       session.MemberDirectory,
    Registrar:     session.MemberRegistrar,
    ProjectID:     session.ProjectID,
    SpaceID:       string(session.SpaceID),
    ActorMemberID: session.MemberID,
}, arguments)

Handler contract

The handler interface is MCP-owned. Service interfaces are consumer-owned and narrow: the handler declares only the methods it needs for list and the member_* composite actions. The MCP session token is already bound to a member id and space id, so the handler first stamps a provisional member-scoped caller.Caller into context.Context. It then resolves ActorMemberID through the member roster interface, requires an active member, and restamps the shared caller with the resolved member id, user id, and space id before service calls.

Caller bootstrapping happens before actor lookup. Member roster reads are space-service methods and require caller identity themselves; calling GetMember on an unstamped context is a capture bug, not an authorization fallback. MCP tools may seed context from the authenticated session token, but they must still resolve the actor record and let service authorization enforce visibility.

Runtime-resolved identity

The agent supplies discovery intent. Agen8 supplies runtime identity. The MCP session token already binds the call to a project, space, member, and channel, so those values are not agent-required request fields. The handler uses them to stamp caller context, resolve the active actor member, and authorize service calls.

MCP registration and delivery

space.register is the MCP-first entry point for harnesses. A harness can call it with only a working directory or project id. Agen8 resolves the project, creates or reuses the project space, creates or reuses the member identity, activates the durable harness session, and returns the ids the harness needs for later tool calls.

When a harness exposes a stable native session or thread id in the MCP call metadata, the MCP server passes that value through the space tool call context. The daemon stores it as the harness session reference. For Codex, the server reads the top-level MCP metadata fields threadId, thread_id, sessionId, and session_id, plus the optional x-codex-turn-metadata object that Codex sends with thread_id and session_id.

Boundary. MCP registration does not recreate Codex or Claude thread management. Agen8 stores a native session reference only when the connected harness exposes one. Tool calls, member ids, task ids, decisions, and graph records remain the durable Agen8 coordination surface. Native-thread delivery is an optional integration path for harnesses that can receive messages into an existing session.

After registration, Agen8 starts the per-member durable delivery worker. The worker drains queued member messages and wakes on new messages. If the registered harness has a routable native session reference, messages can reach that existing harness session. If no native reference exists, the same durable Agen8 records remain available through MCP tools and the inspection UI.

Role policy

Member typeVisible actionsReason
coordinatorlist, member_get, member_list, member_create, member_update_config, member_removeDiscovers spaces, sees routable peers, and manages the roster when coordination requires another member.
workerlist, member_get, member_listDiscovers the current space and routable peer identities. If a worker calls roster mutation actions, the tool rejects the request before mutation.

Visibility is prompt/tool-surface policy. Authorization remains enforced by the handler and the underlying services using caller identity from ctx. The handler rejects missing, removed, or space-less actor members before it calls SpaceSvc.
