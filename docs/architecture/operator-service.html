Architecture · Operator Service

Operator Service

The operator service is the durable boundary for work that leaves autonomous agent execution and requires human/operator attention. It owns the action and escalation subdomains, their lifecycle, task blocking side effects, decision creation, graph relationships, and operator-facing RPC state.

1. Purpose and ownership

The operator service has two subdomains. The action subdomain models work the operator must do outside the agent runtime. The escalation subdomain models a decision gate that needs operator attention. Both subdomains are durable product state, not transient tool output.

The operator service ownsThe operator service does not own
Canonical records for the action and escalation subdomains.Task lifecycle rules or task persistence.
Operator lifecycle transitions, validation, deduplication, and escalation urgency changes.Decision domain validation or decision persistence.
Task block/unblock orchestration through task service ports.Direct task row mutation.
Decision creation requests for operator completions and escalation resolutions.Direct decision row mutation.
Graph edge intent for operator-owned relationships.Contextlink row construction or graph storage.
Operator-facing RPC state and lifecycle commands.Frontend rendering, notification storage, or MCP transport schemas.

Protocol adapters call the operator service with typed app commands. Tool-specific request and result DTOs live in the MCP tool layer. The app service does not import MCP packages.

2. Subdomain model

The subdomains stay separate because the operator's job is different in each case. An escalation is a decision gate that resolves with an approve/reject verdict. An action is a work request that can stay in progress, collect notes, attach evidence, block, unblock, and optionally require agent verification.

PrimitiveQuestion it answersPrimary actorTerminal outcome
operator/actionWhat work must a human/operator perform outside the agent runtime?Operator as doer.completed or canceled.
operator/escalationCan the agent proceed, and under what instruction?Operator as decider.resolved or canceled.

3. Architecture layers

The operator service follows the same service shape as task, decision, and graph. Domain packages own state rules. The app service orchestrates side effects. Adapters translate transport payloads and never own lifecycle semantics.

RPC and MCP adapters
Translate opAction.*, escalation.*, and operator tool payloads into typed app commands. Tool request schemas live here, not in the app service.
Application service
Create and transition operator records, resolve work refs, call task/decision/graph ports, publish lifecycle events, and send operator-result messages.
Domain
Owns action.Action, escalation.Escalation, statuses, urgency, category, validation, and transition rules.
Repository
Persists and queries op_actions and escalations. It does not block tasks, create decisions, publish events, or write graph links.
Events and messages
Lifecycle events feed notifications and UI invalidation. Message ports notify affected members after operator resolution, completion, comments, or blocking.

4. Lifecycle state machines

Escalation lifecycle

An escalation stays pending until the operator resolves it, cancels it, or a deadline worker marks it expired. Resolution creates a decision and unblocks the task when a task is referenced.

Operator action lifecycle

An operator action is an asynchronous work item. Pending actions are acknowledged when an operator opens them or explicitly acknowledges them. Completion either finishes the item or moves it into verification when the requesting agent must accept the result.

5. Service boundary

6. Graph relationships

The operator service expresses relationship intent through the graph service. It never imports contextlink, never creates contextlink ids, and never writes graph rows directly. The graph service validates source and target visibility before storing each edge.

8. MCP tool

The operator MCP tool is the agent-facing adapter for the operator service. It supports two write actions and maps the session project, space, and member identity into typed app commands. The tool does not own lifecycle rules, graph writes, task blocking, or decision creation.

Tool actionCreatesRequired inputService path
requestoperator_actiontitle, description, category, urgencyoperatorapp.Service.Create
escalateescalationtitle, description, category, urgency, recommendationoperatorapp.Service.CreateEscalation

The MCP response is structured JSON with ok, tool, action, and either operator or escalation. Error responses stay visible to the agent; the tool never retries with fallback values for missing required fields.

The tool schema requires the fields shared by both actions: action, title, description, category, and urgency. Action-specific fields are included only when used: recommendation and confidence belong to escalate; run_id, blocking, and requires_verification belong to request. Explicit null values are rejected before service calls.

metadata is optional and accepts only a string-valued object: {"origin":"tool_smoke_test","test":"true"}. Boolean, numeric, array, nested-object, or JSON-string metadata values are rejected at the MCP boundary with a structured validation error.

9. Persistence

The operator service persists one table per subdomain. Repository contracts are split by package namespace and role, so callers import action.Reader, action.Writer, escalation.Reader, or escalation.Writer instead of stuttered names such as OperatorActionRepository.

10. Production wiring

internal/app.NewApplication constructs the operator repositories from the shared database handle, constructs one operator service, passes it graph, task, decision, event, and message ports, and stores it on Application. RPC registration and graph hydrators receive that same process-owned service.

The graph service hydrator list includes the process operator service so operator_action and escalation subdomain nodes are queryable through graph_query, graph RPC, and frontend graph reads.
