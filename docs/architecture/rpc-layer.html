Architecture · RPC

RPC layer

internal/rpc is the transport-agnostic JSON-RPC adapter. It owns envelopes, method registration, dispatch, error mapping, and request identity context. It does not listen on sockets, run HTTP, construct services, or own business rules.

1. Boundary

The daemon owns HTTP listening and web serving. RPC owns JSON-RPC. Services own use cases. Browser RPC calls enter through the daemon and share one service-backed semantic model.

Development web proxying is outside the RPC layer. When AGEN8_DEV_WEB_URL is set, the daemon reverse-proxies SPA assets and Vite hot-reload traffic after protocol routes are claimed. /rpc, /events, /healthz, and setup routes still terminate in the daemon and never pass through Vite.

internal/daemon
Runs the HTTP listener, authenticates transport identity, and calls rpc.Server.
internal/rpc
Decodes JSON-RPC, resolves methods, binds params, dispatches handlers, and encodes protocol responses.
internal/services/<service>/rpc
Owns service-specific RPC DTOs and maps them to typed service calls.
internal/services/<service>/app
Executes business orchestration, authorization, persistence, and service-to-service side effects.

2. Request flow

This diagram uses task.create as an example. Both listeners enter the same RPC server; transport authentication happens before dispatch.

  1. The daemon HTTP listener receives a browser RPC request.
  2. The daemon authenticates through HTTP session rules and stamps rpc.Identity into context.Context.
  3. rpc.Server decodes the JSON-RPC envelope and asks the registry for the named method.
  4. The RPC method registration maps rpc.Identity to the shared caller.Caller context contract.
  5. The service-owned RPC handler validates DTOs and calls a service method.
  6. The service owns business rules, persistence, and service-to-service side effects.
  7. The handler projects the service result into a result DTO and rpc.Server writes the JSON-RPC response.

The RPC server does not live under internal/app. Service-specific RPC adapters and DTOs live next to their service. The daemon wires app.NewApplication, rpc.NewRegistry, service registrations, and the selected listener.

4. DTO ownership

DTOs are transport shapes. They are intentionally separate from service command structs and domain types.

Type kindExampleOwner
JSON-RPC paramsTaskCreateParamsinternal/services/task/rpc
JSON-RPC resultTaskCreateResultinternal/services/task/rpc
Read viewTaskViewinternal/services/task/rpc
Service commandtaskapp.CreateTaskParamsinternal/services/task/app
Domain aggregatedomain.Taskinternal/services/task/domain
 
// internal/services/task/rpc/types.go
type TaskCreateParams struct {
    ProjectID     string   `json:"projectId"`
    AssignedTo  string   `json:"assignedTo"`
    Description string   `json:"description"`
    Title       string   `json:"title,omitempty"`
}

// internal/services/task/app/service.go
type CreateTaskParams struct {
    ProjectID     types.ProjectID
    AssignedTo  types.MemberID
    Description string
    Title       string
}

The handler performs the transport-to-service mapping. The service never receives raw JSON, method names, listener state, or bearer tokens.

5. Task read scoping

Task reads are scoped by the task service contract. RPC supplies authenticated caller identity and request filters; it does not bypass the service or query task storage directly.

Read caseRPC responsibilityService responsibility
task.getValidate taskId, stamp caller identity into context, call TaskSvc.Get, project TaskViewLoad the task through TaskRepository and enforce task access rules
task.listValidate paging and filter DTOs, map filters to domain.TaskFilter, call TaskSvc.List and TaskSvc.CountOwn canonical task filtering, counting, repository access, and user/member scoping rules
