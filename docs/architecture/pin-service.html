Architecture · Pin Service

Pin Service

The pin service owns the durable set of pinned graph nodes for a project. A pin is a lightweight focus marker — it resurfaces a mission, key result, task, or decision at the top of lists and search. It is the server-side source of truth that replaced per-browser localStorage, so a pin set survives across browsers, sessions, and everyone working in the project.

1. Purpose and ownership

A pin is not a work entity. It carries no lifecycle, no events, and no graph edges — it is a presentation affordance that says "keep this in front of me." The service therefore stays deliberately thin: it stamps the pin time, trims and validates input, and persists one row per pinned node. Everything richer (lifecycle, links, notifications) belongs to the entity that was pinned, not to the pin.

The pin service ownsThe pin service does not own
The canonical per-project set of pinned node refs.The pinned entities themselves (missions, key results, tasks, decisions).

The service follows the standard vertical layering: an RPC adapter translates the wire payload, the application service orchestrates trimming and time stamping, the domain validates the record, and the repository persists canonical state.

RPC adapter
Translates pin.add, pin.remove, and pin.list JSON-RPC payloads into typed service calls and maps domain errors onto wire codes. No caller identity is threaded — the project is the scope boundary.
Application service
Trims input, validates the composite key, stamps CreatedAt from an injectable clock, and delegates persistence. No side effects.
Domain
Owns Pin, Pin.Validate, the Reader/Writer/Repository contracts, and ErrNotFound.
Repository
A dialect-neutral SQL store embedded by the SQLite and Postgres repositories. Self-migrates the pins table at construction.

2. Scope: per-project and shared

A pin's identity is the composite key (project_id, node_ref). There is no member dimension: pins are shared across everyone working in the project, exactly mirroring the prior single-pinned-set-per-project localStorage behavior. Re-pinning the same node is idempotent — it preserves the original pin time rather than creating a duplicate. NodeType (for example "mission" or "decision") is advisory metadata so readers can render or filter without a second lookup; it is explicitly not part of the identity.

3. Service boundary

The application service has an explicit constructor that takes a small config. The repository is required; the clock defaults to a system clock so production wiring stays terse while tests can pin CreatedAt.

type Config struct {
    Pins  pindomain.Repository
    Clock Clock
}

func NewService(cfg Config) (*Service, error)

The three service methods are the entire surface:

MethodBehavior
Pin(ctx, projectID, nodeRef, nodeType)Trims, validates, stamps CreatedAt, upserts. Idempotent — re-pinning preserves the first-pinned time.
Unpin(ctx, projectID, nodeRef)Deletes the pin. Returns domain.ErrNotFound when the node was not pinned.
List(ctx, projectID)Returns every pin in the project, newest first. Requires a project ID.

4. Domain model

Pin is a flat record. Validate enforces only the minimal shape the store relies on — both halves of the composite key must be present.

type Pin struct {
    ProjectID string
    NodeRef   string
    NodeType  string // advisory, not part of identity
    CreatedAt time.Time
}

The repository contract is split into reader and writer halves so consumers depend only on what they use. The graph service, for instance, needs only the read side.

type Reader interface {
    List(ctx context.Context, projectID string) ([]Pin, error)
    Exists(ctx context.Context, projectID, nodeRef string) (bool, error)
}

type Writer interface {
    Save(ctx context.Context, pin Pin) error
    Delete(ctx context.Context, projectID, nodeRef string) error
}

5. Persistence and schema

The store is dialect-neutral: a single sqlStore holds all SQL, and the SQLite and Postgres repositories embed it. The only dialect-specific concern is placeholder rebinding. The driver is selected at construction by NewRepository.

Pins use the self-migrating vertical pattern (the same one the location service uses). At construction the store runs CREATE TABLE IF NOT EXISTS rather than going through the version-gated baseline snapshot. Adding pins is therefore additive and safe — it never forces a schema-version bump, so existing databases keep starting without a migration step.

CREATE TABLE IF NOT EXISTS pins (
    project_id TEXT NOT NULL,
    node_ref   TEXT NOT NULL,
    node_type  TEXT NOT NULL DEFAULT '',
    created_at TEXT NOT NULL,
    PRIMARY KEY (project_id, node_ref)
)

The composite primary key enforces identity at the storage layer. Save is an upsert: on conflict it refreshes node_type but preserves the original created_at, so re-pinning keeps a node's first-pinned time. An idx_pins_project index supports the project-scoped list query, which orders created_at DESC, node_ref ASC.

6. RPC surface

Three methods are registered under the project scope. They take no caller identity — the project ID in each payload is the authorization boundary.

MethodRequired paramsResult
pin.addprojectId, nodeRef (nodeType optional){ pin } — the persisted PinView
pin.removeprojectId, nodeRef{ removed } — false when the node was not pinned
pin.listprojectId{ pins } — newest first

Missing projectId or nodeRef returns invalid-params (-32602). pin.remove is intentionally idempotent: a not-pinned node is treated as success with removed: false, so a client can unpin without first checking state.

7. Search ranking integration

The pin set has one cross-service consumer: graph_query search. The graph service exposes a PinReader port; the application wires the pin service into it at startup through a small adapter that flattens a project's pins to a set of node refs.

Pinned status is a primary sort key in the graph results: pinned hits surface ahead of unpinned ones while relevance and recency still order within each group. The dependency is optional and degrades safely — if the pin lookup is absent or errors, the graph service treats the pinned set as empty and ranks purely by relevance. A pin boost re-ranks the candidate set a search already matched; it does not resurrect a node the query did not match. The frontend applies the same idea in node-ranking surfaces, including the strategy-map search UI.
