Architecture · Human Input Service

Human Input Service

The human input service is the production boundary for pausing autonomous execution when a human answer is required, delivering a structured prompt to the right human surface, accepting exactly one answer or cancellation, and resuming the waiting tool call with an auditable result.

1. Purpose and ownership

Human input is not a chat message and not a decision record. It is a pending execution gate. A tool call declares that it cannot continue without bounded human judgment, the service persists that request, the UI resolves it, and the blocked tool call resumes with a typed result.

The human input service ownsThe human input service does not own
Pending request lifecycle, persistence, deadlines, and result storage.The final decision audit record.
Structured primitives: questions, approve/reject, confirm, and form.Agent prompt wording outside the declared payload.
Exactly-once resolution by answer, cancellation, expiry, or caller abort.Task, mission, or plan domain state transitions.
Operator-facing delivery state and wake/resume signals.Long-term notification inbox history.
Recovery of pending requests after daemon restart.Rendering transcript cards for completed decision records.

The decision service consumes the resolved output. For decision(action="ask_user"), the decision tool asks the human input service to wait, receives a QuestionsResult, then calls DecisionSvc.CompleteAskUser. This keeps pending lifecycle out of the decision audit boundary.

2. Domain model

The current domain primitives are the transport-neutral payloads. The service wraps them in a durable request record with identity, state, deadlines, and idempotency keys.

type Declaration struct {
    Kind    PrimitiveKind   // questions, approve_reject, confirm, form
    Payload json.RawMessage // valid JSON matching Kind
}

type Request struct {
    ID             RequestID
    ToolCallID     string
    ToolName       string
    ProjectID      string
    AskerMemberID  string
    ChannelID      string
    Declaration    Declaration
    Status         Status
    Result         json.RawMessage
    CreatedAt      time.Time
    ExpiresAt      time.Time
    ResolvedAt     *time.Time
    IdempotencyKey string
    Version        int64
}
StatusMeaningTerminal
pendingThe request is visible to the human and the tool call is waiting.No
answeredThe human submitted a valid result payload.Yes
cancelledThe human intentionally cancelled the request.Yes
expiredThe deadline passed before resolution.Yes
abortedThe waiting runtime/session ended before resolution.Yes

3. Lifecycle

Creation and terminal transitions run in transactions. A request is visible only after the pending row and delivery event are both durable. Resolution updates the row and publishes the wake signal in the same unit of work or an outbox-backed equivalent.

4. Awaiter contract

The daemon exposes the service to MCP as an Awaiter. The awaiter blocks the tool execution path until the request reaches a terminal state or the context is cancelled.

type Awaiter func(
    ctx context.Context,
    req humaninput.PendingRequest,
) (json.RawMessage, error)

The awaiter is not a polling loop hidden inside the decision tool. It is a service-backed wait: create pending request, subscribe to wake signal, return the typed result, and cleanly unblock when the context ends. If daemon restarts while a request is pending, the service keeps the request visible and the resumed session can reattach using ToolCallID and IdempotencyKey.

5. Repository design

The repository stores pending and terminal requests in one current-state table plus a transactional outbox. Request state is updated in place because the UI, resolver, awaiter, and restart recovery paths all need one canonical row. Auditing is carried by resolver fields, terminal timestamps, version, and outbox events rather than by raw debug logs.

CREATE TABLE human_input_requests (
    id TEXT PRIMARY KEY,
    tool_call_id TEXT NOT NULL,
    tool_name TEXT NOT NULL,
    idempotency_key TEXT NOT NULL,
    project_id TEXT NOT NULL,
    project_id TEXT NOT NULL,
    asker_member_id TEXT NOT NULL,
    channel_id TEXT NOT NULL,
    declaration_kind TEXT NOT NULL,
    declaration_payload_json TEXT NOT NULL,
    status TEXT NOT NULL,
    result_json TEXT NOT NULL DEFAULT '{}',
    resolver_user_id TEXT NOT NULL DEFAULT '',
    resolver_member_id TEXT NOT NULL DEFAULT '',
    terminal_reason TEXT NOT NULL DEFAULT '',
    created_at TEXT NOT NULL,
    expires_at TEXT NOT NULL,
    resolved_at TEXT,
    version INTEGER NOT NULL DEFAULT 1
);

CREATE UNIQUE INDEX idx_human_input_idempotency
    ON human_input_requests(project_id, tool_name, tool_call_id, idempotency_key);

CREATE INDEX idx_human_input_pending_scope
    ON human_input_requests(project_id, project_id, status, created_at);

CREATE INDEX idx_human_input_channel_pending
    ON human_input_requests(channel_id, status, created_at);

CREATE INDEX idx_human_input_expiry
    ON human_input_requests(status, expires_at);

The outbox is written in the same transaction as request creation or terminal transition. A dispatcher publishes events and marks rows delivered. This makes notification and wake delivery retryable without creating prompts that have no durable event path.

CREATE TABLE human_input_outbox (
    id TEXT PRIMARY KEY,
    request_id TEXT NOT NULL,
    event_type TEXT NOT NULL,
    payload_json TEXT NOT NULL,
    created_at TEXT NOT NULL,
    delivered_at TEXT,
    attempts INTEGER NOT NULL DEFAULT 0,
    last_error TEXT NOT NULL DEFAULT ''
);

The domain exposes narrow repository contracts. The application service depends on Repository; UI queries and expiry workers depend on the smallest reader or writer contract they need. Outbox claiming is infrastructure owned by the dispatcher, not part of the service-facing repository surface.

type Reader interface {
    Get(ctx context.Context, id RequestID) (Request, error)
    FindByIdempotency(ctx context.Context, key IdempotencyKey) (Request, error)
    ListPending(ctx context.Context, filter Filter) ([]Request, error)
}

type Writer interface {
    CreatePending(ctx context.Context, req Request) (Request, error)
    Resolve(ctx context.Context, cmd ResolveMutation) (Request, error)
    ExpireDue(ctx context.Context, now time.Time, limit int) (ExpireBatch, error)
    AbortByToolCall(ctx context.Context, toolCallID ToolCallID, reason string) (Request, error)
}

type Repository interface {
    Reader
    Writer
}
Repository methodContract
CreatePendingInserts a pending request or returns the existing row for the same idempotency key. Also inserts humaninput.pending into the outbox.
GetLoads one request by id. Missing rows return a not-found error, never an empty request.
FindByIdempotencyReattaches retries and daemon restarts to the same request.
ListPendingReturns visible pending requests by project, project, channel, member, kind, and pagination.
ResolveAtomically changes pending to answered or cancelled with expected version. Also inserts humaninput.resolved.
ExpireDueClaims due pending rows, marks them expired, and emits resolved events. Returns an aggregate report and surfaces per-row failures.
AbortByToolCallMarks a waiting request aborted when the owning runtime can no longer resume.

Repository implementations validate JSON before writing, preserve declaration and result payloads exactly, and return typed conflict errors for terminal rows or version mismatches. They do not decode primitive-specific answers for business validation; that belongs in the domain/service boundary before mutation.

6. Delivery and wake behavior

Human input delivery uses the same product-facing notification discipline as other agent-visible events: semantic payloads, stable IDs, and no raw debug fallback. The service publishes two event classes:

EventWhenConsumers
humaninput.pendingA pending request is durable and ready for the human.Notification service, UI live query, activity feed.
humaninput.resolvedThe request becomes answered, cancelled, expired, or aborted.Awaiter wake path, notification dismissal, activity feed.

Delivery targets the request's ChannelID, ProjectID, and asking member identity. The UI may show pending input in a global queue and in the relevant project, but list, view, resolve, and cancel calls are authorized by the RPC/UI adapter against the project/project and human user context, not against whichever tab displays it.

7. Production edge cases

CaseRequired behavior
Duplicate tool retryUse IdempotencyKey plus ToolCallID. Return the existing pending or terminal request, never create another visible prompt.
Double submitOptimistic version check. The first terminal update wins; later submissions receive a conflict with the existing terminal state.
Daemon restartPending requests remain queryable. Awaiters reattach or fail visibly if the original runtime cannot resume.
Runtime cancellationContext cancellation marks request aborted only when the waiting tool call is no longer resumable. The UI shows the terminal reason.
Human closes browserNo state change. Request remains pending until answer, cancel, expiry, or abort.
Expired requestDeadline worker marks expired, stores a terminal result payload, dismisses notifications, and wakes awaiters with an expiry error.
Invalid answer payloadReject at the RPC/API boundary with field-level validation errors. Do not store partial answers.
Missing delivery targetCreation fails loudly. No pending row is created without project, project, member, channel, declaration, and tool identity.
Unauthorized resolverThe RPC/UI adapter rejects the request before calling the service mutation. The request remains pending and the attempt is auditable.
Schema evolutionPersist primitive kind and payload version. Old pending payloads remain renderable and resolvable until terminal.
Large form payloadEnforce payload and result size limits before persistence; return validation errors instead of truncating.
Notification outageUse an outbox or transactional event table. Request creation is not considered complete until delivery can be retried durably.

8. Production dependencies

The service is constructed with the dependencies needed to enforce human-input invariants. Runtime delivery and authorization sit at the edge around the service instead of being hidden inside it.

DependencyLayerPurpose
RepositoryCore servicePersists current request state and outbox rows transactionally.
ClockCore serviceSupplies deterministic creation, expiry, and resolution timestamps.
IDGeneratorCore serviceCreates request and outbox IDs before persistence.
PrimitiveValidatorCore serviceValidates declaration and answer payloads for each primitive kind.
LoggerCore serviceRecords lifecycle failures with request, project, tool, status, and correlation IDs.
OutboxDispatcherRuntime infrastructurePublishes durable outbox rows to notification and wake consumers, then marks delivery attempts.
WakeRegistryRuntime infrastructureConnects waiting tool calls to terminal request events and context cancellation.
AccessPolicyRPC/UI adapterAuthorizes list, view, resolve, and cancel calls before invoking service commands.

Logs are operational evidence, not product state. The service logs declaration rejection, repository failure, outbox publish failure, wake timeout, duplicate terminal submission, and expiry batch errors with structured fields. It never logs raw answer payloads or undeclared prompt text. Authorization denials are logged at the RPC/UI edge because the core service receives already-authorized commands.

9. Service interfaces

The application service exposes narrow commands. RPC and MCP adapters translate transport payloads into these commands; they do not mutate repositories directly.

type Service struct {
    requests   Repository
    clock      Clock
    ids        IDGenerator
    validators PrimitiveValidator
    logger     *slog.Logger
}

func (s *Service) Declare(ctx context.Context, cmd DeclareCommand) (Request, error)
func (s *Service) Await(ctx context.Context, id RequestID) (json.RawMessage, error)
func (s *Service) Resolve(ctx context.Context, cmd ResolveCommand) (Request, error)
func (s *Service) Cancel(ctx context.Context, cmd CancelCommand) (Request, error)
func (s *Service) ExpireDue(ctx context.Context, now time.Time) (ExpireReport, error)
func (s *Service) ListPending(ctx context.Context, filter Filter) ([]Request, error)

Every command captures domain arguments: project, project, channel, tool name, tool call ID, primitive kind, and payload. Test doubles for this service capture those arguments; they do not discard them.

InvariantEnforced by
A pending request has exactly one terminal result.Repository transaction, status guard, and optimistic version.
No prompt is visible without durable state.Declare transaction persists request before publishing humaninput.pending.
No raw payload fallback appears in product UI.Primitive-specific renderers and missing-payload error states.
Answer shape matches declaration kind.Boundary validation before Resolve mutates state.
Tool retries are idempotent.ToolCallID and IdempotencyKey uniqueness.
Awaiters never wait forever silently.Context cancellation, expiry worker, and wake signal timeout handling.
Operational logs never become state.Repository rows and outbox messages are the durable source of truth; logger writes are structured diagnostics only.
