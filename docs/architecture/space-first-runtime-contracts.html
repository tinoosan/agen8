Architecture · Runtime Model

Space-First Runtime Contracts

Agen8 coordinates work through spaces and space members. A space is the live context boundary. A member is the actor identity inside that boundary. Harness sessions and runs are execution details owned by managed members, not the product identity.

1. Runtime model

Agen8 uses a space-first, managed-member model. Space is the durable coordination boundary. SpaceMember is the live actor registered into a space. MemberType is structural and contains coordinator or worker. A transitional reviewer type may exist only as a dedicated review member while review policy moves into capabilities.

Identity rule. A coordinator remains a coordinator whether or not workers are currently present. Agen8 does not derive a separate lone-coordinator runtime identity.

4. Registration contract

Registration is the boundary where Agen8 creates a managed member in a space. The caller supplies an existing space_id, requested member type, display name, harness kind, optional role or ad hoc capability declaration, and desired execution settings.

Registration outputPurpose
Member id and channel idStable actor identity and routing address.
Granted member typeValidated structural behavior. Coordinator requests store coordinator directly.
Granted permissions and tool scopesRuntime and MCP authorization context.
Briefing artifact/versionTraceable per-member coordination contract.
Managed run bindingHarness delivery address once provisioned.
Coordinator admission. A space has at most one active coordinator member. If an active coordinator already exists, another coordinator registration fails by policy. Type changes go through the member service rather than direct record mutation.

5. Briefing contract

A briefing is per member and per space. It includes member identity and type, role/profile snapshot summary, granted and denied capabilities, coordination rules, task/decision/plan/request conventions, message routing rules, ask-user/escalation rules, context bootstrap links, and cross-space constraints.

Briefing versions are persisted for traceability. Prompt/system instruction injection is the managed harness startup mechanism, not an attached-session fallback strategy.

6. Cross-space communication

Cross-space communication routes between spaces through active coordinator members. Each message carries source space/member, target space/coordinator member, kind, correlation id, causation id, optional structured context links, and delivery/ack state.

Channels remain UI presentation lanes. Routing authority comes from space identity and coordinator member identity. Raw chat is allowed, but messages should link to tasks, requests, decisions, plans, files, or handoffs when coordination produces structured work.
