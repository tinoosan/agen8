Task Service

How tasks are modelled, validated, and moved through their lifecycle inside agen8 — domain rules in one pure layer, side effects in a deliberate seam.

1. Architecture layers

Each layer has one responsibility. Protocol adapters translate requests into typed service commands. Side effects flow downward through the service into the repository and message publisher; rules and validation flow inward into the pure domain.

Protocol handler
Translate JSON-RPC or MCP payloads into typed task service commands. Tool names, action strings, schemas, and response cards live here, not in the service.
Service (orchestration)
Authorize the caller. Load the task. Call the domain transition. Persist and publish through a single seam. Side effects live here, deliberately.
Domain (pure rules)
domain.Task, domain.TaskID, domain.TaskStatus, and acceptance criteria live in the task domain. The task record exposes named transition methods. Each validates the source state and required inputs, returns the next state or a precise error. No repositories, no tool semantics, no old pkg/types task model.
Repository
Persistence only. Stores the next state the service hands it; does not evaluate rules.
Messages
Agent notifications are created through the message service boundary after task persistence succeeds.

The task domain owns the task record

domain.Task is the canonical task record persisted by the repository. domain.TaskID is the only typed task identifier. RPC projects the domain record into internal/services/task/rpc.TaskView, keeping transport fields separate from lifecycle state.

current, err := repo.GetTask(ctx, taskID)          // taskID is domain.TaskID
next, err := current.Cancel(reason, now)            // domain.Task -> domain.Task
err = repo.UpdateTask(ctx, next)                    // persists the domain record

The service struct

The application service owns orchestration. It resolves the caller from context.Context, validates member and project boundaries, calls the pure domain transition, persists the next task state, and publishes agent messages through the message service. It does not accept a dependency bag; the constructor lists the service boundary explicitly.

type Service struct {
    tasks    domain.TaskRepository
    clock    domain.Clock
    caller   caller.Resolver
    members  MemberLoader
    projects   ProjectLoader
    messages MessagePublisher
    logger   *slog.Logger
}

func NewService(
    tasks domain.TaskRepository,
    clock domain.Clock,
    caller caller.Resolver,
    members MemberLoader,
    projects ProjectLoader,
    messages MessagePublisher,
    logger *slog.Logger,
) (*Service, error)
// internal/caller
type Caller struct {
    UserID   string
    MemberID types.MemberID // optional for user-owned RPC calls
    ProjectID  types.ProjectID
    Role     string
}

2. RPC adapter

The JSON-RPC task handler is a thin CRUD adapter over the task service. It translates request DTOs into typed service calls, validates transport payloads such as UUID strings, and returns TaskView. Repository access stays inside the service boundary, and agent lifecycle actions stay on the MCP task tool.

The RPC registry binds task.create, task.get, task.list, and task.update through internal/app/rpchandlers/task.go. The registry receives the process-owned *taskapp.Service from the application composition root; it does not construct a task service and it does not receive a repository.

type Handler struct {
    svc *taskapp.Service
}

func (h *Handler) Create(ctx context.Context, p TaskCreateParams) (TaskCreateResult, error)
func (h *Handler) Get(ctx context.Context, p TaskGetParams) (TaskGetResult, error)
func (h *Handler) List(ctx context.Context, p TaskListParams) (TaskListResult, error)
func (h *Handler) Update(ctx context.Context, p TaskUpdateParams) (TaskUpdateResult, error)
// internal/caller
func ContextWithCaller(ctx context.Context, caller Caller) context.Context

type ContextResolver struct{}

func (ContextResolver) ResolveCaller(ctx context.Context) (Caller, error)

Adapters stamp the authenticated caller into context.Context before invoking service methods. The task service consumes the same internal/caller contract as the project service, so service-to-service orchestration keeps caller identity intact. The resolver fails when both UserID and MemberID are missing. MemberID is optional because the human user can use RPC without acting as an agent member. The service never infers a member from a user id, project id, or runtime session.

RPC methodService callBoundary rule
task.createService.CreateCreates a pending task and publishes the assignment message through the service.
task.getService.GetReads one task and projects it to TaskView.
task.listService.List + Service.CountApplies service-owned filters, including project, assignee, claim, status, task kind, and plan refs.
task.updateService.UpdateCoordinator-only data edit. It updates title, description, acceptance criteria, refs, kind, and metadata; it does not run lifecycle transitions.

TaskView contains the task service read model: ids, project/member assignment, creator actor, description, acceptance criteria, status, artifacts, KR and plan refs, metadata, and lifecycle timestamps.

3. The task lifecycle

A task moves through a focused state machine via named transitions. Each transition is a method on domain.Task that takes its inputs and the current time explicitly, and returns either the next state or an error. Terminal states (Succeeded, Failed, Canceled) have no outgoing transitions.

Service actions

The product-facing task surface stays small. Read actions never publish messages. Mutations publish only when another agent needs to act.

ActionService methodMessage?Why

get / listGet / ListnoRead-only actions do not wake agents.
updateUpdatenoCRUD data edits do not represent a lifecycle transition.
claimClaimnoThe caller already knows they claimed the task.
releaseReleaseyes, releasedThe coordinator needs to decide what happens next.
submitCompleteyes, review_requestedThe coordinator needs to review the completed work.
blockBlockyes, blockedThe coordinator needs to resolve the blocker or escalate.
unblockUnblockyes, unblockedThe assigned worker can continue after the claimant or coordinator clears the blocker.
review retryRetryReviewyes, retry_requestedThe worker needs feedback and another pass.
review approveApproveReviewnoThe worker is done; no action is required.
review failFailReviewnoNo action is required unless the coordinator separately retries or cancels.
cancelCancelyes, canceled, when someone may still be workingThe assigned or claimed worker needs to stop work.

Task message kinds

The task service owns lifecycle notification timing because it is the layer that knows whether a state change committed. Message composition is typed and event-specific. A task message is a wake-up envelope: it includes canonical ids, the lifecycle event, the intended next action, and short event-specific context. It does not duplicate the task read model because the receiver can call task.get with the provided taskId.

KindPublished byRecipientMessage guidance
assignedCreate and assignment correctionassigned worker/memberClaim the task before starting work. Work against the acceptance criteria and submit it for review when complete.
review_requestedCompletecoordinatorReview the worker summary, artifacts, and acceptance criteria. Approve only when every criterion is satisfied; otherwise request a retry with concrete feedback.
retry_requestedRetryReviewassigned worker/memberContinue from the active task state. Focus on coordinator feedback and unsatisfied acceptance criteria, then submit again when the remaining work is complete.
releasedReleasecoordinatorThe worker returned the task without completing it. Decide whether to assign it again, change the direction, or cancel it.
blockedBlockcoordinatorThe worker cannot continue without intervention. Resolve the blocker directly, escalate for human action when needed, then unblock the task.
unblockedUnblockassigned worker/memberContinue from the current task state and submit for review when the acceptance criteria are satisfied.
canceledCancelassigned or claimed worker/memberStop working on the task. Do not claim, continue, or submit it unless a coordinator creates or assigns a new task.

Every task message body includes event, taskId, projectId, actorMemberId, targetMemberId, nextAction, guidance, and a concise human-readable message. Review-ready messages may include the worker summary. Retry, blocker, and cancel messages include a short reason. Unblock messages may include a short note. Message bodies do not include task descriptions, acceptance criteria, artifacts, metadata, plan refs, or KR refs; those live behind task.get.

Acceptance criteria as review state

Acceptance criteria are task state, not metadata. Creation turns criterion text into stable criterion objects. Review transitions update their satisfaction state so a retry can tell the worker which criteria already passed and which still need work.

type AcceptanceCriterion struct {
    ID        string `json:"id"`
    Text      string `json:"text"`
    Satisfied bool   `json:"satisfied"`
}

Review commands do not rewrite criterion text. They submit outcomes for existing criterion ids:

type CriterionReview struct {
    ID        string
    Satisfied bool
}
Review ruleReason
ApproveReview requires every criterion to be satisfiedApproval means the task meets the coordinator's stated acceptance bar.
RetryReview accepts partial satisfactionThe worker receives durable state for what passed and what remains.
FailReview records criterion outcomes and requires a reasonThe terminal failure preserves why the task did not satisfy the bar.
Unknown, duplicate, or missing criterion ids fail the reviewPartial review payloads are ambiguous and stale ids hide protocol bugs.

Anatomy of a lifecycle call

1
Handler decodes the protocol payload and builds a typed command such as CreateTaskParams, CompleteTaskParams, or ReviewTaskParams.
2
Service authorizes the caller. User-owned actions verify the user against the task's project; member-scoped actions verify the caller against the task's assigned or claimed member.
3
Service loads the current task with the typed id: current, err := repo.GetTask(ctx, taskID).
4
Service calls the domain transition: next, err := current.Cancel(reason, clock.Now()). If validation or state rules fail the call returns an error before any side effect.
5
Service persists the next state and, when another agent needs to act, publishes the corresponding agent message through one service-owned seam. The task service calls the message service boundary; it does not write the message repository directly.

4. Routing model — tasks go to members

Tasks are routed by member id. Every task has exactly one assigned member. Assigning a task to a different worker is still assignment; it is not a separate product concept.

  • AssignedTo holds the member id.
  • ClaimedByMemberID records the member currently doing the work.
  • Claim fails when the caller is not the assigned member.

This makes the claim authorization question direct: is the caller the assigned member? If yes, the claim succeeds; if no, it fails.

5. Caller identity — user vs. agent

"User" and "agent" are calling-context kinds, not roles. The service determines which kind is calling from the request context and authorizes accordingly.

User (human)
UserID
present (authenticated session)
MemberID
optional / usually absent
Authorized for
create, update, assign, review, and cancel when the user owns the task's project
Agent
UserID
project tenant
MemberID
present
Authorized for
claim, complete, block, and release by assigned/claimed member; unblock by assigned/claimed member or same-project coordinator; create, assign, review, update, and cancel by coordinator members

User-owned calls authorize against Project.UserID. Member-owned calls authorize against the member record and member type. When both UserID and MemberID are present, member authorization is used so a worker cannot become a coordinator just because the owning user is also authenticated.

Authorization happens at the service boundary, before any domain transition runs. The domain assumes any caller it sees has already been authorized — it only validates state and inputs.

6. Task history belongs to events

The task service does not own an embedded activity log. Task history is a read model over the event service: events that refer to a task carry a canonical task id in their structured data, and the UI queries the event service for those task-associated events when it needs an activity timeline.

EventRecord{
    Type: "task.review_requested",
    Data: map[string]string{
        "taskId": "task_...",
    },
}

The event service owns event persistence, event querying, and task-history projection. The task service may emit task-related events as part of lifecycle orchestration, but it does not copy those events into Task.Metadata and it does not expose a task-history mutation method.

Boundary ruleReason
Task history is queried from the event serviceThe event service already owns append-only event persistence and timeline queries.
No TaskActivity type in the task domainThe task aggregate stays focused on lifecycle state, assignment, review, blockers, and task data.
No task activity projector writes back to tasksEvents are not duplicated into Task.Metadata.
Task-related events carry taskIdThe UI can build the activity timeline by asking the event service for events associated with that task.

7. Persistence and message publishing

Only state changes that require another agent to act publish messages. That keeps the message stream useful: messages wake agents for assignment, review, retry, release, blockers, unblock, and cancel. Approval and failure do not notify the worker because no worker action is required.

Every notification-producing state change passes through a single seam that orders task persistence before message publishing and surfaces the two outcomes distinctly:

1
Repository writes the next state. On failure the seam returns the error — no message is published, no side effect leaks.
2
Message publisher creates the corresponding AgentMessage through the message service boundary. The task service never receives or calls a message repository.

Two outcomes are meaningfully different to callers:

  • Caller receives an error. The task repository did not commit, or the message service rejected the notification. State is unchanged unless the service method explicitly documents a committed-before-notify result.
  • Caller receives no error. The task state committed and the message service accepted the notification for persistence and delivery.

Repository implementation

The task repository is a concrete infra concern. The domain declares the repository contract; internal/services/task/infra owns the SQL-backed implementations. The repository stores the canonical domain.Task document and maintains query columns for task-list filters.

ColumnPurpose
task_idPrimary key, mirrored from Task.ID.
project_idProject-scoped list and ownership filter.
assigned_toAssigned member filter.
claimed_by_member_idClaimed member filter.
task_kindTask kind filter.

key_result_refKR linkage for strategy and review surfaces.
created_at, updated_at, completed_atOrdering and date-range filters.

Metadata is preserved in task_json for task-owned extensibility only. Task history is not stored in metadata; it is queried from the event service by task id.

The repository implements CreateTask, UpdateTask, GetTask(ctx, domain.TaskID), ListTasks, and CountTasks. It fails loudly for unsupported metadata filtering until metadata query semantics are defined.

8. Invariants — what cannot happen

The design forces these states to be unreachable. Each row is enforced by the listed mechanism; there is a regression test for every row in internal/services/task/domain.

State that cannot occurEnforced by
Task with empty ProjectID, CreatedBy, AssignedTo, or DescriptionNewTask returns an error before any repository call
Task claimed by the wrong memberClaim compares the caller member id to AssignedTo
Task with status Active but no ClaimedByMemberIDClaim is the only normal entry to Active; Complete rejects unclaimed active tasks
Worker output marked Succeeded without coordinator reviewComplete moves Active to In Review only; ApproveReview is the success transition
Approved task with unsatisfied acceptance criteriaApproveReview requires a criterion outcome for every criterion and rejects any unsatisfied result
Retry that loses completed criteriaRetryReview persists the reviewed satisfaction state before returning the task to Active
Task with status Canceled or Failed but no reasonCancel and FailReview reject empty reason
Status transition outside the state machineEvery transition method validates the source status
Pending task with a stale ClaimedByMemberIDRelease drops the claim
No-action lifecycle update spamming agentsApproval and failure do not publish worker messages; retry or cancel carries the next action when one exists
Re-claiming a terminal taskClaim rejects unless the source status is Pending
User-owned action by an unauthorized callerThe service checks user ownership or coordinator membership before state changes
