1. Service boundary

The graph service owns relationship storage, relationship validation, graph node hydration, neighbourhood expansion, graph search, and agent-facing graph mutations. It exposes typed application methods and protocol adapters; repositories remain private to the service.

Boundary. contextlink is a graph subdomain. It owns the persisted edge aggregate and edge repository. The graph application service owns product operations such as Node, Search, Link, and Unlink. MCP and RPC adapters call the graph service, not the contextlink repository.

Other services create graph edges through graph application ports when their domain events produce durable relationships. The decision service links decisions to referenced work. Task and mission services expose read ports used by graph hydrators; they do not embed graph traversal logic.

The graph service ownsThe graph service does not own
Canonical context link records and graph edge validation.Task, mission, or decision lifecycle state.
Graph node references, typed edge vocabulary, confidence, rationale metadata, and creator attribution.Transcript rendering, React Flow layout, or frontend graph interaction state.
Graph query orchestration: node lookup, neighbour hydration, breadth-limited expansion, and search.Full-text indexing or semantic embedding storage.
The graph_query MCP tool and graph RPC methods.Decision logging, task review, or mission progress.
Dangling-edge visibility and cleanup helpers for deleted entities.Deleting the source domain object that an edge points at.

Hard service boundary

The graph service is the only package that exposes graph operations to protocol layers. Context links are an internal graph repository concern, and graph query orchestration lives under the graph service boundary. The package shape is graph-first:

Service constructor

The application service has an explicit constructor. Required dependencies are constructor parameters, not mutable setters. Missing production dependencies fail at startup.

type Service struct {

    searchTimeout time.Duration

}

func NewService(
    links contextlink.Repository,
    clock domain.Clock,
    caller caller.Resolver,
    members MemberLoader,
    hydrators []domain.NodeHydrator,

links, clock, caller, members, hydrators, and logger are required. searchTimeout must be positive. Hydrator node types are normalized and must be unique. A nil hydrator is a startup error.

3. Architecture layers

Protocol adapters are thin. They decode transport payloads, stamp caller identity, and call the graph service. The graph service owns scope checks and graph semantics. Contextlink repositories only persist edge records; they do not hydrate nodes or interpret product actions.

Read flow

1
The adapter validates transport shape and maps the request into a typed graph command.
2
The graph service resolves caller identity from context.Context and verifies the caller can access the requested project and project scope.
3
The service loads the focal node through the hydrator for its node type. Missing or wrong-project nodes return an error.
4
The service loads all context links where the focal node is source or target, then groups neighbouring refs by node type.
5
Neighbour refs are hydrated through the same service ports. Missing hydrators and missing neighbour nodes become graph warnings with capped affected ids.

Mutation flow

1
The service validates source ref, target ref, edge type, confidence, rationale, project id, and caller identity before any write.
2
Both endpoints are hydrated in the requested project scope. A link cannot point to a node that the graph service cannot resolve.
3
The contextlink aggregate validates the edge record. The repository writes exactly the validated edge or returns a persistence error.
4
The service returns the persisted edge projection. Graph mutations do not publish notifications; callers already receive the result synchronously.

4. Domain model

A graph node is any durable work object addressable by type/id. A context link is a directed, typed edge between two graph nodes. The direction carries meaning even when the UI renders an edge as visually symmetric.

type NodeRef struct {
    Type NodeType
    ID   string
}

type ContextLink struct {
    ID         ContextLinkID
    Source     NodeRef
    Target     NodeRef
    EdgeType   EdgeType
    Confidence float64
    Metadata   map[string]string
    CreatedAt  time.Time
    CreatedBy  string
}

The graph domain owns the link record. Transport adapters project it into JSON DTOs. The graph service does not use pkg/types.ContextLink as its domain model.

ConceptFieldsRule
Node reftype, idType is one known graph node type; id is non-empty and resolves within the requested project scope.
Context linkid, source ref, target ref, edgeType, confidence, metadata, creator, timestampSource and target are different nodes. Edge type is one known enum. Confidence is between 0.0 and 1.0.
Graph node detailCore node fields, neighbours, edges, optional subgraph, warningsEvery returned edge is backed by a persisted context link. Missing neighbour nodes are reported as warnings, not fabricated nodes.
Graph warningcode, message, affected type, capped affected ids, countWarnings describe partial graph shape issues without hiding service errors.

Allowed edge types

blocked_by, resolved_by, completed_by, serves, informed_by, produced, made_during, spawned, child_of, and relates_to are the graph edge vocabulary. Unknown edge types fail at the boundary and in the contextlink aggregate.

Edge typeMeaningTypical direction
blocked_byThe source cannot progress until the target is resolved.Task to task.
resolved_byThe source was resolved by the target decision.Task or decision to decision.
completed_byThe source was completed by the target decision.Task to decision.
servesThe source contributes toward the target objective.Task to key result, decision to mission.
informed_byThe source used the target as supporting context.Decision to decision, task, key result, or mission.
producedThe source produced the target work object.Decision to task.
made_duringThe source was created during the target work context.Decision to task.
spawnedThe source created the target follow-up object.Decision to task.
child_ofThe source is a child of the target in a work hierarchy.Task to task.
relates_toThe source has a general durable relationship to the target.Any visible node to any visible node.

Generic relationships use relates_to only when none of the semantic edge types describe the relationship. Free-form edge names are not accepted.

5. Edge classes

The graph stores two classes of edges with the same durable contextlink aggregate: structural edges and context shortcut edges. Structural edges mirror durable source-domain structure. Context shortcut edges preserve useful working-memory jumps so agents do not need to rediscover the same multi-hop context on every turn.

ClassPurposeExamplesRule
Structural edgeRepresents the source-domain relationship or hierarchy.task --serves--> key_result, key_result --serves--> mission, task --child_of--> taskThe source service writes the edge when it creates or changes the underlying domain reference.
Context shortcut edgeCreates a direct recall path across a relationship that is semantically useful to agents.decision --made_during--> task, decision --informed_by--> mission, task --relates_to--> missionThe source service writes the edge when the shortcut captures durable context, with rationale metadata explaining why it exists.

Shortcut edges do not replace source-domain truth. They are explicit graph memory that optimizes recall. A mission can be connected to a decision because the decision was made while fixing a task under that mission, even when the structural path also exists through key result and task nodes.

Source services write both classes through narrow graph application ports. They do not write contextlink rows directly. The graph service validates endpoint visibility, edge vocabulary, confidence, and persistence uniqueness for every structural or shortcut edge.

6. Service integration

Source services use the graph service through narrow graph-owned ports. They do not import contextlink, they do not construct persisted link rows, and they do not call graph RPC or MCP adapters. The application composition root injects the process graph service as the implementation of these ports.

package graphapp

type Linker interface {
    Link(ctx context.Context, req domain.GraphLinkRequest) (domain.GraphEdge, []domain.GraphWarning, error)
}

type NodeLinkDeleter interface {
    DeleteLinksForNode(ctx context.Context, nodeType string, nodeID string) error
}

The source service owns the moment and intent of the relationship. The graph service owns validation, endpoint hydration, duplicate handling, operation reporting, and persistence. A task service can therefore write task --serves--> key_result when a task is assigned to a key result, while the graph service verifies that both endpoints resolve before storing the edge.

Source serviceStructural edgesContext shortcut edgesCleanup
Tasktask --serves--> key_result, task --child_of--> tasktask --relates_to--> mission when direct mission recall is useful.Deletes edges for the task node when the task is deleted.
Decisiondecision --made_during--> task, decision --produced--> taskdecision --informed_by--> mission or decision --serves--> key_result when the decision should appear directly around those nodes.Deletes edges for the decision node when the decision is deleted.
Mission / key resultkey_result --serves--> missionMission-level shortcut edges created from mission workflows when the relationship is durable agent context.Deletes edges for mission or key-result nodes when those records are deleted.

Graph write calls are synchronous. If endpoint hydration fails, the source service returns the error rather than silently skipping the edge. Link calls are idempotent for the same source, target, and edge type, so source services can retry safely and inspect operation to distinguish created, updated, and noop.

7. Query surface

The graph service exposes four product operations. Reads hydrate live node records through service ports so graph output reflects current titles, statuses, scopes, and timestamps. Edges remain durable even when a referenced node is deleted; reads surface those dangling edges as warnings until cleanup removes them.

type GraphQueryService interface {
    Node(ctx context.Context, req NodeRequest) (GraphNodeDetail, []GraphWarning, error)
    Search(ctx context.Context, req SearchRequest) ([]GraphNodeSummary, []GraphWarning, error)
    Link(ctx context.Context, req LinkRequest) (GraphEdge, []GraphWarning, error)
    Unlink(ctx context.Context, req UnlinkRequest) (GraphEdge, []GraphWarning, error)
}
OperationInputsBehavior
Nodeproject id, node type, node id, depthLoads one node, its persisted edges, hydrated neighbours, and optional breadth-limited subgraph.
Searchproject id, node type, query, limit, edge filtersSearches one hydrator or all hydrators, ranks by query relevance, and applies any-direction or direction-aware edge filters without reordering surviving hits.
Linkproject id, source ref, target ref, edge type, confidence, rationaleVerifies both endpoints through hydrators, then creates, updates, or no-ops the matching context link.
Unlinkproject id plus edge id, or project id plus source ref, target ref, and edge typeDeletes the exact persisted edge and returns the removed edge view with operation=deleted.

Search behavior

Search accepts a concrete node type or all. Concrete search calls one hydrator. all fans out across hydrators with a per-hydrator timeout, merges hits, scores exact title matches ahead of prefix and substring matches, then sorts by score, created time, type, and id. Concrete search uses the same final scoring step when a query is present, so a newer weak match does not outrank an older title match. A hydrator timeout produces a search_partial_timeout warning; a non-timeout hydrator error fails the request.

Search inputRule
queryRequired for node_type=all unless an edge filter is present. Optional for concrete node types, where an empty query browses that node type.
limitDefaults to 10 and caps at 50.
has_edgeFilters to nodes with at least one incoming or outgoing context link of the requested edge type.
missing_edgeFilters to nodes with no incoming or outgoing context link of the requested edge type.
outgoing_edgeFilters to nodes where the node is the source of at least one matching edge.
incoming_edgeFilters to nodes where the node is the target of at least one matching edge.
has_edge plus missing_edgeAllowed only when the edge types differ.

Search relevance

Match classScoreExample for query metrics
Exact title match1.0metrics
Title prefix match0.8metrics-server restore
Title substring match0.6Restore metrics-server and kubectl top
Hydrator-provided fallback hit0.4A node returned by the source service without the query in its title.

Score is the primary sort key. Created time, node type, and id are deterministic tie-breakers. Edge filters are applied after the search candidate set is built; they preserve the relevance order of surviving hits. has_edge and missing_edge are direction-agnostic by design. Agents use outgoing_edge or incoming_edge when source/target direction matters. Search hits that survive a positive edge filter include matchedEdges snippets so callers can see which relationship satisfied the filter without issuing a follow-up node expansion.

8. Caller identity and scope

The graph service consumes the shared internal/caller contract. RPC calls carry the authenticated user identity. MCP calls resolve the active member from the session and stamp both user and member identity into context before service calls.

CallerAllowed graph behaviorScope basis
Authenticated userRead and mutate graph links for projects the user owns.User owns the project.
Active project memberRead same-project graph context and create or remove links for visible nodes.Active member belongs to the project.

The service never infers project scope from a node id. Every public method requires ProjectID. Hydrators enforce project ownership by reading through source services and checking project or membership. A node id prefix can infer node type for convenience on node, link, and unlink calls, but it cannot infer project, project, user, or member authority.

9. Persistence

The contextlink repository stores only canonical edge records. It enforces uniqueness for source_type, source_id, target_type, target_id, and edge_type. It does not query source-domain tables and it does not hide duplicate or missing records.

ColumnPurpose
idPrimary key, generated by the graph service when absent from internal callers.
source_type, source_idDirected source endpoint index.
target_type, target_idDirected target endpoint index.
edge_typeSemantic relationship filter and uniqueness component.
confidenceConfidence weight constrained to 0.0 through 1.0.
metadata_jsonSmall graph-owned metadata such as rationale; not a general document store.
created_at, created_byAudit fields for graph provenance.

Replace semantics

Link is idempotent for the same source, target, and edge type. If no matching edge exists, the service creates one and returns operation=created. If the edge exists and confidence, rationale, origin, or creator changes, the service updates the row and returns operation=updated. If the edge exists with the same confidence, rationale, origin, and creator, the service returns operation=noop and does not write. Updates preserve the link id and creation timestamp.

10. Repository interfaces

The contextlink package owns repository interfaces and SQL implementations. Application services consume package-namespaced contracts or narrower consumer-owned ports; they never depend on SQL repository structs directly.

Domain contracts

The repository contract is composed from smaller interfaces so consumers can depend only on the operations they need. The package name carries the domain namespace; the type name carries the role. That keeps imports clear and avoids stutter such as contextlink.ContextLinkRepository.

Infrastructure implementation

internal/services/graph/contextlink contains the contextlink interfaces, SQL-backed repository implementations, and repository assertion tests. It is a repository package under graph. It does not define service methods, RPC handlers, MCP handlers, or caller authorization.

SQLite and Postgres implementations share the same assertion suite. The suite verifies insert, duplicate rejection, replace, source lookup, target lookup, between lookup, edge-type lookup, delete by id, delete by entity, metadata round-trip, timestamp round-trip, and transaction rollback on replace failure.

Replace and transactions

Replace is a repository operation because the uniqueness boundary belongs with persistence. It updates the one row identified by source, target, and edge type. If the row exists, Replace preserves id and creation audit unless the caller explicitly provides a new id for a create path. If the row does not exist, it inserts the supplied link. The operation is atomic.

Source-domain cleanup

Source services clean graph edges through the graph application's deletion port when they delete an entity that can appear in the graph. They pass an exact node type and id; the graph service deletes every row where the ref is either source or target. Cleanup is not a fallback for graph reads: reads still surface dangling edges as warnings when cleanup has not happened.

11. RPC adapter

The JSON-RPC graph adapter is a thin product API over the graph service. It is used by the web UI and any local client that needs graph queries without MCP. It stamps the authenticated caller before invoking the service.

RPC methodService callUse
graph.nodeNodeLoad a focused node for detail panels and graph inspection.
graph.searchSearchSearch nodes and find relationship gaps.
graph.linkLinkCreate or replace a relationship from UI workflows.
graph.unlinkUnlinkRemove a relationship from UI workflows.
graph.linksBySourceFindBySourceEfficient strategy-map edge loading for known source nodes.
graph.linksByTargetFindByTargetEfficient strategy-map edge loading for known target nodes.

RPC views use JSON field names consistent with frontend graph types: id, sourceType, sourceId, targetType, targetId, edgeType, confidence, rationale, createdAt, createdBy, origin, source, and manual. origin is the semantic source of the relationship: manual for graph-tool or UI edits, reference for relationships materialized from domain references, and system for service-owned maintenance edges. createdBy records the actor or service that wrote the row, such as graph_query, task_service, or decision_service. The adapter does not expose SQL errors.

12. MCP graph tool

graph_query is the agent-facing MCP tool for durable work-memory retrieval and graph mutation. The handler owns action names, schema, strict JSON decoding, member session resolution, caller stamping, service request mapping, and structured result formatting.

MCP actionService methodResult
nodeGraphService.NodeOne hydrated node detail with neighbours, edges, subgraph, and warnings.
searchGraphService.SearchA stable list of graph node summaries and warnings. Positive edge-filter hits include matchedEdges.
linkGraphService.LinkThe graph edge plus stable id, audit provenance, and operation: created, updated, or noop.
unlinkGraphService.UnlinkThe deleted graph edge plus operation=deleted. Callers may unlink by stable edge_id or by exact endpoint tuple.

The MCP session supplies GraphService, MemberDirectory, ProjectID, ProjectID, and ActorMemberID. The handler resolves the active member before calling the service. Missing graph service, member directory, project id, or actor member id returns an MCP error result.

The schema requires only action at the top level. Callers include only the fields used by the selected action. The handler rejects unknown JSON fields, fields that belong to a different action, and explicit null values before any service call. Required fields are validated after unmarshal. Empty strings are invalid for required fields; they are not resolved to defaults.

MCP result shape

Every successful MCP result includes text content for the agent transcript and structured content for the UI event projector. The structured payload includes action, projectId, one of node, nodes, or edge, and warnings. Edge payloads include the stable edge id, createdAt, createdBy, provenance origin, compatibility source, and manual so agents can distinguish manual graph edits from derived reference edges. Link results include edge.operation so agents can distinguish creates, updates, and no-ops. Unlink success returns edge.operation=deleted; unlink not-found remains an error result. Error results use MCP isError=true and contain the validation or service error message.

13. Production wiring

The application composition root constructs one graph service after the services it hydrates from are available. The same process-owned graph service is passed to RPC registration and MCP session registration.

contextLinks, err := graphcontextlink.NewRepository(handle)
graphSvc, err := graphapp.NewService(graphapp.Config{
    Links:         contextLinks,
    Caller:        caller.ContextResolver{},
    Members:       projectSvc,
    Hydrators:     graphapp.DefaultHydrators(taskSvc, decisionSvc, missionSvc),
    SearchTimeout: 2 * time.Second,
    Logger:        logger.With("service", "graph"),
})

The RPC registry binds graph methods through internal/rpc/graph.go. The MCP server registers internal/mcp/tools/graph in internal/mcp/toolset.go and dispatches it in executeNativeMCPTool. Managed harness startup includes the process graph service in every member MCP session so agents can call graph_query end to end.

Hydrator ports

Hydrators depend on narrow read ports owned by the graph service. They do not import repositories from source domains. Each hydrator returns a stable core shape: id, type, title, status, scope id, created timestamp, and fields.
