Architecture · Schedule Service

Schedule Service

The schedule service stores future work intents. Agents and operators use it to say what should happen later, when it should happen, and which service should receive the command when the time arrives. The first scheduled target is task creation.

1. Purpose

The schedule service is the durable memory for work that should happen in the future. It exists so agents can schedule their own follow-up work instead of polling, waiting inside a turn, or relying on a human to remember a delayed check.

The main product use case is scheduled task creation. A coordinator or worker can create a one-off or recurring schedule entry such as "check whether this long-running admission completed tomorrow morning" or "review this integration every weekday until the mission closes." When the entry becomes due, the schedule service invokes the task service to create a normal task assigned to the target member. From that point forward, the task service owns claim, active work, review, retry, block, unblock, cancel, messages, and completion.

This makes scheduling feel like task creation without turning the schedule service into a second task lifecycle engine. A schedule entry is a future command. A task is actual work. The schedule service stores and fires the future command; the task service manages the created work.

2. Service boundary

The schedule service owns scheduled intent CRUD and due-time execution. It does not own the lifecycle of whatever it creates. Each scheduled target has its own owning service, and the schedule service invokes that service through a typed target adapter when a run becomes due.

Owned by schedule serviceOwned elsewhere
Schedule entry identity, timing, target descriptor, status, run cursor, expiry, and run history.Task status, task review, task messages, task blockers, task completion, task failure, and task artifacts.
Validation that a scheduled target payload is complete enough to invoke later.Business rules for the target object after it is created or mutated.
Due-run detection and exactly-once run materialization per schedule window.Worker execution and coordinator review after the task exists.
Calendar/list/read models for scheduled intent and run history.Board/task read models for active work.

3. Architecture layers

The service follows the same layering discipline as task and mission. Protocol handlers translate payloads. The service authorizes and orchestrates. The domain owns schedule rules. Repositories persist. Target adapters call owning services.

Protocol handlers
Decode JSON-RPC and MCP tool calls into typed schedule commands. Action strings, schemas, cards, and DTOs live here.
Service
Authorize the caller, validate the schedule command, persist entries, compute due runs, invoke targets, and record run results.
Domain
Defines schedule entries, target descriptors, timing expressions, statuses, recurrence rules, guardrails, and state transitions. It has no repository or protocol imports.
Repository
Persists schedule entries, run rows, leases, due cursors, and query indexes. It does not call target services.
Target adapters
Invoke owning services with typed commands. The task target adapter calls task creation and lets the task service publish assignment messages.

5. Service commands

The schedule service exposes operations that describe schedule behavior, not task behavior. Creation and update operations persist future intent. The runner materializes due occurrences and hands them off to target adapters. The public surface stays explicit so protocol handlers, tools, and tests all drive the same service boundary. 

type Service struct {
    repository schedule.Repository
    targets    TargetRegistry
    clock      Clock
    caller     CallerResolver
    spaces     SpaceLoader
    members    MemberLoader
    guardrails GuardrailPolicy
    events     EventPublisher
}
CommandWhat it doesWhat it never does
CreateValidates caller, timing, target payload, context refs, dedupe key, and guardrails; stores a new schedule entry.Creates a task before the schedule is due.
Get / ListLoads schedule entries, recent runs, target summaries, and calendar metadata inside the caller's visible spaces.Reads task lifecycle state directly from task internals.
UpdateChanges future timing, future target payload, title, description, expiry, pause state, or context refs.Mutates runs that already fired or tasks already created.
CancelStops future runs.Cancels created tasks; that remains a task service operation.
RunDueFinds due entries and executes a bounded batch for the background runner.Runs unbounded work or hides per-entry errors.

Command inputs are action-specific. A caller that lists schedules supplies filters only. A caller that schedules a task supplies task creation payload and timing. Protocol schemas mirror this shape so callers omit unused fields instead of sending null placeholders.

Validation happens at the boundary: caller identity, space membership, timing, target payload, context references, and self-scheduling policy are checked before an entry becomes active.

6. Authorization model

Schedules live inside spaces because spaces define membership, assignment, and operational authority. The schedule service authorizes the schedule operation first, then the target adapter authorizes the target payload against the owning service's rules.

CallerCan createCan manageCan execute due run
Human operatorSchedules in spaces they can manage.Can update or cancel schedules in spaces they manage.Does not execute due runs directly.
Coordinator agentSchedules work for members in its space when policy allows.Can update or cancel schedules it owns or manages.Does not execute due runs directly.
Worker agentSchedules self-follow-up tasks and permitted member handoffs inside its space.Can update or cancel schedules it owns.Does not execute due runs directly.
System runnerCannot create arbitrary schedules.Cannot update user-created intent except by advancing due cursors and run state.Executes active due entries through the runner path using schedule actor metadata.

The runner invokes target services through their public service APIs and carries immutable origin metadata: scheduleEntryId, scheduleRunId, and createdBy. For task.create, the target adapter supplies the schedule creator member as the task caller so the task service still enforces its own coordinator and assignment rules.

Agent-created recurrence is within policy.Guardrail policy before activation.Agents can create future work without creating unbounded background load.
Runner can execute only active due entries.RunDue query, lease creation, and state transition checks.The system runner is not a general command executor.

7. What can be scheduled

A schedule entry has a target. The target answers two questions: what service receives the due-run command, and what payload is sent to that service. The schedule service is generic at this target boundary, while still validating each supported target type strictly.

Task creation The supported target. A due run calls the task service to create a task assigned to a space member. The resulting task is marked with task kind scheduled and includes a schedule reference in metadata.
Registered service command The extension point. Additional targets are added only when a service exposes a typed adapter with validation, authorization, and run-result mapping.

Scheduling context

A scheduled item can be attached to product context so agents and humans understand why it exists. Context is not the lifecycle owner; it is a reference used for filtering, authorization, display, and task creation metadata.

ContextPurposeExample
spaceIdRequired scope. Schedules live inside a space because agent membership, permissions, and task assignment are space-owned.Schedule the finance worker to re-check vendor data tomorrow.
targetMemberIdRequired for scheduled task creation. The task service receives this as the task assignee.Assign follow-up work to member-analyst.
missionIdOptional strategic context for filtering and generated task refs.Run a recurring adoption-risk check while a mission is active.
keyResultIdOptional measurable-outcome context.Check a KR source every Monday and create a task when progress needs review.
planPhaseId / planTodoIdOptional planning context for scheduled implementation follow-ups.Revisit a blocked plan todo after an external deployment window.
relatedTaskIdOptional task follow-up context. The schedule can create a future task about another task without taking over that task's lifecycle.Check whether a long-running admission task reached review.
createdByRecords whether the schedule was created by an agent, human, or system command.A worker schedules a one-off reminder for itself.

8. Target adapter registry

The target registry is the extension point that makes the service generic without accepting arbitrary commands. Every target kind is registered by name, owns a typed payload, validates that payload before activation, and invokes exactly one owning service when a run is due. 

type TargetAdapter interface {
    Kind() ScheduleTargetKind
    Validate(ctx context.Context, payload TargetPayload, scope ScheduleScope) error
    Describe(payload TargetPayload) TargetSummary
    Invoke(ctx context.Context, run TargetRun) (TargetResult, error)
}
Adapter responsibilityContract
Payload validationRejects missing fields, unsupported fields, invalid context refs, and cross-space assignments before an entry becomes active.
Display summaryProvides labels for calendar cards, schedule detail views, and audit logs without making the calendar understand target internals.
InvocationCalls the owning service through a public service method and returns the created or affected object id.

The registry is constructed in the production composition root. A schedule service without a registered adapter for task.create fails startup validation because an active entry must never become due with no executable target.

9. Domain model

Schedule records store future intent, not task state. A schedule entry says "create this later." A schedule run says "this due occurrence was attempted." The created task is read from the task service.

11. Timing model

Timing is stored as a normalized domain expression plus a UTC cursor. Calendar-like recurrence is evaluated in the entry timezone, while due-run scanning uses UTC timestamps. This keeps the runner simple and keeps human-facing recurrence understandable.

Timing modeFieldsCursor behaviorUse case
oncerunAt, optional timezone for display.nextRunAt is the single run timestamp. Successful execution makes the entry terminal.Check a long-running admission tomorrow morning.
intervalinterval, optional startsAt, optional endsAt, optional max runs.Each successful run advances from the previous due cursor by the interval.Re-check an external API every 30 minutes until cancelled.
cronexpression, required timezone, optional start/end bounds.The next cursor is computed from the previous due cursor in the entry timezone, then stored as UTC.Every weekday at 09:00 in the space timezone.

Timezone behavior

Recurrence is evaluated in the schedule timezone and stored as UTC cursors for runner scans. The implementation owns the exact edge-case behavior for daylight-saving transitions, but it must be deterministic and visible in run history when an occurrence is skipped.

CaseRule
No timezone supplied for cronCreation fails. Cron schedules require an explicit timezone.
Timezone changed on updateFuture cursors are recomputed from the update time. Historical run rows keep their original due timestamps.
Ambiguous or invalid local occurrenceThe runner records an explicit run outcome instead of silently shifting the schedule.

Catch-up and missed runs

When the app is offline or a runner is paused, due entries remain visible because nextRunAt stays in the past. The runner processes missed work explicitly rather than silently fast-forwarding.

ConditionBehavior
One-off entry is overdueThe next runner batch attempts the overdue occurrence once.
Recurring entry missed several intervalsThe runner processes a bounded number of catch-up occurrences per batch and records skipped overflow when policy caps are reached.
Entry expired before catch-upNo target is invoked after expiry. A skipped run records the expiry reason if a due cursor existed.
Target service rejects the due commandThe run is failed and the entry's retry policy decides whether the same due occurrence can be retried.

12. Agent guardrails

Agents can create future work for themselves, so schedule creation has product guardrails in addition to normal authorization. Guardrails do not hide errors. They either allow activation or reject invalid input.

GuardrailDefault behaviorWhy it exists
Allowed target kindsAgent-created schedules can target only registered kinds allowed by space policy; the first slice supports only task.create.Prevents agents from turning the scheduler into a generic privileged command runner.
Minimum intervalVery frequent recurring schedules are rejected by policy.Protects the task system and runner from runaway schedule creation.
Runner batch sizeDue scans process a bounded number of entries per run.Keeps catch-up work predictable.
Target assignee policyWorkers default to self-scheduling. Scheduling other members requires coordinator or human authority.Prevents accidental assignment loops and unauthorized delegation.
Expiry requirementRecurring agent-created schedules require expiry or max-run bounds unless policy explicitly allows open-ended schedules.Long-running monitors need an intentional end condition.
Dedupe keyRepeated schedule creation for the same actor, context, target, and timing can reuse or reject an existing active entry.Prevents duplicate follow-up tasks for the same future intent.

13. Scheduled task creation

Task creation is the first schedule target because the product already has robust task assignment, worker wake-up messages, review, retry, blockers, and board surfaces. The schedule service reuses that path instead of inventing a separate scheduled-work lifecycle.

1
An agent creates a schedule entry in a space. The target kind is task.create; the payload contains the future task title, description, acceptance criteria, target member, and optional mission/KR/plan refs.
2
The service validates timing, target payload, target member membership, caller permissions, dedupe key, and guardrails. It persists a schedule entry. No task exists yet.
3
When nextRunAt becomes due, the runner leases the occurrence and records a ScheduleRun row.
4
The task target adapter calls task.Service.Create with caller context stamped as a system schedule actor plus the originating creator metadata.
5
The task service persists the task and publishes the normal assignment message. The assigned member wakes up and handles the task through the existing task lifecycle.
6
The schedule service stores the created task id on the run row, advances the schedule cursor for recurring entries, or marks one-off entries triggered.

Created task shape

The created task is a normal task with schedule metadata. The task service owns the task record; the metadata only links it back to the schedule entry and run.

Task fieldValue
SpaceIDCopied from the schedule entry.
AssignedToCopied from the target payload's target member.
TaskKindscheduled.
Title, Description, AcceptanceCriteriaCopied from the target payload, optionally rendered with safe schedule context.
KeyResultRef, MissionRefCopied from schedule context when present.
Metadata.scheduleEntryIdThe durable schedule entry id.
Metadata.scheduleRunIdThe due occurrence that created this task.
Metadata.scheduleCreatedByThe original agent, human, or system actor that configured the entry.

The created task does not inherit schedule status. It starts in the task service's normal pending state. The assigned member claims it, completes it, blocks it, or releases it through task actions. The coordinator reviews it through the task review path.

Task adapter command mapping

The task.create adapter translates schedule intent into the same task service create command used by the UI and other backend callers. It does not write task rows directly and it does not publish assignment messages itself.

Schedule valueTask create valueValidation
entry.SpaceIDCreateTaskParams.SpaceIDSpace exists and caller can schedule inside it.
payload.TargetMemberIDCreateTaskParams.AssignedToMember exists in the same space and can receive tasks.
payload.TitleCreateTaskParams.TitleNon-empty after rendering; no schedule-only placeholders remain unresolved.
payload.DescriptionCreateTaskParams.DescriptionOptional but preserved exactly as future work instructions.
payload.AcceptanceCriteriaCreateTaskParams.AcceptanceCriteriaEach criterion is non-empty when supplied.
context.MissionID, context.KeyResultIDTask refs and metadataEach referenced object belongs to the same space.
run.ID and entry.IDTask metadataRequired for traceability and idempotency.

If task creation succeeds but run recording fails, the service returns an error and surfaces the inconsistency for repair. It does not create a second task to hide the recording failure. The run uniqueness key and task metadata give operators enough information to reconcile the created task with the schedule occurrence.

14. Scheduler runtime

The schedule service uses an app-owned scheduler runtime, not operating-system cron. Cron expressions are supported as one timing syntax, but the runtime that decides what is due, leases work, invokes targets, records runs, and advances cursors lives inside agen8.

ConceptUsed forOwned by
One-off timestampRun exactly once at a concrete time.Schedule timing parser and runner.
IntervalRun repeatedly after a duration such as 30m, 8h, or 24h.Schedule timing parser and runner.
Cron expressionDescribe calendar-like recurrence such as weekdays at 09:00.Schedule timing parser and runner.
OS cronNot used for product schedules.External environment only.

This keeps scheduled work visible and controllable inside the product. Agents can create schedules, users can see them in the calendar, operators can cancel them, and the system can audit each due run. OS cron cannot provide product-scoped authorization, calendar projection, target-specific validation, dedupe, run history, or task links.

1
The runner wakes on a short internal tick or process signal and asks the repository for active entries where nextRunAt <= now.
2
For each due entry, the runner creates or claims a lease keyed by entryId + dueAt. If another process already owns the lease, this runner skips that occurrence.
3
The runner writes a schedule_runs row before invoking the target. This gives the calendar an auditable record even when target execution fails.
4
The runner invokes the typed target adapter, such as task.create. The target adapter calls the owning service, not a repository shortcut.
5
The runner records success, failure, or skip reason on the run row. Successful task creation stores the created task id as targetObjectId.
6
The runner advances the schedule cursor by computing the next run from the stored timing expression. One-off entries become terminal after their due occurrence is recorded.

Why the runner is database-backed

RequirementRuntime behavior
Multiple daemon processes do not create duplicate tasks.Run leases are persisted with a unique entryId + dueAt key.
Missed time while the app is offline is visible.Due scan finds entries whose nextRunAt is in the past and records catch-up behavior explicitly.
Calendar shows future and past scheduled work.Entries provide future projections; run rows provide history.
Agent-created schedules can be governed.Guardrails are checked before entries become active.
Target failures are debuggable.Failed runs keep error details and do not disappear into process logs.

Cron syntax

Cron expressions are parsed only to compute nextRunAt. The expression is stored on the schedule entry, and each successful recurring run recomputes the next cursor from the current cursor and timezone policy. Cron syntax is therefore a recurrence language, not the scheduling engine.

15. Calendar view

The calendar is a human-facing read model over schedule entries and schedule runs. It makes scheduled work familiar by showing future due times, recurring patterns, run history, skipped runs, and created tasks in a calendar/agenda layout.

Calendar itemSourceNavigation
Future scheduled occurrenceScheduleEntry.nextRunAt plus recurrence preview.Opens schedule detail and edit/cancel controls.
Created scheduled taskScheduleRun.targetObjectID when target kind is task.create.Opens the created task.
Skipped runScheduleRun.status = skipped and reason.Opens run details and schedule entry.

The calendar does not create or mutate task lifecycle state. It calls schedule RPC for schedule entry operations and task/board routes for created tasks.

16. RPC and agent tool

RPC surface

RPC supports UI and human workflows. It exposes schedule CRUD and read models. Run history is returned with schedule.get; a dedicated history method is added only when pagination is needed.

RPC methodService callBoundary rule

17. Execution and publishing

The runner is a background application workflow. It scans due entries, leases each due run, invokes the target adapter, and records the outcome. It never silently skips failures.

StepBehaviorFailure handling
Due scanFind active entries with nextRunAt <= now.Repository errors fail the scan and are logged/returned.
LeaseCreate or claim a deterministic run row for the entry and due time.Existing lease prevents duplicate target invocation.
InvokeCall the target adapter with typed payload and caller context.Target errors mark the run failed and keep retry policy explicit.
RecordPersist target object id, timestamps, and status.Record failures are surfaced; the service does not pretend the run succeeded.
AdvanceCompute the next run for recurring entries or mark one-off entries triggered.Advance errors leave the entry visible for operator repair.

Task assignment messages

The schedule service does not publish worker assignment messages directly. For scheduled task creation, the task target adapter calls the task service. The task service persists the task and publishes the assignment message through the same path used by manually-created tasks. This keeps worker wake-up semantics in one place.

18. Repository contracts

The schedule domain owns one repository contract. The package name provides the namespace, so the interface is named Repository, composed from Reader and Writer. It exposes schedule persistence primitives only; it does not know how to create tasks, evaluate guardrails, or publish events. 

type Repository interface {
    Reader
    Writer
}

type Reader interface {
    Get(ctx context.Context, id EntryID) (Entry, error)
    List(ctx context.Context, filter Filter) ([]Entry, error)
    ListDue(ctx context.Context, now time.Time, limit int) ([]Entry, error)
    ListRuns(ctx context.Context, filter RunFilter) ([]Run, error)
}

type Writer interface {
    Create(ctx context.Context, entry Entry) error
    Update(ctx context.Context, entry Entry) error
    ClaimDue(ctx context.Context, run Run) (Run, bool, error)
    UpdateRun(ctx context.Context, run Run) error
}
Repository ruleReason
schedule_runs(entry_id, due_at) is unique.A single schedule occurrence can produce at most one canonical run row.
Run claiming returns an explicit claimed boolean.Concurrent runners can detect that another process already owns an occurrence without treating it as success.
Due scans return bounded batches.The runner remains predictable when many entries are overdue.
Run rows store target result ids as strings with target kind.The schedule service can link to target objects without importing target persistence schemas.
Queries are scoped by space_id.Calendar and tool reads cannot accidentally leak cross-space schedules.

20. Storage and indexes

The persistence model optimizes for due-run scans, calendar queries, and context filtering. The canonical entry stores the complete typed schedule command, while selected columns make common queries efficient.

21. Verification

The schedule service is verified through the public paths that production uses: RPC handlers, the agent tool, the background runner, repositories, event publishing, target adapters, and the calendar read model. Tests do not reach around the service to insert tasks or mutate schedule internals.

ScenarioExpected verification
Worker schedules a one-off self follow-up.RPC or tool create stores an active entry, the calendar shows it, and no task exists until the due run creates one through the task service.
Coordinator schedules a recurring mission monitor.The runner creates scheduled tasks on due runs and records task ids in run history.
Agent requests a 1-minute infinite recurrence.Guardrails reject the entry according to space policy.
Two runner processes see the same due entry.Only one lease wins for the entryId + dueAt occurrence, so only one task create command is invoked.
Task service rejects target creation.The schedule run is marked failed with the target error. The failure is visible in history and the entry retry policy remains explicit.
User cancels a schedule after it created tasks.Future runs stop. Existing tasks remain in the task service and must be handled through task actions.
