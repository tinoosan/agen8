Architecture · Space Service

Space Service

The space service owns space CRUD, lifecycle, and the member roster subdomain. A space is either open or closed. Members are registered inside spaces. Messages, runtime sessions, plans, missions, tasks, and decisions remain separate service boundaries. Tools compose services to perform actions.

1. What a space is

A space is a bounded coordination context inside a project. It holds a title, a status (open or closed), and timestamps. One project can have many spaces.

The space record is deliberately minimal. The member roster is a space subdomain with its own repository and service methods, but it is still owned under the space boundary. These things are not part of the space's own state:

  • Messages — owned by the message service. Messaging is a separate concern with its own persistence and delivery pipeline.
  • Runtime sessions — owned by the runtime service. Whether a coordinator is running is independent of whether the space is open.
  • Plans, missions, tasks, decisions — each owned by its respective service.

The space service stores and retrieves domain.SpaceRecord records, enforces the open/closed lifecycle, and owns the roster of members registered inside a space. Cross-domain composition happens at the MCP tool layer, where handlers receive services from the Application composition root and call multiple service use cases. The MCP space tool defines the agent-facing space(action=...) contract.

Service boundary principle. Space membership is part of the space boundary. The space service owns space CRUD, lifecycle transitions, and the member roster subdomain. An MCP handler that needs to list a space's members calls the space service and its membership use cases. The space service never imports or depends on message, MCP, task, or runtime packages.

2. Architecture layers

RPC Handler
Per-service rpc.Handler translates JSON-RPC requests into spaceapp.Service calls. Each service owns its own handler.
Concrete Service
*spaceapp.Service owns space CRUD, lifecycle transitions, member roster use cases, caller-scoped visibility, harness config validation, and service logging. Dependencies are explicit repositories, Clock, CallerResolver, ConfigValidator, and *slog.Logger.
Domain
Space aggregate wraps domain.SpaceRecord with named transition methods. Two transitions, both idempotent, both reversible.
Repository
Space-owned repository interfaces. SQLite and Postgres implementations sit behind the same contract, each with native SQL.

Concrete service

The service struct keeps the space record repository and member roster repository explicit. Harness/model/effort validation is an explicit dependency because the roster must reject member configs that cannot create a valid harness session. Logging is a service-level dependency so space and member lifecycle operations produce consistent structured records.

type Service struct {
    spaces  domain.Repository
    members member.Repository
    clock   domain.Clock
    caller  CallerResolver
    configs ConfigValidator
    logger  *slog.Logger
}

The application composition root constructs one *spaceapp.Service and passes it to the space RPC handler, MCP session wiring, and services that need a narrow member loader. The service is a concrete struct, not an interface. Consumer packages define narrow interfaces when they need a subset of its methods.

Member roster subdomain

A member is a space-scoped runtime identity. Users authenticate to agen8; members act inside a specific space as coordinators or workers. The roster stores the member id, owning user id when present, project id, space id, member type, lifecycle state, channel id, display label, and harness preferences. Task assignment, message routing, MCP caller identity, and harness prompt identity all use this roster.

Each repository implementation owns its own SQL. SQLite uses ? placeholders; Postgres uses $N. There is no shared rebind layer.

Wrapping domain.SpaceRecord for state changes

Same pattern as the task and mission services: the domain record is the durable shape and the aggregate is the safe handle for transitions. Service code never mutates domain.SpaceRecord lifecycle fields directly — every state change is a load-wrap-transition-unwrap-save round trip.

3. Lifecycle — open ↔ closed

A space is either open or closed. Both transitions are reversible; closing is not terminal. A closed space is retired from the active set but its history stays readable.

Transition table

MethodSource stateResultNotes
CloseOpenClosedIdempotent for already-closed
ReopenClosedOpenIdempotent for already-open

Empty source status normalises to open. Same-state transitions short-circuit so retry loops do not fail on a status the space already holds.

The transition code

Close and Reopen are thin wrappers around a shared transition core that validates against a validSpaceTransitions table — adding a third state means adding one table entry, not editing the methods.

func (a Space) Close(now time.Time) (Space, error) {
    return a.transition(domain.SpaceStatusClosed, now)
}

func (a Space) Reopen(now time.Time) (Space, error) {
    return a.transition(domain.SpaceStatusOpen, now)
}

func (a Space) transition(target string, now time.Time) (Space, error) {
    current := a.Status()
    if current == target {
        return a, nil
    }
    allowed, ok := validSpaceTransitions[current]
    if !ok {
        return Space{}, fmt.Errorf("space: no transitions defined for status %q", current)
    }
    if !allowed[target] {
        return Space{}, fmt.Errorf("space: cannot transition from %q to %q", current, target)
    }
    next := a.inner
    next.Status = target
    next.UpdatedAt = now.UTC()
    return Space{inner: next}, nil
}

4. Service surface

The service exposes space lifecycle methods and member roster methods. Space lifecycle methods read from or write to the space repository through the domain aggregate. Member roster methods read from or write to the member subdomain repository.

// internal/caller
type Caller struct {
    UserID   string
    MemberID member.ID
    SpaceID  domain.SpaceID
    Role     string
}

func ContextWithCaller(ctx context.Context, caller Caller) context.Context

type ContextResolver struct{}

func (ContextResolver) ResolveCaller(ctx context.Context) (Caller, error)

Adapters stamp authenticated caller identity into context.Context before invoking the service through the shared internal/caller contract. RPC stamps the authenticated user id. MCP resolves the active actor member first, then stamps the member id, user id, and current space id. The space service and task service consume the same resolver, so service orchestration does not lose caller identity across package boundaries.

The logger is owned at service construction time and scoped with service=space. Space lifecycle and member roster writes log the operation, space id, project id, member id when present, caller user id, caller member id, and resulting lifecycle/status. Read methods do not produce success logs; failed reads and rejected writes return errors and may be logged at the adapter boundary.

No cross-domain repository access. The space service owns its member repository because membership is a space subdomain. It does not import message, task, MCP, or runtime packages, and it does not write another service's repository. Tools that need to combine space/member data with message or task data call multiple services through the Application composition root.

5. Per-service RPC handler

Each service owns its own rpc/handler.go. The handler struct takes the concrete service pointer and translates between the JSON-RPC wire format and typed Go method calls. The top-level RPCServer becomes a thin router that dispatches to per-service handlers.

// internal/services/space/rpc/handler.go
package rpc

type Handler struct {
    svc *spaceapp.Service
}

func NewHandler(svc *spaceapp.Service) *Handler {
    return &Handler{svc: svc}
}

The handler owns protocol translation: unmarshalling request params, calling the service, marshalling the response. Business logic stays in the service; wire format stays in the handler.

Each handler depends on exactly one concrete service. The RPC server owns protocol dispatch; the service owns business behavior.

Composition root wiring

The Application struct is a pure composition root — only fields, only NewApplication. It holds all service pointers. Both RPCServer and MCPServer depend on it.

// Application (composition root) — simplified
type Application struct {
    SpaceSvc   *spaceapp.Service
    MessageSvc *messageapp.Service
    // ... other services
}

// RPC registration creates service-owned handlers from Application.
// The space handler owns both space.* and space.member.* RPC methods.
spacerpc.NewHandler(app.SpaceSvc)
messagerpc.NewHandler(app.MessageSvc)
