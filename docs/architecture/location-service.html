Location Service

The location service records where project roots live and provides bounded filesystem discovery for those roots. It does not start, resume, or supervise AI harness sessions.

1. Service boundary

A location is a durable reference to a place that can contain project files. The baseline always includes the local location so a new local daemon can register a project from the current machine. SSH locations represent project roots on other machines. Their purpose is root discovery and access validation, not harness orchestration.

2. Domain shape

The current service shape is intentionally small. A location can be local, SSH, or managed in the domain. The release baseline supports local and SSH locations for project-root browsing. Managed locations remain a reserved domain kind until there is a concrete backend that fits the same root-addressability model.

3. Project root flow

The browser or MCP caller selects a location and root. Project creation stores the association after the location service confirms the root can be addressed. Project registration from an MCP client can also create or reuse a project from the caller's working directory, which maps to the local location by default.

4. Filesystem contract

Filesystem calls are location-scoped. Clients send a location id plus a path or a project-scoped virtual path. Local locations read through the daemon filesystem. SSH locations read through the SSH/SFTP transport using the referenced credential. The service normalizes paths and returns structured entries, not shell output. File previews are owned by the file service; location only answers discovery and addressability questions.

Local path inputs are validated before every filesystem operation. Path strings must be absolute after normalization, must not contain null bytes, and may use ~ to resolve to the daemon home directory only. Relative inputs and traversal-looking segments (such as ..) are rejected so local operations remain bounded and predictable.

Local mutating operations also execute through rooted filesystem handles instead of re-opening raw string paths after validation. Directory creation, writes, copies, and moves create destination parents inside the resolved root; local moves are rejected when source and destination resolve to different filesystem roots. This keeps validation and execution attached to the same path boundary.

5. Credential boundary

Locations reference credentials by id. Credential values live in the credential service and are resolved only by trusted backend callers. Location records never store raw private keys, passwords, tokens, or command output that could contain secrets. The browser can create SSH password or private-key credentials while adding an SSH location, but the created location still stores only the credential id.

6. RPC surface

The RPC adapter translates browser requests into typed location service calls. The Locations page uses the RPC surface to list locations, create SSH locations, probe readiness, delete unused locations, and browse directories during project creation. MCP project registration can use the local project root directly; it does not need to call location RPC first when the harness already knows its working directory.
