Architecture · Location Service

Location Service

The location service owns execution-capable work locations. A project stores a locationId and root path, but the location service owns reachability, filesystem browsing, readiness probes, and remote setup state.

1. Service boundary

A location is a reachable work boundary that can host harness sessions. It can be this machine, a user-owned machine reached by SSH, or an agen8-managed execution worker. Storage-only endpoints are not project locations because members cannot execute there. The service does not own projects, projects, tasks, or messages. It answers whether a location is known, whether it is reachable, whether it can run harness sessions, and how clients can browse roots inside it.

Location owns
Reachability
Location identity, kind, label, online status, connection metadata, and readiness probe results.
Location filesystem owns
Browsing and stat
Directory listing, path normalization, write/read checks, and location-scoped path validation.
Project owns
Project association
Project records store locationId and root. They do not browse or probe the location directly.
Harness owns
Execution sessions
Harness startup, Codex availability, member process lifecycle, and runtime execution stay behind the harness boundary.

2. Domain shape

The first version always exposes a default local location so a local daemon can create a project without manual configuration. The local record keeps the daemon host name in address.host, which lets clients show the actual execution machine while keeping the user-facing label as This machine. Remote locations use the same record shape, but readiness is discovered by probe rather than assumed from the kind.

3. Capabilities

Locations are intentionally narrower than generic storage. Every selectable project location must be able to browse files and execute managed harness work. A probe can report that a configured location is not ready, but that location does not become valid for project creation until ready is true.

4. Project creation flow

The browser asks the location service for known locations, browses a root through the selected location, and then calls project.create with locationId and root. When the only ready location is the default local location, the UI selects it automatically and starts at root selection. Project creation does not perform filesystem access itself.

5. Remote execution flow

A project does not run code. A location can run code. The daemon deployment mode describes where the control plane runs; the location kind describes where project work and harness execution run.

The project record never stores SSH hosts, credentials, tunnels, probe state, or process handles. The harness service loads member and project context, stores the project's locationId and root on the harness session, asks the location service for the location-scoped bridge endpoint when the location is not local, and lets the selected harness adapter decide how to create or resume its protocol thread inside the project root.

Command execution is location-scoped. For local, the transport starts an OS process with the harness adapter's command, args, environment, and working directory. For ssh, the transport dials the configured SSH target, changes to the remote project root when a raw command is the correct protocol, exports the runtime environment, and execs the adapter command remotely. A command request requires a ready location and a non-empty command; it fails instead of running in the daemon checkout when the location or root cannot be resolved.

Long-lived harness protocols use a bridge rather than per-turn command launches. The SSH environment manager detects the remote OS and architecture, builds or reuses a cached local agen8-bridge binary for that target, uploads it to a content-addressed path under ~/.agen8/bin, reuses a recorded bridge process only when its stored binary identity matches the uploaded binary, replaces stale bridge processes on remote loopback, verifies readiness and diagnostics, opens a daemon-side loopback tunnel to the bridge, and opens a reverse SSH tunnel from remote loopback back to the local daemon MCP endpoint. The bridge owns runtime backend processes on the SSH machine. The selected runtime adapter still owns the protocol: Codex sends the remote project root as cwd in app-server thread calls, while Claude Code starts in the remote project root and receives command metadata as a first WebSocket message, not as HTTP handshake headers.

Codex app-server sessions stay open across completed turns while their process-level configuration stays the same. Agen8 calls initialize, sends the required initialized notification, calls thread/start for a new managed member, persists the returned Codex thread id, and then sends each follow-up user message as another turn/start on the same live app-server connection. When member runtime config changes, Agen8 invalidates the live app-server client immediately while preserving the thread id. Agen8 calls thread/resume when it reconnects to an existing persisted Codex thread after the live app-server connection is gone or after model, reasoning effort, permission, command, or MCP process config changes. A successful turn/start response supplies the active turn id; terminal events for any other turn are ignored instead of completing the current message.

Managed Codex sessions run with the selected model, reasoning effort, and permission mode as Codex config overrides. The app-server process starts with the selected model, model_reasoning_effort, and permission config; thread start/resume also carries those values in the app-server config payload so a resumed native thread sees the current member runtime settings. Each turn carries the selected model, effort, and permission protocol fields. Full-access turns use the Codex native full-access sandbox preset: approvalPolicy="never" plus sandbox="danger-full-access" for thread start/resume and sandboxPolicy.type="dangerFullAccess" for turn start. For SSH locations, the daemon sends model, effort, and permission config in bridge headers, the bridge includes those values in the backend cache key, and the remote app-server process is replaced when they change. Codex HTTP MCP configuration is passed as a Codex config override for the location-scoped MCP URL.

The bridge diagnostics endpoint reports the bridge version, recorded binary identity, resolved Codex path/version, and resolved Claude Code path/version or setup error. The bridge proxies Codex app-server WebSocket frames with the same multi-megabyte read limit as the harness client so large thread/resume payloads are forwarded intact. When a Claude Code request names claude, the bridge resolves common user install paths and login-shell paths before PATH. If Claude Code is missing and npm is available, the bridge installs @anthropic-ai/claude-code under $HOME/.local and resolves the executable again. Authentication remains an explicit runtime readiness concern: the bridge can install and start harness CLIs, but account login state belongs to the user account on the selected location and is verified with each CLI's auth commands.

CLI setup is a location workflow for both local and SSH locations. location.installCodex and location.installClaude install missing CLIs with the selected location's package manager path and then reprobe. location.codexAuthStatus runs codex login status; location.codexLogin starts codex login --device-auth and returns the device-login URL and sanitized output. location.claudeLogin starts claude auth login --claudeai, keeps its stdin connected to a location-scoped input file under ~/.agen8/claude-login, and returns the OAuth URL and sanitized log output. If Claude's browser flow shows an authorization code, location.claudeLoginComplete appends that one-time code to the waiting login process and returns the refreshed login log. Agen8 never persists the code or writes it into the login log.

6. Repository

The repository persists location records and probe state. It does not persist secrets directly and it does not open network connections. Connection credentials live behind credential infrastructure; transports use the location record plus credential reference when the app service asks them to probe, browse, or execute.

7. Credential boundary

Location records contain enough non-secret connection metadata to identify a target, plus an opaque credentialRef. The credential service owns secret material and credential lifecycle. Location probes and transports ask the credential service to resolve usable authentication material at runtime, then redact that material from logs, probe errors, RPC results, and harness session records.

Location stores
Reference and public metadata
Location id, kind, label, host/port/user metadata, status, probe results, and opaque credential reference.
Credential service stores
Secret material
Private keys, passphrases, passwords, managed worker tokens, refresh material, rotation metadata, and external secret-manager references.
Transport consumes
Resolved auth
SSH and managed adapters receive short-lived resolved credentials for probe, browse, and execution. They do not write them back to project or harness records.
SSH auth modeHow it worksDefault stance
sshAgentUses the daemon user's existing SSH agent. The credential ref points to the agent-backed identity policy, not to private key bytes.Preferred first slice for local desktop installs.
keyRefUses a private key managed by credential infrastructure or an external secret manager. The location stores only the credential ref.Valid for SSH and managed execution.

  "kind": "ssh",

The create flow validates public connection fields, stores a location record with a credential reference, and then runs location.probe. Probe resolves credentials, dials the target, checks readiness, and persists sanitized state.

Logs can include location id, kind, label, host, port, auth mode, credential id, and sanitized failure category. Logs never include private keys, passwords, passphrases, tokens, raw credential payloads, or command strings that embed secrets.

9. Client contract

Clients render known locations with explicit readiness states. A known location can be offline or not ready; it remains visible on the Locations page so users can repair it, but it is not selectable for project creation until its probe reports ready=true.

Ready
ready=true
The UI can browse roots and create projects against this location.
Known but blocked
Offline or not ready
The UI shows a concrete state: offline, auth failed, root missing, permission denied, Codex missing, or execution missing.
Repair path
location.probe
Users can re-run probes after installing dependencies, fixing credentials, or reconnecting a remote worker.

Project creation keeps backend validation inside the service layer. The browser browses with location.fs.listDir and submits project.create; the project service loads the selected location, requires online and ready=true, and asks the location service to validate that the root is accessible before storing the project.

The first-run project form does not force users to choose a location when the only usable option is local. It uses the ready local location by default, shows a location picker when multiple ready locations exist, and links to the Locations page when no location is ready.

Location credentials, SSH keys, managed worker tokens, and injected runtime secrets do not live on project records. They belong to location/credential infrastructure. Project records contain only projectId, locationId, root, title, status, and timestamps.
