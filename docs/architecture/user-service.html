Architecture · User Service

User Service

The user service owns account identity, first-run setup, and account lifecycle. Auth owns sessions, API keys, password credential checks, and bearer-token validation. A user can sign in to agen8; a space member participates inside a space. Those are different records with different lifecycles.

1. Architecture layers

The service is the account boundary. The daemon and RPC layer authenticate transport requests and call the user service for account state; they do not manufacture users or lifecycle state themselves. Auth owns credential validation and session/API-key records.

Protocol handler
Translate setup and account RPC payloads into typed user service calls. Browser storage names, bearer tokens, and HTTP details live in daemon/RPC/auth, not in the user domain.
Service (orchestration)
Create the first user, update account profile, rotate account lifecycle state, and call the repository. Account rules live here.
Domain (account model)
user.User, user.ID, and user.Role define account identity. The domain does not know spaces, members, projects, sessions, API keys, daemon routes, or React local storage.
Repository
Persist users only. It does not decide who can register, validate passwords, store sessions, or store API keys.

2. The user domain

user.User is the canonical account record. user.ID is the only typed user identifier. User ids are account ids; they are never member ids, project ids, or runtime ids.

type ID struct {
    value string
}

type Role string

const (
    RoleAdmin Role = "admin"
    RoleUser  Role = "user"
)

type User struct {
    ID           ID
    Email        string
    Name         string
    Role         Role
    Lifecycle    Lifecycle
    CreatedAt    time.Time
    UpdatedAt    time.Time
}

Lifecycle state belongs on the account record so the service can disable or close an account without deleting durable ownership history.

LifecycleCan sign in?Meaning
activeyesThe account can authenticate and use agen8.
suspendednoThe account exists, but authentication is blocked by an admin decision.
closednoThe account no longer signs in, but historical ownership remains readable.

The domain validates account data before persistence. Email is normalized to lowercase. Password hashing happens in auth because it is credential behavior. The user domain rejects missing email, missing name, invalid role, invalid lifecycle state, and missing timestamps.

type NewInput struct {

    Name         string
    Role         Role
    Now          time.Time
}

The service struct

The constructor names the account boundary explicitly. Credential state is not injected into the user service; auth handles sessions, API keys, and password checks.

3. Identity boundaries

A user is an account. A project is the first durable workspace object the user creates after setup. A space is created inside a project. A member is an actor inside a space. Setup creates only the account and browser session.

4. First-user setup

First-run setup is the only open registration path. It is available only while the user repository is empty. It creates the first user as the account owner/admin. Auth creates the browser session for that new user. Setup does not create a project, space, member, API key, or agent.

type SetupFirstUserParams struct {
    Email        string
    Name         string
}

type SetupFirstUserResult struct {
    User    user.User
}

func (s *Service) SetupFirstUser(ctx context.Context, params SetupFirstUserParams) (SetupFirstUserResult, error)

Anatomy of first-user setup

1
Daemon validates the setup token and decodes the setup form. The token is a daemon concern; it is not passed into the user domain.
2
User service checks the user repository count. If any user exists, setup fails with registration closed.
3
Auth validates password policy before user creation. The password hash is stored only in auth credential persistence.
4
User service normalizes email, validates account fields, creates user.User with role admin, and persists it.
5
Auth creates a browser session for the new user and returns the session token to the daemon response.

Account role adminA member or coordinator role

5. Auth boundary

Auth owns credentials and bearer-token validation. The user service owns the account records those credentials point to. This keeps user lifecycle simple and keeps credential behavior in one place.

ConcernOwnerWhy
Account identity and lifecycleUser serviceUser records are durable product entities.
Password policy and password hashesAuth servicePasswords are credentials, not profile data.
Browser sessionsAuth serviceSessions are bearer credentials.
API keysAuth serviceAPI keys are programmatic bearer credentials.
Bearer-token validationAuth serviceThe daemon asks auth to turn a credential into a user identity.

6. RPC adapter

The RPC adapter exposes account-level methods. It does not create projects, spaces, or members. It maps authenticated daemon identity into response DTOs and maps login/setup payloads into user service commands.

RPC methodService callBoundary rule
user.statusService.CurrentUser or validated identity projectionReturns authenticated account profile and setup state.
user.getService.GetReturns the current account profile.
user.updateProfileService.UpdateProfileUpdates account name and email after validation.
user.suspendService.SuspendUserAdmin-only account lifecycle transition.
user.closeService.CloseUserAdmin/self-service account closure path.

The daemon setup route coordinates auth and user service because setup is not normal authenticated RPC. All normal account actions go through RPC with daemon-stamped identity. Login, logout, session status, password changes, and API-key methods live on auth RPC, not user RPC.

7. Persistence

The user repository stores account records and supports uniqueness checks. Auth stores session and API-key records in its own persistence layer.

8. Repository builder

The application composition root does not choose concrete user repository types directly. It asks the user infra package to build the repository from the configured storage handle. SQLite/Postgres selection stays inside the user service infrastructure boundary.

// internal/services/user/infra/repository_builder.go
func NewRepository(handle *storagedb.Handle) (user.Repository, error) {
    switch handle.Dialect() {
    case storagedb.DialectSQLite:
        return NewSQLiteRepository(handle)
    case storagedb.DialectPostgres:
        return NewPostgresRepository(handle)
    default:
        return nil, fmt.Errorf("unsupported user repository dialect %q", handle.Dialect())
    }
}

internal/app.NewApplication calls only userinfra.NewRepository(handle). It never imports or selects NewSQLiteRepository or NewPostgresRepository directly.

9. Code layout

internal/services/user/
  domain/
    user.go             # User, ID, Role, Lifecycle
    new.go              # validated New constructor
    repository.go       # Reader / Writer / Repository
    clock.go            # Clock interface and system clock
    errors.go           # typed user-domain errors

  app/
    service.go          # setup account creation, profile, lifecycle
    service_test.go     # service behavior with repository spies

  infra/
    repository_builder.go # storage strategy selection from configured handle
    sqlite_repository.go    # SQLite implementation
    postgres_repository.go  # PostgreSQL implementation
    repository_assertions_test.go

  rpc/
    handler.go          # user.status/get/updateProfile/suspend/close adapter
    types.go            # RPC params/results/views

internal/daemon owns the setup HTTP page and calls the user service first-run setup method. Normal account RPC lives under internal/services/user/rpc. The user service does not live under pkg, and no application method wraps it.

10. Logging

The service receives a service-scoped logger from the application composition root. It logs account lifecycle events without logging credential data.
