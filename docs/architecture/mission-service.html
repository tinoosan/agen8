Architecture - Mission Service

Mission Service

Missions describe strategic objectives. Key results describe measurable outcomes. The mission service owns mission lifecycle, key-result lifecycle, progress rules, persistence, and mission event publication.

1. Service boundary

The mission service is an application service. It is called by protocol adapters and other services through typed methods. It does not parse tool actions, build transcript cards, own MCP schemas, or talk to another service's repository.

2. Domain records

The public records are deliberately small. They hold durable mission facts, not tool state, UI projections, notification delivery state, or activity timelines.

3. KR subdomain

Key results are a mission-owned subdomain. They are not a separate service, because a KR cannot exist outside a mission and mission activation/completion depends on KR state. They are also not just fields on Mission, because measurement, progress, assignment, milestones, and completion checks have their own rules.

Repository infrastructure follows the task service pattern. The application composition root opens the database from config once, then passes the resolved *storagedb.Handle into the mission repository builder. Mission repositories do not receive host config and do not choose storage from config directly. 

func NewRepositories(handle *storagedb.Handle) (RepositorySet, error) {
    switch handle.Driver() {
    case storagedb.DriverSQLite:
        repo := NewSQLiteRepository(handle)
        return RepositorySet{Missions: repo, KeyResults: repo, ProgressEntries: repo, LifecycleEvents: repo}, nil
    case storagedb.DriverPostgres:
        repo := NewPostgresRepository(handle)
        return RepositorySet{Missions: repo, KeyResults: repo, ProgressEntries: repo, LifecycleEvents: repo}, nil
    default:
        return RepositorySet{}, fmt.Errorf("mission repositories: unsupported storage driver %q", handle.Driver())
    }
}

6. Mission lifecycle

A mission moves through named transitions. Archived is terminal. Completed is not terminal because adding or reopening scope can reactivate the mission.

TransitionAllowed fromResultEvent type
ActivateDraft, Paused, CompletedActive; clears pause/completion timestamps as needed.mission.activated
PauseActivePaused; stamps PausedAt.mission.paused
CompleteActiveCompleted; stamps CompletedAt.mission.completed
ArchiveDraft, Active, Paused, CompletedArchived.mission.archived

UpdateMission(Status=...) is the service command boundary for lifecycle requests. active runs the activation gate. completed runs the completion gate. paused is allowed from active without KR checks. archived archives any non-archived mission. Repeating the current status returns the current mission without publishing a duplicate lifecycle event. draft is not a valid update target; draft exists only at creation.

7. Key results and progress

Key results are the mission's measurable work units. A KR belongs to one mission and can be owned by one space. Progress updates produce append-only history and fired events.

Measurement model

Measurement type defines how raw KR values become progress. Direction is not a free-standing concept; it is required, forbidden, or constrained by the measurement type. 

type MeasurementType string

const (
    MeasurementNumber     MeasurementType = "number"
    MeasurementPercentage MeasurementType = "percentage"
    MeasurementBoolean    MeasurementType = "boolean"
)

type MeasurementDirection string

const (
    DirectionIncrease MeasurementDirection = "increase"
    DirectionDecrease MeasurementDirection = "decrease"
)
Measurement typeDirection ruleProgress rule
numberRequires increase or decrease.Uses baseline, target, current value, and direction to compute 0..100.
percentageDirection is constrained to increase for now.Current value is already a percent and is clamped to 0..100.
booleanDirection is forbidden.false is 0; true is 100.

Maintain/range measurements are intentionally out of scope until tolerance fields are designed. They should become a separate measurement type, not a third direction, because they need acceptable bounds rather than a simple better-higher or better-lower rule.

Progress math

Numeric KRs use 0 as the baseline when Baseline is unset. For direction=increase, progress is (current - baseline) / (target - baseline). For direction=decrease, progress is (baseline - current) / (baseline - target). The result is clamped to 0..100.

Percentage KRs treat the submitted value as the percentage and clamp it to 0..100. Boolean KRs use numeric values at the service boundary: 0 means false and any value greater than or equal to 1 means true.

A progress update moves a draft or open KR to in_progress when computed progress is below 100, and to completed when computed progress is 100. ExpectedVersion=0 skips the version check; any non-zero expected version must match the KR version. completed and dropped KRs reject progress updates.

Mission progress is the unweighted average of all non-dropped KR progress percentages, rounded to the nearest integer. Dropped KRs are excluded. A mission with no non-dropped KRs reports 0 progress and 0 counted KRs. The progress read model also includes counts by KR status and a blocking list of non-dropped KRs whose status is not completed, so callers can distinguish a numeric percentage from lifecycle closability. KR weights are not part of the model; adding weights would add user burden unless the product can abstract that complexity.

Mission activation gate

A mission can activate only when it has measurable scope and each live KR has an accountable owner. The activation predicate is: 

count(nonDroppedKRs) > 0 && every(nonDroppedKRs, ownerSpaceID != "" && ownerSpaceStatus == "open")

These mission states do not activate: no KRs, all KRs dropped, or any non-dropped KR without an owning space. If there is no active measurable scope, the coordinator should add KRs. If a live KR has no owner, the coordinator should assign it to a space before activation.

Owner space availability

A KR owner space is both a durable assignment and a live execution dependency. The historical SpaceID stays on the KR, but activation depends on that space still being open.

Assigning a KR to an open space moves the KR from draft to open. Reassignment is allowed only while the KR is draft or open. Once progress starts and the KR becomes in_progress, ownership is locked to preserve accountability. completed and dropped KRs cannot be reassigned through this command.

Owner space changeMission resultReason
A KR is assigned to an open space.Eligible for activation.The live KR has an accountable delivery owner.
A KR's assigned space is closed or archived before activation.Not eligible for activation.The assignment remains historical, but the space cannot own live work.
An active mission has a live KR whose owner space closes or archives.PausedThe mission has live scope without live execution capacity.
A completed mission has a completed KR whose owner space closes or archives.CompletedThe measurable outcome is already satisfied.
The KR is reassigned to an open space.Eligible for activation again.Live ownership has been restored.

Mission completion gate

A mission can complete only when its measurable scope has actually been satisfied. The completion predicate is: 

count(nonDroppedKRs) > 0 && every(nonDroppedKRs, status == "completed")

These mission states do not complete: no KRs, all KRs dropped, or only draft/open/in-progress KRs. If there is no active measurable scope, the coordinator should add KRs, pause the mission, or archive it instead of completing it.

Dropping KRs recomputes mission state

Dropping a KR changes the mission's measurable scope. The service must recompute the parent mission from the remaining non-dropped KRs instead of leaving the old mission status untouched.

After the dropMission resultMeaning
Zero non-dropped KRs remain.PausedThe mission still exists, but has no measurable scope to execute.
At least one non-dropped KR remains and all remaining KRs are completed.CompletedThe remaining measurable scope is satisfied.
At least one non-dropped KR remains and any remaining KR is draft/open/in-progress.ActiveThe mission has live measurable work.

Renewed scope reactivates completed missions

A completed mission reactivates only when new live measurable work is introduced. Completion is not invalidated by cosmetic edits or administrative changes.

Change to a completed missionMission resultReason
Add a new non-dropped KR.ActiveThe mission has renewed measurable scope.
Reopen a completed or dropped KR.ActivePreviously satisfied or removed scope now has live work again.
Add or keep a dropped/archived KR.CompletedDropped scope is ignored by active mission progress rules until it is explicitly reopened.
Edit title, description, note, metadata, or display fields on a completed KR.CompletedNo new measurable work was introduced.
Assign or change owner space on an already-completed KR.CompletedOwnership changed, but the measurable outcome is still satisfied.

Progress update atomicity

UpdateProgress is all-or-nothing. The service validates the caller, loads the KR and parent mission, computes the next progress state, and runs every completion gate before it writes a progress entry, KR state, mission state, or event. If a completion gate fails, the call returns an error and no progress row, KR value, KR status, mission status, or event is written.

Progress can be recorded only after the parent mission is active. Draft missions are still being shaped; progress on a draft mission creates execution evidence before the mission has passed its ownership and activation gate.

Milestone jumps

A progress update can cross multiple milestone thresholds at once. The service fires one milestone event for every newly crossed milestone and never re-fires a milestone that was already recorded in LastMilestoneNotified.

A normal kr.progress_updated event is still fired for the value change. Milestone events are additional facts emitted after the progress write for thresholds crossed by that update.

Progress regression

Progress can move down only while the KR is not completed and the measurement type allows regression. Completed KRs are stable: if the outcome is no longer true, the KR must be explicitly reopened before progress can regress.

Linked task completion gate

A KR can complete only when every linked task is terminal. The mission service resolves linked task ids through LinkedTaskLoader and checks task state through TaskLoader. It does not query task repositories, context-link repositories, or graph storage directly.

succeededTerminal; does not block KR completion.
failedTerminal; does not block KR completion.
canceledTerminal; does not block KR completion.
pending, active, blocked, in_reviewNon-terminal; blocks KR completion.

Concurrent progress updates

Progress updates use optimistic concurrency. A KR update includes the version or updated timestamp the caller read. If the stored KR changed before the write, the service rejects the update with a conflict and the caller must reload before trying again.

8. Fired events

Mission events are facts emitted after a successful state change. They are not agent instructions. Lifecycle event facts are also stored in mission-owned history so lifecycle notes remain readable after the action response is gone. Subscribers may translate fired facts into messages, heartbeat changes, dashboards, or operator workflows.

Event failure semantics

Mission/KR state changes and their fired events are one use case. If the lifecycle history write or event publication fails, the operation returns an error. There is no silent event loss for mission lifecycle or KR progress transitions.

Event consumers own delivery workflows. Mission activation briefings, heartbeat pause/resume changes, coordinator wakeups, and operator notifications are event-subscriber behavior, not methods on the mission service.

Mission events are published only after the state change is persisted. If mission persistence fails, no event is emitted. If event publication fails after persistence, the service returns that error so the caller sees that the transition side effect did not complete.

Notification idempotency

Mission activation can be retried, recomputed after KR assignment, or replayed by an event subscriber. Activation messages must therefore be idempotent per mission, assigned space, and event kind.

The mission service still publishes events only. The event subscriber that creates agent messages must use deterministic producer intent/correlation ids so message persistence can reject or ignore duplicates.

10. RPC adapter

RPC is the UI surface. DTOs live with the mission service under internal/services/mission/rpc. Shared JSON-RPC routing lives under internal/rpc. The handler validates DTO fields, stamps caller identity into context, calls a typed service method, and maps the result to a response DTO.

11. MCP mission tool

MCP is the agent-facing strategy surface. The MCP mission tool owns action names, request decoding, session member resolution, caller context stamping, and deterministic structured output. The mission service owns all mission, KR, measurement, progress, persistence, and event rules.

12. Delete and archive semantics

Mission and KR service methods do not expose hard deletion. Deletion requests are lifecycle changes that preserve history.

OperationResultVisibility
DeleteMissionArchives the mission.Archived missions are terminal unless a future restore flow is explicitly designed.
DeleteKeyResultDrops the KR.Dropped KRs are excluded from activation, completion, and progress aggregation, but remain queryable as history.

13. Hard rules

RuleWhy it exists
No Deps bag in mission service construction.Constructor dependencies stay visible and reviewable.
No tool request or generic action dispatcher in internal/services/mission/app.MCP owns tool semantics.
No direct writes to task, space, heartbeat, message, or context-link repositories.Services talk to services through narrow interfaces.
No lifecycle notification handlers in the mission app service package.Event subscribers belong to the event/subscriber layer, not the mission service.
No member-facing message registry or exported event factory in mission service.The mission service owns typed event kinds and private publishing/spec helpers; subscribers own message wording and delivery.
No automatic mission-event-to-agent-message rule.Mission events become messages only when a subscriber identifies an actionable obligation or intervention need; mission.activated is actionable for coordinators of assigned spaces.
No duplicate mission activation messages.Activation notifications use deterministic idempotency keys per mission and assigned space.
No raw JSON or protocol DTOs in service methods.Protocol adapters translate at the boundary.
No partial progress writes.UpdateProgress runs completion gates before persistence and writes progress entry, KR state, mission state, and events as one use case.
No KR progress under a draft mission.Progress updates require the parent mission to be active.
No last-write-wins progress updates.Concurrent KR progress writes use optimistic concurrency and stale writes return a conflict.
No lost milestone events on progress jumps.A single update from low progress to high progress emits every newly crossed threshold, not only the final threshold.
No silent regression of completed KRs.A completed KR must be explicitly reopened before progress can decrease, and reopening resets progress to the starting value and reactivates the parent mission.
No milestone un-notification.Progress regression does not clear LastMilestoneNotified or make already fired milestones eligible to fire again.
No unsupported measurement semantics.maintain and range/tolerance KRs are not supported until their fields and progress rules are designed.
No mission activation without owned measurable scope.Activation requires at least one non-dropped KR and every non-dropped KR assigned to an open owning space; no KRs, all dropped KRs, unowned live KRs, and closed/archived owner spaces fail the gate.
No mission completion without satisfied measurable scope.Completion requires at least one non-dropped KR and every non-dropped KR completed; no KRs, all dropped KRs, and only draft/open/in-progress KRs fail the gate.
No KR completion with non-terminal linked tasks.Linked tasks in pending, active, blocked, or in_review block KR completion.
No stale mission status after dropping KRs.The parent mission is recomputed from remaining non-dropped KRs; previous status does not preserve an invalid active or completed state.
No reactivation for cosmetic or administrative KR edits.A completed mission reactivates only when new live measurable work is introduced.
No silent event-publish failures on state transitions.Fired events are part of the service contract.
No hard delete through mission service methods.Mission deletion archives and KR deletion drops so history remains available.
No activity timeline embedded in mission metadata.The event layer owns event history and query projections.
Tests drive service methods and production RPC/MCP entry points.The service is done only when real wiring reaches it.
