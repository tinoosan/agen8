Frontend Behavior and Pin Ranking

This page captures UI behavior that is cross-file and behavior-critical: server-backed pin persistence, cache semantics, and visible ranking/ordering behavior.

1. Pin lifecycle and persistence

The frontend pin surface is now server-backed and shared across sessions via pin.list, pin.add, and pin.remove RPC methods.

  • usePins(projectId) is the hook-level gateway used by mission surfaces and should be shared for future pinnable entities.
  • When signed in and a projectId exists, hook state is backed by pin.list and keyed as qk.pins(projectId).
  • togglePin(nodeRef, nodeType) calls pin.add/pin.remove; this allows mission pins plus extensibility for decisions, tasks, and key results.

2. Cache semantics and consistency

Consistency is tuned for low-latency UX with safe fallback:

  • Pin add/remove is optimistic: the cache updates before RPC response.
  • On RPC failure, optimistic changes are rolled back to previous cached state.
  • On settle, cache invalidation runs via qk.pinsAll to force a fresh server read for all pin consumers.
  • The hook refreshes periodically (refetchInterval: 30_000) as an additional eventual-consistency backstop.

3. Mission list surfaces

Mission list components render pin state consistently through usePins() and prioritize pinned rows:

  • DashboardMissionsPanel sorts visible missions with pinned IDs before unpinned rows.
  • Pin toggles in the panel preserve existing filtering/search behavior and only alter ordering by priority.
  • Pin affordance remains mission-centric here; new pinnable node types flow through the same hook contract.

4. Command palette search behavior

Search ranking uses non-invasive pin boosting:

  • pinned keyword is injected into command keywords for pinned mission rows only.
  • pinnedBoostFilter adds a small score bump without changing match eligibility.
  • Unmatched items remain hidden; pin status does not force-display nonmatching rows.
  • Pinned missions are visually marked with the pin glyph.

Implementation reference:

  • web/src/components/CommandPalette.tsx

5. Strategy Map search behavior (desktop + mobile)

Context-map search has two entry points that must stay aligned:

  • Keyboard: / focuses/open the node-search dialog inside StrategyMapSearch.
  • Mobile top bar: tapping the app top-bar search icon while activeView === 'strategy' opens the same strategy-map node-search dialog via global store state.
  • For all other views, the top-bar search icon opens the command palette.
  • Open state is stored in strategySearchOpen so it can be controlled from components outside the page tree.
  • The map page does not force-reset this flag on unmount; the shared modal close path clears it on actual close so stale-open state is avoided without disrupting StrictMode mount/unmount cycles.

This avoids the keyboard-driven touch-gap introduced by mobile devices that cannot rely on / reliably.

6. Mission lifecycle and delete semantics

Frontend mission lifecycle remains soft-first:

  • MissionLifecycleActions only renders status transitions (activate/pause/resume/complete/archive) mapped to mission.update.
  • mission.delete is the Archive action (reversible by un-archiving in supported flows).
  • mission.purge is destructive and permanent, and is surfaced as Delete permanently in mission detail.
  • The same detail surface intentionally copies lifecycle texts and confirmation copy to keep status and irreversibility semantics clear to users across view states.

Implementation references:

7. Backend impact

Frontend ordering is user-visible, but source-of-truth ranking support comes from backend pin-aware search:

  • pin service provides list/add/remove endpoints used by the frontend.
  • Graph search routes promote pinned nodes in ranking for both query and browse paths, so pin boosts are durable and consistent across clients.
