Architecture · Project Service

Project Service

The project service owns project identity, a location-scoped root reference, and the member roster. The project is the coordination boundary: members attach directly to a project. There is no space layer.

Hard cutover. The space service has been retired and its member roster subdomain absorbed into the project service. Members key off project_id, not space_id. The former project-over-spaces topology is gone.

1. Service boundary

Projects are durable workspace records. A project root is meaningful only inside a location, so the project stores locationId with root. A project does not run code; its location can run code. Members are project-scoped work-context identities registered by MCP callers. A member belongs to exactly one project through Member.ProjectID. The project service owns the member roster directly: member identity, labels, member type, and lifecycle state. It does not own location probing, filesystem browsing, credentials, tasks, missions, decisions, graph links, or HTTP tool execution.

Project owns
Composition and context
Project identity, location-scoped root reference, display metadata, lifecycle, and the member roster.
Member roster owns
Actor identity
Member id, (project_id, harness_kind, native_session_ref), display label, member type, channel id, and lifecycle state.
Location owns
Reachability and capabilities
Location records, filesystem browsing, remote connection setup, credentials, online status, and capability probes live outside the project service.
Other services own
Behavioral state
Tasks, missions, decisions, files, and harness-visible context remain behind their own service boundaries.

2. Architecture layers

The project service follows the same service shape as task and message: domain aggregates own rules, app services orchestrate cross-service reads, infra persists through repository interfaces, and RPC returns client-ready views.

Protocol
RPC handlers validate transport params, resolve caller identity, call app.Service, and return project and member views.
App
app.Service manages projects and the member roster, validates member runtime config, and enforces coordinator admission.
Domain
project.Project owns project identity and the locationId + root mapping. member.Member owns actor identity, member type, and lifecycle.
Infra
SQLite and Postgres repositories persist projects and members behind domain repository contracts.

4. Member roster

The member roster is a subdomain of the project. A member is one harness session registered into the project when a stable native session reference is available, identified by (project_id, harness_kind, native_session_ref). The channel id is deterministic: channel:<project>:member:<id>. Registration is the boundary where the MCP project tool binds the caller to an Agen8 member record.

Coordinator admission is a project-scoped invariant: a project has at most one active coordinator member. The first member registered into a project becomes the coordinator; later session-specific members become workers. When the future group primitive is introduced, coordinator uniqueness can be re-scoped from project to group additively, without changing member identity.

5. RPC surface

Project RPC methods expose durable project records and the member roster. Transport handlers validate required ids, call app.Service, and return frontend-ready views.

project.createCreate a project from browser/user input.CreateProjectAccepts locationId, root, and title. The service derives the project id so clients do not duplicate id rules.
project.saveCreate or update a durable project record when the caller already has a project id.SaveProjectRequires projectId and root; empty locationId means local. It is an upsert-shaped command, not a filesystem initializer.

project.deletePermanently remove an archived project record.DeleteProjectRefuses active projects. A project must be archived before it can be deleted.

6. Client contract

The browser treats projectId as the route key. Project roots are display and filesystem context scoped to locationId, not routing identity. Project-scoped UI calls use projectId and receive views that are already shaped for rendering.

Project list
project.list
Returns id, locationId, root, title, status, and timestamps for project switchers and the home page.
Member list
project.member.list
Accepts projectId. Returns members sorted coordinator-first, active before inactive, then by label.
Creation command
project.create
The client-facing creation command is the boundary for deriving a project id from user input. It accepts location id, root, and title, then calls the app service with a valid id.

project.save is available when a caller already has a valid project id. The UI creation flow does not invent ids itself; it uses project.create so every client gets the same id derivation rule.
