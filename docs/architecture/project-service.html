Architecture · Project Service

Project Service

The project service owns project identity, a location-scoped root reference, and project-scoped topology over spaces. Space records remain owned by the space service and are hydrated through a narrow loader interface.

1. Service boundary

Projects are durable workspace records. A project root is meaningful only inside a location, so the project stores locationId with root. A project does not run code; its location can run code. Member harness sessions execute inside the project location and root through the location and harness services. A space belongs to exactly one project through Space.ProjectID. The project service organizes those spaces into pinned views, clusters, and coordination scopes without owning location probing, filesystem browsing, credentials, runtime state, member roster, message channels, tasks, missions, or harness delivery. Those reachability concerns belong to the location service.

Project owns
Composition and context
Project identity, location-scoped root reference, display metadata, pinned spaces, and project-scoped space clusters.
Location owns
Reachability and capabilities
Location records, filesystem browsing, remote connection setup, credentials, online status, and capability probes live outside the project service.
Space owns
Space truth
Project membership via ProjectID, title, status, customization, member roster, member labels, and member runtime state.
Other services own
Behavioral state
Tasks, messages, missions, decisions, escalations, files, and harness-visible context remain behind their own service boundaries.

2. Architecture layers

The project service follows the same service shape as task and message: domain aggregates own rules, app services orchestrate cross-service reads, infra persists through repository interfaces, and RPC returns client-ready views.

Protocol
RPC handlers validate transport params, resolve caller identity, call app.Service, and return project views.
App
app.Service manages projects and project topology, then hydrates space display data through SpaceLoader.
Domain
project.Project owns project identity and the locationId + root mapping. cluster.Cluster and cluster.SpaceRef own project-scoped grouping, pinning, and coordination scope.
Infra
SQLite and Postgres repositories persist projects and topology records behind domain repository contracts.

4. Project space list flow

The project service loads spaces by project through SpaceLoader, then overlays project-owned topology such as pinned order and cluster membership. This keeps project organization durable without duplicating space-owned state.

type SpaceLoader interface {
    Get(ctx context.Context, id spacedomain.SpaceID) (spacedomain.SpaceRecord, error)
    List(ctx context.Context, filter SpaceFilter) ([]spacedomain.SpaceRecord, error)
}

type ProjectSpaceView struct {
    ProjectID types.ProjectID
    SpaceID   spacedomain.SpaceID
    Status    string
    SortOrder int
    Pinned    bool

    // Hydrated from the space service.
    Title     string
    SpaceOpen bool
    Members   []SpaceMemberView
}

5. RPC surface

Project RPC methods expose durable project records and project-owned organization. Direct space management remains on space.* methods. Transport handlers validate required ids, call app.Service, and return frontend-ready views.

project.saveCreate or update a durable project record when the caller already has a project id.SaveProjectRequires projectId and root; empty locationId means local. It is an upsert-shaped command, not a filesystem initializer.
project.archiveHide a project from active work without deleting its record immediately.ArchiveProjectSets project status to archived and keeps durable project metadata available.
project.deletePermanently remove an archived project record.DeleteProjectRefuses active projects. A project must be archived before it can be deleted.

project.space.listRender project sidebars, boards, dashboards, and project-scoped pickers.ListProjectSpacesLoads spaces by project through SpaceLoader and overlays pinned/cluster state.
project.cluster.saveCreate or update a project-owned space cluster.SaveClusterRequires clusterId, projectId, and name. The cluster is organization state, not space ownership.
project.cluster.listRender project-owned space groups and coordination scopes.ListClustersReturns clusters and their ordered/pinned space refs. Cluster commands stay separate from space lifecycle.

6. Client contract

The browser treats projectId as the route key. Project roots are display and filesystem context scoped to locationId, not routing identity. Project-scoped UI calls use projectId and receive views that are already shaped for rendering.

Project list
project.list
Returns id, locationId, root, title, status, and timestamps for project switchers and the home page.
Space list
project.space.list
Accepts projectId. Returns spaces sorted with pinned spaces first, open spaces before closed spaces, then configured order and title.
Creation command
project.create
The client-facing creation command is the boundary for deriving a project id from user input. It accepts location id, root, and title, then calls the app service with a valid id.

project.save is available when a caller already has a valid project id. The UI creation flow does not invent ids itself; it uses project.create so every client gets the same id derivation rule.
