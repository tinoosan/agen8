Architecture · Note Service

Note Service

The note service is where an agent keeps the lightweight thoughts it produces mid-session — a learning worth remembering, an idea worth pursuing — that would otherwise die in the transcript. A note starts as freely editable, freely deletable scratch memory. The moment something durable grows from it — a decision that cites it, a task spawned from it — it hardens into permanent record: immutable and undeletable, for as long as that durable thing exists. That one hardening rule is the whole primitive. Everything else a note does, it does through the work graph.

1. Purpose and ownership

A note is a captured thought, not a log line. It holds the kind of artifact an agent generates while working and would otherwise lose: a learning that explains why the code behaves as it does, or an idea for work that is not yet a task. The service makes that artifact durable and queryable, and lets it participate in the work graph like any other node.

The lifecycle turns on one fact, and it is read from the graph, not stored on the note: does a durable node currently depend on this note? While nothing does, the note is freely mutable and freely deletable by the agent or the user. The moment a durable node grows from it — a task it spawned, a decision that was informed by it — the note is frozen: it can no longer be edited or deleted, because something permanent now stands on it. Because the freeze is derived from live edges rather than a stored flag, it answers its own edge cases: archive that durable node and the edge stays live, so the note stays frozen; delete that node and its edges cascade away, so the note becomes editable again — with no un-freeze code to run.

That derived latch is the entire reason the note primitive exists. A note is the one agent-facing object that is freely-deletable working memory until it has a consequence, then hardens into permanent record. Its type and its relationships it borrows from the graph.

The service follows the same architectural rule as the task and decision services: protocol adapters translate payloads, the application service orchestrates side effects, the domain validates the record, and the repository persists canonical state.

MCP and RPC adapters
Translate tool or JSON-RPC payloads into typed service calls. The MCP note tool owns capture, edit, delete, archive, get, and list action semantics. There is no promote action.
Application service
Capture, edit, or delete an open note; before any edit or delete, ask the graph whether a consequence edge exists and refuse loudly if it does. Toggle the archived flag independent of the latch, and publish events.
Domain
Owns Note, the curated NoteType label, NoteSource, constructors, filters, and body validation. There is no stored status field — open vs frozen is derived from live edges, not a domain enum.
Repository
Stores and loads note records. Query methods take NoteFilter so project scope and filter semantics stay in one contract.

2. Note model

A note carries a curated type label, a body, who produced it, and an archived flag. Its relationships — what it was captured against, what grew from it — live in the graph, not on the record.

TypeMeaningTypically leads to
insightA learning or observation worth keeping.A decision that is informed_by it.
ideaA seed of future work.A mission, key result, or task it spawned.

The "typically leads to" column is convention, not constraint. type is a curated soft label: seeded with insight and idea, and extended deliberately when a new value earns its keep for filtering. The agent picks from the set; it does not invent values per note, because a free-text type fragments the very scannability the label exists to provide. What the label does not do is gate consequences — an insight can lead to an idea, a note captured under one mission can relate to another, and any note can lead to anything the graph can express. The label is for humans scanning and for filtering; the edges carry the meaning.

The note's mutability is a derived state with two values, and a durable node is the toggle between them:

The forward transition is the appearance of a consequence edge; the backward one is its disappearance when the durable node is deleted. Both are read from the graph — the note service stores neither. Archiving the durable node is not deletion, so it leaves the edge live and the note frozen.

MCP tool schema

The MCP note tool schema requires only action at the top level because the active model tool runtime does not accept top-level schema combinators. Callers provide action and only the fields used by that action. The handler enforces the action-specific field contract, rejects unknown fields, rejects fields that belong to a different action, and rejects explicit null values before any service call.

ActionRequired fieldsOptional fields
capture action, type, body context_ref (draws a made_during edge to a task, key result, or mission)
edit action, note_id, and at least one of body / type the unedited one of body / type
delete action, note_id —
archive action, note_id, archived —
get action, note_id —
list action, project_id type, archived, since, until, limit, offset

There is no promote action, because a note does not create the thing it leads to. Work that grows from a note is created by its own tool — the task, mission, or decision surface — which references the note and draws the spawned or informed_by edge. edit and delete are refused when the note is frozen; the handler surfaces that as an error, never a silent no-op. archive is always permitted, frozen or not, because visibility is a separate axis from mutability.

3. Service boundary

The application service has an explicit constructor. It does not accept a dependency bag. Required production dependencies fail startup when absent.

func NewService(
    repo domain.Repository,
    clock domain.Clock,
    edges GraphConsequenceReader,
    links GraphLinkWriter,
    linkDeleter GraphLinkDeleter,
    events EventPublisher,
    members MemberDisplayLookup,
    logger *slog.Logger,
) (*Service, error)

edges is the read port the latch is derived from: before an edit or delete, the service asks it whether any spawned or informed_by edge is currently incident to the note. A non-empty answer means a durable node depends on the note, so the verb is refused. links draws the note's own associative edges — the made_during context link at capture — and linkDeleter removes them when an open note is deleted. Member display lookup enriches event payloads for readable text; failures there are presentation-only and do not block persistence.

There are no promotion ports. The note service does not import the decision, mission, or task services, and never creates a durable node. That keeps it a leaf: it owns its records and its latch, and it reads the graph to evaluate that latch, but it does not reach into other domains. The node that grows from a note is built and validated by its own service, which draws the consequence edge as it does so.

4. Domain model

Note is a small, intrinsic record. It carries no status field and no target pointer, because the open/frozen distinction is not stored on the note — it is computed from the edges the graph holds against it.

type Note struct {
    ID             NoteID
    ProjectID      string
    Source         NoteSource
    SourceIdentity string
    Type           NoteType
    Body           string
    Archived       bool
    CreatedAt      time.Time
    UpdatedAt      time.Time
}

Two independent axes govern a note, and only one of them is stored:

AxisValuesStored?Reversible?Controls
Mutability (the latch)open ↔ frozenNo — derived from live consequence edgesYes — re-opens if the depending node is deletededit and delete
Visibilityactive ↔ archivedYes — the Archived fieldYeswhether the note shows in default views

Source records who produced the note; the retained source is agent. UpdatedAt moves on every edit while the note is open; once a consequence edge exists, edits are refused, so the timestamp naturally settles at the last moment the note was still scratch.

5. Persistence and queries

The repository is split into reader and writer contracts. Service methods use domain names: CreateNote, GetNote, ListNotes, UpdateNote, and DeleteNote. UpdateNote serves both the edit path and the archive toggle; the service, not the repository, enforces that an edit or delete is refused once a consequence edge exists — the repository persists stored state and does not know about the latch.

type NoteFilter struct {
    ProjectID string
    Types     []NoteType
    Archived  *bool
    Query     string
    Since     *time.Time
    Until     *time.Time
    SortDesc  bool
    Limit     int
    Offset    int
}

Project scope is part of NoteFilter, and the filter covers the stored facets: type, archived state, text search, time window, sort order, and pagination. There is no status filter, because open vs frozen is not stored. When a caller needs that distinction — for example, to show only the still-open notes an agent can still revise — the service hydrates each note's derived state through the same GraphConsequenceReader the latch uses, rather than reading a column.

6. Leading to work: edges, the latch, and events

Capture is ordered like any creation: validate the type label and body, optionally draw a made_during edge to a referenced task, key result, or mission, persist the row, and publish note.captured. Deleting an open note removes that associative edge before deleting the row, so a discarded note leaves nothing behind. A made_during edge is context, not consequence — it records where the note was captured and never freezes it.

A note leads to durable work from the other side. The node is created by its own service, which references the note and draws a consequence edge — spawned from the note to the new work, or informed_by from a decision back to the note. The note is not the actor and creates nothing; this is what keeps the note service a leaf. The latch is then a pure derivation: the edge is the frozen state.

The freeze is never written to the note. Before an edit or delete, the service reads the live consequence edges; any present and the verb fails loudly. Because the state is derived, two awkward problems simply do not arise: there is no window where a note is linked but still mutable, since the edge and the frozen state are the same thing; and there is no un-freeze code, since the graph's cascade on node deletion removes the edge and the note re-opens on its next read.

One contract this leans on lives outside the note service: the consequence edge and the durable node it implies must come into being together. A note must never be frozen against a node that does not exist, so the creating service draws the spawned or informed_by edge atomically with the node it creates. The note service does not invent a fallback or paper over a half-built link; it simply reads whatever edges are really there.

note.captured, note.edited, note.archived, and note.deleted are published after their respective persistence steps; publish failure returns an error, because a missing event hides a state change from downstream projections. There is no note.frozen event: freezing is not a transition the note service performs, it is a derived reading of the graph. The signal that a note became load-bearing rides on the edge-creation event emitted by the service that drew it.
