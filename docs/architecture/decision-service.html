Architecture · Decision Service

Decision Service

The decision service is the durable work-memory boundary for consequential choices. It records what was decided, who made or requested the decision, what context made it necessary, what human answer resolved it when human judgment was required, and how that record connects to tasks, key results, missions, and plans.

1. Purpose and ownership

A decision is a product artifact, not a log line. It explains a branch in the work: an agent selected an approach, an operator resolved an escalation, or a human answered a structured question that unblocked the next step. The service makes that artifact durable, queryable, and linked into the work graph.

The decision service ownsThe decision service does not own
Canonical Decision records and payload validation.Prompt instructions or model behavior.
The resolved audit entry for log and ask_user decisions.The blocking wait loop that collects human input.
Context links from decisions to tasks, key results, missions, and plans.Task lifecycle, mission lifecycle, or plan review state.
Project-scoped decision queries, counts, exports, and graph hydration.Transcript card rendering or activity-feed formatting.
decision.logged publication after persistence.Notification storage, delivery, or inbox read state.

The service follows the same architectural rule as the task service: protocol adapters translate payloads, the application service orchestrates side effects, the domain validates the record, and the repository persists canonical state.

MCP and RPC adapters
Translate tool or JSON-RPC payloads into typed service calls. The MCP decision tool owns action="log" and action="ask_user" semantics.
Application service
Build or accept a decision, resolve related refs, deduplicate retry storms, persist, write graph links, and publish the decision event.
Domain
Owns Decision, DecisionKind, DecisionSource, LogPayload, AskUserPayload, constructors, filters, and validation.
Repository
Stores and loads decision records. Query methods take DecisionFilter so project scope and filter semantics stay in one contract.

2. Human input model

ask_user is a decision because the human answer becomes part of the reasoning trail. The question itself is not enough; the durable artifact is the resolved question, including whether the user answered or cancelled.

The human-input primitives live outside the decision service. They define the shape of a question and answer:

type Question struct {
    ID             string
    Text           string
    Type           string
    Options        []string
    AllowFreeForm  bool
    Recommendation string
    Blocking       bool
}

type QuestionsResult struct {
    Cancelled bool
    Answers   []Answer
}

The MCP layer delegates the active interaction to the human input service: DeclareHumanInput parks the tool call and exposes the questions to the operator; ResolveHumanInput receives the answers or cancellation. The decision service is called after resolution through CompleteAskUser, and it persists the final audit record.

func (s *Service) CompleteAskUser(
    ctx context.Context,
    req AskUserRequest,
    result humaninput.QuestionsResult,
) (Result, error)

The decision row stores the original questions, the returned answers, and cancelled=true when the operator cancels. Agents treat returned answers as authoritative: they do not ask the same question again unless they need a genuinely new, narrower decision.

MCP tool schema

The MCP decision tool schema requires only action at the top level because the active model tool runtime does not accept top-level schema combinators. Callers provide action and only the fields used by that action. The handler enforces the action-specific field contract, rejects unknown fields, rejects fields that belong to a different action, and rejects explicit null values before any service call.

ActionRequired fieldsOptional fields
log action, title, rationale alternatives_rejected, invalidation_conditions, confidence, task_ref, key_result_ref, mission_ref, plan_ref
ask_user action, title, questions context, task_ref, key_result_ref, mission_ref, plan_ref, answers, cancelled

3. Service boundary

The application service has an explicit constructor. It does not accept a dependency bag. Required production dependencies fail startup when absent.

func NewService(
    repo domain.Repository,
    clock domain.Clock,
    links GraphLinkWriter,
    linkDeleter GraphLinkDeleter,
    events EventPublisher,
    tasks TaskKeyResultReader,
    missions KeyResultMissionReader,
    members MemberDisplayLookup,
    logger *slog.Logger,
) (*Service, error)

repo, clock, links, linkDeleter, and events are mandatory. Task and mission readers enrich references: a decision linked to a task can also link to the task's key result and mission. Member display lookup enriches event payloads for notification text; failures there are presentation-only and do not block persistence.

4. Domain model

Decision is a discriminated record. Exactly one payload pointer is set, and that pointer determines the kind.

type Decision struct {
    ID             DecisionID
    ProjectID      string
    Source         DecisionSource
    SourceIdentity string
    Title          string
    Confidence     float64
    TaskRef        string
    KeyResultRef   string
    MissionRef     string
    PlanRef        string
    CreatedAt      time.Time
    Log            *LogPayload
    AskUser        *AskUserPayload
}
KindMeaningRequired payload
logAn agent or operator records a decision already made.LogPayload.Rationale
ask_userA structured human question is resolved and recorded.At least one Question; answers or cancellation come from QuestionsResult.

Source records who produced the decision: agent for agent tool calls and operator for operator-owned resolutions. It is separate from Kind; an agent can ask a human question, and an operator can resolve an escalation by creating a log decision.

5. Persistence and queries

The repository is split into reader and writer contracts. Service methods use domain names instead of storage-era names: CreateDecision, GetDecision, ListDecisions, CountDecisions, ExportDecisions, and DeleteDecision.

type DecisionFilter struct {
    ProjectID string
    Sources   []DecisionSource
    ProjectID   string
    Tags      []string
    Query     string
    Since     *time.Time
    Until     *time.Time
    SortDesc  bool
    Limit     int
    Offset    int
}

Project scope is part of DecisionFilter. List, count, and export use the same filter contract, which keeps project scoping, text search, tags, project filtering, sort order, and pagination in one place.

6. Links, events, and notifications

Decision creation is ordered: validate, resolve refs, deduplicate, persist, write context links, publish event.

Context links are emitted from the decision to each referenced key result, mission, task, and plan. decision.logged is published after link creation. Publish failure returns an error because a missing decision event hides a product-visible state transition from notification evaluators and wake-signal consumers.
