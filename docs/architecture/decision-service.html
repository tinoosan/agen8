Architecture · Decision Service

Decision Service

The decision service is the durable work-memory boundary for consequential choices. It records what was decided, who made the decision, what context made it necessary, and how that record connects to tasks, key results, and missions.

1. Purpose and ownership

A decision is a product artifact, not a log line. It explains a branch in the work: an agent selected an approach, accepted a tradeoff, or chose a next direction. The service makes that artifact durable, queryable, and linked into the work graph.

The decision service ownsThe decision service does not own
Canonical Decision records and payload validation.Prompt instructions or model behavior.
The resolved audit entry for log decisions.Blocking human waits or external approval flows.
Context links from decisions to tasks, key results, and missions.Task lifecycle or mission lifecycle state.
Project-scoped decision queries, counts, exports, and graph hydration.Transcript card rendering or activity-feed formatting.
decision.logged publication after persistence.Notification storage, delivery, or inbox read state.

The service follows the same architectural rule as the task service: protocol adapters translate payloads, the application service orchestrates side effects, the domain validates the record, and the repository persists canonical state.

MCP and RPC adapters
Translate tool or JSON-RPC payloads into typed service calls. The MCP decision tool owns action="log" semantics.
Application service
Build or accept a decision, resolve related refs, deduplicate retry storms, persist, write graph links, and publish the decision event.
Domain
Owns Decision, DecisionKind, DecisionSource, LogPayload, constructors, filters, and validation.
Repository
Stores and loads decision records. Query methods take DecisionFilter so project scope and filter semantics stay in one contract.

2. Decision log model

The retained decision surface is log. Agents record the rationale, rejected alternatives, confidence, invalidation conditions, and graph references directly in the decision row.

The decision payload is intentionally small:

type LogPayload struct {
    Rationale              string
    Context                string
    AlternativesRejected   string
    InvalidationConditions []string
}

The decision row stores the rationale and its work references. Agents treat logged decisions as durable context and create a new decision only when the direction materially changes.

MCP tool schema

The MCP decision tool schema requires only action at the top level because the active model tool runtime does not accept top-level schema combinators. Callers provide action and only the fields used by that action. The handler enforces the action-specific field contract, rejects unknown fields, rejects fields that belong to a different action, and rejects explicit null values before any service call.

ActionRequired fieldsOptional fields
log action, title, rationale alternatives_rejected, invalidation_conditions, confidence, task_ref, key_result_ref, mission_ref

3. Service boundary

The application service has an explicit constructor. It does not accept a dependency bag. Required production dependencies fail startup when absent.

func NewService(
    repo domain.Repository,
    clock domain.Clock,
    links GraphLinkWriter,
    linkDeleter GraphLinkDeleter,
    events EventPublisher,
    tasks TaskKeyResultReader,
    missions KeyResultMissionReader,
    members MemberDisplayLookup,
    logger *slog.Logger,
) (*Service, error)

repo, clock, links, linkDeleter, and events are mandatory. Task and mission readers enrich references: a decision linked to a task can also link to the task's key result and mission. Member display lookup enriches event payloads for readable display text; failures there are presentation-only and do not block persistence.

4. Domain model

Decision is a discriminated record. Exactly one payload pointer is set, and that pointer determines the kind.

type Decision struct {
    ID             DecisionID
    ProjectID      string
    Source         DecisionSource
    SourceIdentity string
    Title          string
    Confidence     float64
    TaskRef        string
    KeyResultRef   string
    MissionRef     string
    CreatedAt      time.Time
    Log            *LogPayload
}

Source records who produced the decision. The retained source is agent.

5. Persistence and queries

The repository is split into reader and writer contracts. Service methods use domain names instead of storage-era names: CreateDecision, GetDecision, ListDecisions, CountDecisions, ExportDecisions, and DeleteDecision.

type DecisionFilter struct {
    ProjectID string
    Sources   []DecisionSource
    ProjectID   string
    Tags      []string
    Query     string
    Since     *time.Time
    Until     *time.Time
    SortDesc  bool
    Limit     int
    Offset    int
}

Project scope is part of DecisionFilter. List, count, and export use the same filter contract, which keeps project scoping, text search, tags, project filtering, sort order, and pagination in one place.

6. Links, events, and notifications

Decision creation is ordered: validate, resolve refs, deduplicate, persist, write context links, publish event.

Context links are emitted from the decision to each referenced key result, mission, and task. decision.logged is published after link creation. Publish failure returns an error because a missing decision event hides a product-visible state transition from downstream projections.
