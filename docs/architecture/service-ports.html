Architecture · Service Ports

Caller-owned service ports

Agen8 service application packages stay decoupled by owning the ports they call. A service may depend on its own domain, repositories, event publishers, and local ports, but it must not import a sibling service's app package.

1. Port ownership rule

When a service application package needs behavior from another service, the calling package defines the interface it needs. That interface is a narrow port owned by the caller. The callee service does not leak its application API into the caller.

Package kindAllowed importsForbidden imports
Service app package, such as internal/services/question/app Its own domain, shared primitives, event contracts, and interfaces/DTOs declared in the same app package. Sibling service app packages, such as internal/services/decision/app, and new imports of another service's domain package unless the import is explicitly allowlisted as migration debt.
Service domain package Domain-only dependencies and standard library support. This includes literal domain packages and service-owned model subpackages such as internal/services/auth/password, apikey, session, and linktoken. Application services, RPC adapters, infrastructure repositories, service app packages, composition-root packages, read-model adapters, or another service's domain package unless the import is explicitly allowlisted as migration debt.
Service infra package, such as internal/services/location/infra Its own service domain, its own service app contracts when implementing a local adapter, storage and external-system dependencies. Foreign service app packages. Cross-service orchestration belongs behind caller-owned ports and composition-root wiring.
Composition root Concrete services from multiple packages so it can wire adapters. Business rules that should live inside a service app or domain package.

The direction is always from caller need to local port. If question/app needs to record a decision, question/app declares a DecisionLogger port. It does not import decision/app or call decisionapp.Service directly.

2. Caller-owned DTOs

Data that crosses a port is owned by the caller side. The caller defines request and result DTOs that describe the data it needs, not the callee's public application structs.

type DecisionLogger interface {
    LogDecision(ctx context.Context, req LogDecisionRequest) (DecisionLogResult, error)
}

type LogDecisionRequest struct {
    ProjectID    string
    MemberID     string
    Title        string
    Rationale    string
    Context      string
    Confidence   float64
    TaskRef      string
    KeyResultRef string
    MissionRef   string
}

This keeps the caller stable when the callee's application API changes. The adapter is responsible for translating the caller-owned DTO into the callee-owned request shape.

3. Composition root

internal/app is the composition root. It builds repositories and services, then connects service-local ports to concrete adapters. Those adapters may import both sides because they live at the process wiring boundary, not inside a service application package.

Composition-root adapters should be small translators. They may convert ids, copy fields, and handle process-level wiring concerns. They should not own domain validation, persistence decisions, retries, or lifecycle rules that belong to one of the services.

4. Cross-service read models

A read model or projection may compose facts from several services, but it must live outside the domains being read. The service domain remains the owner of invariants and state transitions; the read model owns a flattened view for lookup, hydration, search, notification, or display.

The direction is:

service domain -> no cross-service read model imports
service app    -> owns narrow row/snapshot ports when it needs a view
internal/app   -> owns concrete adapters that translate service records into those rows/snapshots

Graph hydration is the reference pattern. internal/services/graph/app/hydrators.go owns TaskHydrationReader, DecisionHydrationReader, MissionHydrationReader, and their row DTOs. Those row DTOs are graph-owned and do not import task, decision, or mission domain records. internal/app/graph_hydration.go is the concrete adapter: it imports the task, decision, and mission services, reads their domain records, and maps them into graphapp.*HydrationRow values for the graph service.

Notification derivation is the projection pattern. internal/services/notification/domain owns TaskSnapshot, the minimal neutral task view needed by Derive. internal/services/notification/app owns the TaskSource port that returns those snapshots. internal/app/application.go wires notificationTaskSource, reads tasks through the task service, and maps them into notificationdomain.TaskSnapshot. The notification service never imports task aggregates or task/app.

Do not move these adapters into a service domain to make a dependency convenient. That reverses the boundary: a domain would start depending on a projection of other domains, and the next rule change in one service could silently change another service's invariants.

5. Allowed exceptions

The import rules protect service-to-service boundaries. Delivery and infrastructure adapters have different jobs and therefore have narrower exceptions.

BoundaryAllowedReason
Delivery adapters: MCP, RPC, HTTP handlers They may import the service app package they expose and the protocol DTOs they own. They translate external payloads into service calls. They are not another service app package.
Infrastructure adapters: storage, filesystem, transport, crypto They may import their own service app or domain contracts when implementing a local adapter, plus infrastructure dependencies needed to do the work. They adapt external systems to local service contracts. They must not import a foreign service app package.
Composition root: internal/app It may import multiple service app packages and construct adapters that know both sides. Process assembly is the one place that sees all concrete services.
Service app to service app Not allowed. This couples service application APIs and makes one service's orchestration depend on another service's app layer.
Service domain to foreign service domain Only explicit allowlist entries for known migration debt. Domain packages should own their concepts. Shared ids and snapshots should move to neutral primitives or caller-owned DTOs.
Service app to foreign service domain Only explicit allowlist entries for known migration debt. New app-layer cross-service data needs a caller-owned port or a neutral contract rather than a foreign aggregate type.

6. Agen8 examples

Question to decision

internal/services/question/app owns the DecisionLogger port, LogDecisionRequest, and DecisionLogResult. When an answered question is marked AsDecision, the question service calls that local port. It does not import internal/services/decision/app.

internal/app/question_decision_logger.go is the concrete adapter. It imports both question/app and decision/app, maps questionapp.LogDecisionRequest into decisionapp.LogRequest, calls the decision service, and maps the result back to questionapp.DecisionLogResult.

Location to credential

internal/services/location/app owns a Transport port whose methods work in location-owned terms: Probe, ListDir, ProbeResult, and DirEntry. The location app does not import credential/app.

The SSH transport implementation in internal/services/location/infra needs credentials to open remote connections, so the infrastructure adapter defines a CredentialResolver dependency and resolves credential material while performing transport work. internal/app/application.go wires the concrete credential service into that transport with locationinfra.NewTransport(locationinfra.TransportConfig{Credentials: credentialSvc}).

Other reference patterns

notificationTaskSource in internal/app/application.go adapts task service data into notification-owned snapshots so notification code does not import task domain or app types. linkTokenIssuerAdapter lets the project service request link-token behavior through project-owned DTOs while the composition root translates to auth service calls.

7. Guardrail test

The import boundary is enforced by internal/architecture/service_app_imports_test.go. The test parses service app, domain, and infra packages and fails on these boundary directions:

  • internal/services/*/app importing another service's app package.
  • Service-owned domain packages importing another service's domain package unless the exact file and import path are allowlisted as debt. The scan covers literal internal/services/*/domain trees and non-adapter model subpackages under a service, excluding app, infra, and rpc.
  • Service-owned domain packages importing any service app package, including their own service's app package.
  • Service-owned domain packages importing internal/app, where concrete read-model and projection adapters belong.
  • internal/services/*/app importing another service's domain package unless the exact file and import path are allowlisted as debt.
  • internal/services/*/infra importing another service's app package. Own-service infra-to-app imports remain allowed for adapters that implement local service contracts.
  • internal/services/graph/app importing task, decision, or mission implementation records instead of graph-owned hydration row ports.
  • internal/services/notification/app or internal/services/notification/domain importing task aggregates or task/app instead of using notification-owned TaskSnapshot values through TaskSource.

Run it directly with:

go test ./internal/architecture

Failure output includes the importer file, line, import path, and boundary direction. The guardrail catches the forbidden shape, but it does not judge adapter quality. Reviewers should still check that composition-root and infrastructure adapters are small translators and that caller-owned DTOs do not become copies of callee application structs.

8. Allowlist discipline

Allowlist entries are temporary debt markers, not a general extension point. Each entry names the importer file and import path exactly, and the note should say what refactor will make the exception disappear.

Do not add a new allowlist entry for convenience. First prefer a caller-owned port, a local DTO, a neutral primitive id, or composition-root adapter wiring. If a refactor removes the crossing, delete the allowlist entry in the same change; stale entries fail the architecture test so the list stays honest.
