Architecture · Composition Root

Application composition root

How services are owned, wired, and reached. The single mental model for adding, finding, or replacing any dependency.

The flow, in one diagram

Different clients speak different protocols suited to them. Each protocol has its own adapter. All adapters converge on one Application. From there, one direction down: service → repository → backend.

The composition root also wires cross-service runtime boundaries that are not user-facing protocols. The harness service receives a project workdir resolver backed by the project service and a command-runner resolver backed by the location service. That wiring makes harness sessions start in the project's selected location and root instead of inheriting the daemon process directory.

The rules

R1 — Every dependency is a service. The LLM client, the event bus, the harness registry, the broadcaster — they all live on Application as services. Not "shared infrastructure," not "passed via cfg," not "global." A service. The shape is uniform; callers learn one access pattern (app.X) and apply it everywhere.
R2 — Application has zero methods. Only NewApplication and field access. Application is a composition root, not a behavior owner. If logic feels like it wants to live on Application, that logic belongs inside one of the services Application holds.
R3 — Services are stateless. Per-tenant state lives in repositories. A service is a process singleton. User identity travels via ctx. Repositories filter by user_id from ctx. No closure-captured user context, no per-tenant service rebuilds, no scope juggling. This is what lets one Application serve N concurrent users with goroutine-per-request.
R4 — No DBHandle outside infra packages. The database is an implementation detail of each repository. Storage backends are selected behind repository interfaces. Nothing above the repository layer knows or cares which backend is in use. Repositories are constructed once in NewApplication, the chosen backend selected from config.
R5 — Repository interfaces split by capability. XReader, XWriter, XReaderWriter (which embeds both). Consumers depend on the smallest interface they need — a query handler takes XReader, a mutation handler takes XWriter, the service itself takes XReaderWriter. Massive god interfaces are forbidden; they leak implementation across consumers and make mocking painful.
R6 — Outside callers reach services through Application, never via internal/services/<svc>/{app,infra} directly. Importing the service's domain types (e.g. messagedomain.MessageFilter, the Message struct) is fine — those are the service's public contract. Importing messageinfra.NewSQLiteRepository from outside the message service is a boundary violation: someone else is constructing your service's storage.

Protocol adapters

Two protocols exist: JSON-RPC and MCP. They are peers, not stacked. RPC is a transport adapter for the UI and CLI. MCP is an agent-facing tool surface that orchestrates one or more application services behind each tool action. Neither adapter routes through the other.

AdapterProtocolClientsHow identity arrives
RPCServer JSON-RPC 2.0 over stdio or HTTP CLI (cmd/agen8), web UI User identity from the connection / session
MCPServer
(external harness MCP)		 MCP over HTTP Member harnesses (Codex, Claude Code, etc.) running as members Member identity from a session token registered when the harness is spawned

Both adapters hold a *Application and inject identity into ctx using their own auth mechanism. RPC handlers usually dispatch straight to one service. MCP tool handlers interpret the product-facing tool action, compose service dependencies supplied from Application, and return one agent-facing result. From the service's perspective, both are still typed method calls with a ctx that carries identity.

MCP tool composition

MCP tools are organized around product concepts, not backend package names. A single tool action may coordinate multiple services behind one coherent agent-facing operation.

Tool callService compositionMeaning
project(action="register") ProjectSvc member roster methods Register the calling harness session as a member of the project.
project(action="member_list") ProjectSvc member roster methods List the members registered in the project.
message(action="send") ProjectSvc + ChannelSvc + MessageSvc Resolve the destination, authorize the route, persist the message, and trigger delivery.
http(...) CredentialSvc + package-local HTTP clients Make a bounded HTTP request with host-scoped credential injection.
task(action="create") TaskSvc + ProjectSvc member loader + context readers Create a member-routed task, validate linked context, and let the task service publish the assignment message.
mission.kr_list MissionSvc + mission read-side collaborators List key results for a mission without exposing internal read-model boundaries to the agent.

The MCP server owns cross-service composition. Services do not reach into each other's repositories, and services do not expose tool-shaped methods such as Execute(action, rawJSON). Tool handlers coordinate through Application; each service still reads and writes through its own repository boundary.

Native MCP wiring

Native MCP tools receive typed dependencies from the application composition root through the MCP session. The MCP bootstrap registers each session with the services it is allowed to use. The native tool handler receives a narrow call context and owns tool-specific orchestration.

// MCP session bootstrap
tokenStore.Register(token, Session{
    ProjectReader:     app.ProjectSvc,  // project.ProjectService
    MemberDirectory: app.ProjectSvc,  // project.MemberService
    ChannelReader:   app.ChannelSvc,
    MessagePublisher: app.MessageSvc,
    CredentialResolver: app.CredentialSvc,
    TaskService:     app.TaskSvc,
    TaskMembers:     app.ProjectSvc,
    ProjectID:       projectdomain.ProjectID(projectID),
    MemberID:        memberID,
})

// internal/mcp/server.go
project.Handler.Handle(ctx, project.CallContext{
    Projects:        session.ProjectReader,
    Members:       session.MemberDirectory,
    ProjectID:       string(session.ProjectID),
    ActorMemberID: session.MemberID,
}, args)

The MCP task tool follows the same native shape, with a larger dependency set. Its handler owns task tool actions and cross-service lookups. The task service owns lifecycle state transitions, persistence, and task-originated assignment messages through the message service boundary.

MCP call flow

An MCP tool call is a protocol request that enters one handler. The handler owns the tool contract and maps it to service use cases. The service receives a typed command, not the original tool payload.

StepOwnerResponsibility
tools/call internal/mcp/server.go Authenticate the session, resolve the named handler, and pass the raw MCP arguments to that handler.
task(action="create") internal/mcp/tools/task/handler.go Decode the MCP payload, validate required fields, enforce member-facing tool policy, and build a typed service command.
CreateTaskCommand internal/services/task/app Authorize the caller, create the task, persist it, publish events/messages, and return a domain result.
MCP result internal/mcp/tools/task/format.go Shape the service result into deterministic MCP text and structured content. No raw payload fallback.

MCP package layout

The MCP adapter lives in its own package tree. It is a peer of the RPC adapter, not a helper hidden inside internal/app and not a global registry rooted in pkg/.

internal/mcp/
  server.go               // MCP HTTP endpoint, session auth, tools/list, tools/call routing
  context.go              // member/session identity injection into ctx
  registry.go             // local handler registry for this adapter
  toolset.go              // builds and registers product-facing handlers
  tools/
    domain/
      definition.go       // ToolDefinition and ToolFunctionDefinition
      handler.go          // shared handler contracts
      result.go           // shared result envelope helpers
    task/
      definition.go       // task(...) schema and callable definition
      handler.go          // decode task(...) actions and call typed task use cases
      types.go            // MCP request shapes and command mapping
      format.go           // deterministic MCP text and structured content
      handler_test.go     // success, validation, policy, and formatting coverage
    project/
      definition.go       // project(...) schema and callable definition
      handler.go          // decode project(...) actions and compose service use cases
      types.go            // MCP request shapes
      format.go           // deterministic MCP result shaping
    mission/
    plan/
    decision/
    operator/
    heartbeat/
    http/

internal/mcp/tools/<tool> is the canonical home for MCP tool behavior. Product-facing tool names live here, request/response decoding lives here, tool-action policy lives here, and cross-service orchestration lives here. Service packages remain transport-agnostic and do not define MCP tool schemas, tool actions, or raw JSON tool request envelopes. The MCP project tool is the reference shape for handler-owned orchestration.

The MCP message tool owns agent-facing message sending. Member discovery remains in project(action="member_list"); message delivery remains in message(action="send").

The MCP adapter does not load tools through side-effect imports or a process-global module registry. The composition root builds the handler set from application services, the MCP server registers those handlers in a local registry, and the server exposes one member-authenticated MCP surface. The registry stores handlers, not domain services and not generic runtime modules.

Adding a new protocol (anything that wants to expose agen8's capabilities under different rules) means writing a new peer adapter at this layer. It does not mean tunneling through an existing adapter.

The Application struct

// internal/app/application.go

// Application is the process composition root. Every service the
// running system reaches for lives here as a field. Construction
// happens exactly once, in NewApplication.
//
// Hard rule: Application has no methods. If you find yourself wanting
// to add one, the logic belongs in a service.
type Application struct {
    ChannelSvc     *channelapp.Service
    MessageSvc     *messageapp.Service
    ProjectSvc       *projectapp.Service
    CredentialSvc  *credentialapp.Service
    ContextLinkSvc *contextlinkapp.Service
    DecisionSvc    *decisionapp.Service
    MissionSvc     *missionapp.Service
    // ... remaining services
}

func NewApplication(cfg config.Config) (*Application, error) {
    // 1. Open the storage backend chosen by cfg (SQLite or Postgres).
    // 2. Construct each service's repository against that backend.
    // 3. Construct each service against its repository.
    // 4. Return a fully wired *Application.
    //
    // Order matters only when services depend on each other; document
    // those dependencies inline and keep the graph shallow.
}

Application does not own protocol behavior. It owns services. The composition root constructs protocol adapters separately and gives each adapter the same *Application.

Adding a service

The same five steps apply for every service. Each step is small enough to ship as a single commit.

#StepWhat it touches
1 Define / verify repository interfaces in internal/services/<svc>/domain/ Split into XReader, XWriter, XReaderWriter. Keep them small.
2 Concrete repository implementation(s) in internal/services/<svc>/infra/ One per backend. SQLite required. Postgres added when storage abstraction work lands.
3 Add field to Application; construct in NewApplication internal/app/application.go
4 Register protocol handlers from Application services internal/rpc and internal/mcp receive service fields from the composition root.
5 Repoint callers from local variables / config fields to app.XSvc RPC handlers, MCP handlers, hosted scope, tests. Boundary violations (cross-service imports of infra/) get fixed in this step too.

Adding an MCP tool

#StepWhat it touches
1 Create internal/mcp/tools/<tool>/ definition.go, handler.go, types.go
2 Define typed request and response shapes for each action No stringly "action bag" structs and no raw JSON service request. Decode into concrete command types.
3 Inject service dependencies from *Application into the tool handler The composition root supplies concrete app services; the handler calls typed service methods.
4 Register the tool in internal/mcp/toolset.go Local MCP adapter registration only; no global module registry
5 Keep one product-facing tool path The MCP catalog registers the native handler once, and internal/mcp/server.go dispatches to that handler.
R7 — MCP tool ownership lives under internal/mcp/tools. Tool orchestration does not live in service packages, and it does not live in a shared global pkg/tools runtime. The MCP adapter owns tool registration, request decoding, service composition, and response shaping.
R8 — Product-facing tool grouping is allowed to span services. A project tool may call ProjectSvc, ProjectSvc project lifecycle methods, ProjectSvc member roster methods, and MessageSvc. The grouping is a product decision at the MCP layer, not a permission for services to cross repository boundaries.
R9 — Services do not know about tools. Service packages do not define ToolService interfaces, parse MCP action strings, or accept raw tool JSON. They expose typed use cases. MCP handlers translate tool payloads into those use cases.

messagedomain.MessageRepositoryNO — only the service implements/depends on its own repository
messageinfra.NewSQLiteRepository(...)NO — building someone else's storage
messageapp.NewService(...)NO — only NewApplication constructs services

The hosted vs local question

There is no architectural fork. Both run the same Application. The difference is which storage backend the repositories were built against (SQLite for local, Postgres for hosted) and how the RPC server is exposed (stdio for local, HTTP for hosted). Per-tenant isolation lives entirely in the repository layer via user_id from ctx.

There is no per-tenant service rebuild. Services are process singletons constructed once in NewApplication (R3). Every method receives the tenant's identity through ctx and every repository query scopes to user_id extracted from that context. The hosted adapter authenticates the inbound HTTP request, injects the tenant identity into ctx, and forwards to the same RPCServer that local mode uses.

Process entry, one paragraph

The active process entrypoint opens the storage backend chosen by config, constructs Application once, constructs peer adapters such as RPCServer and MCPServer from the same *Application, and starts each adapter on its own listener. Every incoming request enters through an adapter. RPC handlers usually dispatch straight to one service. MCP handlers decode a product-facing tool action, map it to typed service commands using dependencies supplied from Application, and return one agent-facing result. No daemon supervisor owns service semantics.

The composition root owns service construction once. Protocol adapters and background processes reach the system through the same *Application.
