Architecture · Channel Service

Channel Service

A channel is a single conversation surface inside a project — one per active member. The channel service owns channel records, per-user read state, and the four RPC methods (channel.list, channel.get, channel.send, channel.markRead) the frontend uses to render and drive those conversations.

1. What a channel is

A channel is a record in the channel store keyed by projectId + memberId (the id is derived deterministically by MemberChannelID). It carries a few small fields — status, last-message timestamp, member label, runId — and serves as the addressable target for one side of a conversation. Channels do not own messages; messages live in the message service and reference a channel by id via Metadata["channelId"].

The channel service deliberately keeps the model thin:

  • Channel content (the messages themselves) lives in the message service — channel records just point at them.
  • Routing rules (who can send to which channel, broadcast fan-out) live in the project service's ProjectMessageOperation — the channel service only knows how to resolve a member to its channel id and how to enforce per-channel invariants like "closed channels reject sends".
  • Unread tracking is a join between channel_reads.last_seen_at and channels.last_message_at — computed at list time, not stored as a counter.

2. Architecture layers

RPC
The four channel.* RPC methods live in services/channel/rpc/Handler; the host (RPCServer) provides cross-service dependencies through a small interface.
App
Service wraps the repository with the per-method business rules — id derivation, normalization, EnsureMember, StampRunID. A single instance is constructed at the assembly root and injected; BuildService(cfg) exists only as the constructor used by that root.
Domain
Pure types — Repository interface, ErrNotFound sentinel, MaxListChannels const (the SELECT backstop). No I/O.
Infra
SQLite-backed repository. Channel rows + per-user channel_reads rows; the join for unread computation is one SQL query.

3. Retired member cleanup

When a member is retired (lifecycle moves out of active), the next channel.list call notices the dangling channel and best-effort-deletes it via DeleteForMember. The cleanup is opportunistic, not scheduled — the storage cost of a few stale rows is far smaller than the cost of running a janitor process.

4. channel.send — user to member

The frontend (and integration tests) call channel.send to push a user-input message at a specific member. The handler validates the channel, looks up the run that owns the member, builds a MemberMessage, and publishes it via the message service. The supervisor wakes; the receiving runtime claims the message via message.claim.

Two preconditions reject the send up front: channel.status == closed and projectId in the request mismatching the channel's own projectId. Each returns a precise protocol error so the frontend can render the right message.

5. Per-user unread state

Unread isn't a counter the channel service maintains. Each channel row carries a last_message_at bumped by the message publish hook whenever a message lands in the member address. Each user carries a channel_reads.last_seen_at per channel, written by channel.markRead. The two are joined at list time:

// services/channel/app/service.go — ListWithUnread (conceptual)
SELECT c.*,
       (c.last_message_at > coalesce(r.last_seen_at, 0)) AS unread
FROM channels c
LEFT JOIN channel_reads r
  ON r.channel_id = c.id AND r.user_id = ?
WHERE c.project_id = ?

The bump is wired as a hook on the message service. The application composition root sets it at startup:

// internal/app/application.go
channelSvc, _ := channelapp.BuildService(cfg)
messageService.SetOnPublish(channelActivityOnPublish(channelSvc))

The hook runs synchronously after every successful messageService.PublishMessage. It reads channelId from the published message's metadata and calls channelSvc.RecordMessageActivity(ctx, channelID, ts) on the same service instance the rest of the runtime uses — no per-call construction. Failures are logged but never propagated; a missed activity bump must not block publishing. There is no separate event-bus subscription; "channel activity" is exactly "a message landed", nothing more.

6. The Host interface

The channel RPC handler doesn't reach into *RPCServer directly. Instead, it declares the surface it needs from its caller — config, an existence check for projects, a way to publish messages, and a wake signal for the runtime host — and the caller (today *RPCServer) provides them. The interface is named Host because that's literally what it represents: the methods the host has to implement.

// services/channel/rpc/handler.go
type Host interface {
    EffectiveUserID(ctx context.Context) string
    ValidateProject(ctx context.Context, projectID string) error
    RequireProjectService() (*projectapp.Service, error)
    PublishMessage(ctx context.Context, msg types.MemberMessage) (types.MemberMessage, error)
    Wake()
    ListRunsByStatus(ctx context.Context, statuses []string) ([]types.Run, error)
}

type Handler struct {
    host       Host
    channelSvc *channelapp.Service
}

func NewHandler(host Host, channelSvc *channelapp.Service) *Handler {
    if channelSvc == nil {
        panic("channel RPC handler requires channel service")
    }
    return &Handler{host: host, channelSvc: channelSvc}
}

The channel service itself is not a Host method — it's an explicit constructor argument. Host is reserved for cross-service dependencies the handler can't own (the supervisor, the project service member roster, the message publisher); the channel service is the handler's own domain dependency and is passed straight in. The host side implements the remaining interface with thin accessors in internal/app/rpc_channel_host.go:

// internal/app/rpc_channel_host.go (excerpt)
func (s *RPCServer) EffectiveUserID(ctx context.Context) string {
    return effectiveUserID(ctx, s.cfg)
}

func (s *RPCServer) ValidateProject(ctx context.Context, projectID string) error {
    _, err := s.loadProjectRecord(ctx, projectID)
    return err
}

// ... more accessors ...

// Compile-time assertion: *RPCServer must satisfy channelrpc.Host.
var _ channelrpc.Host = (*RPCServer)(nil)

The channel service itself lives as a field on *RPCServer (channelSvc *channelapp.Service), required at NewRPCServer via RPCServerConfig.ChannelService. The constructor fails loudly if it's nil; production wires it from Application.ChannelSvc. There is no fallback "build one if missing" path.

Why this shape

Three properties fall out of putting the interface on the handler side rather than the host side:

  • The handler's package owns the dependency surface. services/channel/rpc/ has no compile-time dependency on internal/app/. The handler can be tested with a fake Host and reasoned about without seeing RPCServer's lowercase fields.
  • The compile-time assertion fails at build time, not at wire-up. If a future change drops (s *RPCServer) Wake(), the var _ channelrpc.Host = (*RPCServer)(nil) line breaks the build immediately rather than producing a nil-pointer panic at process startup.
  • Dependencies point inward. Bridge wiring lives in internal/app/ (the host's package), so the handler is reusable without dragging the host with it.
Pattern name. In hexagonal architecture this is a port; in plain Go terms it's a dependency-inversion interface. It is not the GoF Bridge pattern. The project service uses the same shape under the same name — projectrpc.Host, implemented by *RPCServer via internal/app/rpc_project_host.go. Future service migrations follow the same convention.

7. Where the code lives

internal/services/channel/ domain/ # pure rules, no side effects repository.go # Repository interface, ErrNotFound, MaxListChannels const app/ # Service and the package-public builders service.go # Service — Load / ListByProject / ListWithUnread / EnsureMember / StampRunID / MarkRead / DeleteForMember / RecordMessageActivity builders.go # BuildService(cfg) — used only at the assembly root infra/ # SQLite persistence sqlite_repository.go # Repository implementation + channel_reads join rpc/ # JSON-RPC handler handler.go # Handler + Host interface + 4 RPC methods + helpers internal/app/ rpc_channel_host.go # thin *RPCServer accessors → satisfies channelrpc.Host channel_activity_hook.go # channelActivityOnPublish — publish-path hook into message svc rpc_project_lifecycle.go # binds protocol.MethodChannel* to ch.ChannelList / ChannelGet / ChannelSend / ChannelMarkRead

The four protocol.MethodChannel* bindings live in rpc_project_lifecycle.go alongside the project-service handlers — a single registration file currently fans out across multiple service handler structs. Splitting registration per service is a possible follow-up, but it doesn't change behaviour; only file organisation.
