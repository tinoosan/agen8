Architecture · MCP Task Tool

MCP task tool

The agent-facing task lifecycle tool. It is a native MCP handler wired directly to the task service.

1. Boundary

task is an MCP protocol adapter. It owns the member-facing action names, request schema, payload validation, session member resolution, service context stamping, and deterministic MCP result formatting. The task service owns lifecycle authorization, state transitions, and persistence.

Service rule. The handler calls internal/services/task/app.Service methods. It never calls task repositories or storage handles.

2. Wiring

internal/mcp/toolset.go registers the schema with task.NewHandler().Schema(). internal/mcp/server.go resolves the MCP token into a Session, dispatches the native task tool by name, and passes Session.TaskService, Session.TaskMembers, ProjectID, and MemberID into the handler.

3. Handler flow

  1. The handler decodes the action-specific JSON payload and rejects unknown fields.
  2. The handler resolves the MCP caller through TaskMembers.Get.
  3. The handler validates active member state and same-project assignee routing.
  4. The handler stamps taskapp.Caller{MemberID: ...} into context.Context.
  5. The handler maps the action payload into typed task service params.
  6. The task service authorizes the caller, transitions state, persists, and publishes any required task message.
  7. The handler returns a stable text payload and structured MCP content.

5. Schema

The schema requires only action at the top level. Callers include only the fields used by the selected action. The decoder rejects unknown fields, fields that belong to another action, and explicit null values before resolving members or calling the task service. create requires description and assignee_member_id; reassign requires task_id and assignee_member_id. review supports summary and note for reviewer guidance in addition to reason where required by the decision.

6. Result shape

Lifecycle responses return ok, tool, action, and a task object. Service reasons such as block, retry, failure, or cancellation notes are exposed as statusReason. They are not exposed as error when the lifecycle transition succeeds.

7. Authorization

CallerAllowed task behavior
Active project memberCreate, list/get same-project tasks, assign/reassign, review, cancel, and unblock same-project blocked tasks. Assigned or claimed members can claim, release, submit, and block their own active work.

Unblock exists because blocked tasks need an explicit recorded resolution. After an active project member resolves the blocker, the same task service transition returns the task to active work.
