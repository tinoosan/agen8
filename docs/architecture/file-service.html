Architecture · File Service

File Service

The file service owns native file browsing and preview for project-scoped files. The browser uses virtual paths, and the service resolves those paths through the saved project record and execution location before touching storage.

1. Service boundary

The file service is the production entry point for file operations used by the Files page, context panel, inline file cards, and native document viewers. It does not own projects, harness sessions, or artifact history. It loads the saved project by projectId, resolves a virtual file path against that project's location, performs the filesystem operation, and returns a UI-ready result.

File owns
Native browsing
Directory entries, previews, binary metadata, uploads, creates, moves, copies, and deletes.
Project owns
Root registration
The project service remains the source of truth for the root and location behind each project ID.
Harness owns
Execution
Members create or modify files through runtime tools; the file service only exposes the resulting filesystem state.

The app service depends on file.Repository. The repository is composed from file.Reader and file.Writer so read-only surfaces can be tested independently from mutating operations. Repository methods receive a location-aware file reference. The production repository loads the project location and routes local projects through the local filesystem and SSH projects through the location transport's SFTP implementation.

For local projects, file writer operations use rooted filesystem handles after virtual-path resolution. The local transport creates parent directories and writes, copies, or moves files relative to the resolved root rather than trusting a second raw-path lookup; cross-root local moves are rejected.

2. Virtual paths

Clients never send raw storage paths for selected files. They send projectId plus a virtual path. The virtual root /project maps to the project root on the project's location. The virtual root /workspace maps to the project workspace directory on that same location. The Files rail starts at /project so routine browsing stays rooted in the repository, while viewers and context surfaces can still request any valid virtual file path directly.
