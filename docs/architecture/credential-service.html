Architecture · Credential Service

Credential Service

The credential service owns credential records, encrypted secret material, redacted metadata, and runtime credential resolution. Consumers attach credentials at their own boundary: locations reference SSH credentials, and HTTP tooling owns host-match injection policy.

1. Service boundary

A credential is a named reference to authentication material. The credential service keeps the durable record and resolves usable secret material for trusted backend callers. UI and RPC clients see metadata and write-only secret fields. Locations, HTTP tools, and harness adapters keep only credential ids.

Credential owns
Secret registry
Credential id, kind, label, status, redacted field metadata, timestamps, and encrypted secret material.
Location owns
Connection target
Host, port, username, readiness probe state, and an opaque credential id for SSH execution.
HTTP tool owns
Host match policy
HTTP credential binding maps a host pattern and injection mode to a credential id.
Clients own
Write-only input
Users create, rename, rotate, and delete credentials without ever reading secret values back from RPC.

2. Domain model

The domain separates public record metadata from secret material. This keeps list and get views useful while making secret reads impossible through client RPC.

3. Usage bindings

The credential record does not carry a generic ownership field. Usage is modeled where the credential is consumed. Locations attach one credential id for SSH auth. HTTP tooling stores host-match bindings that describe when and how an API key is injected.

type LocationCredentialRef struct {
    LocationID   location.ID
    CredentialID credential.ID
}

type HTTPBinding struct {
    ID           string
    CredentialID credential.ID
    HostPattern  string

    FieldName    string

    UpdatedAt    time.Time

4. Resolution flow

Runtime callers resolve credentials by id. A resolver checks status, kind, storage kind, and the caller's purpose before returning a typed resolved credential. Resolved values stay in memory and are redacted from logs and result payloads.

5. Repository

The repository is split between metadata reads, metadata writes, and material writes. Metadata can be listed. Secret material can only be stored, replaced, deleted, or resolved through the app service.

type Reader interface {

7. Client contract

The Credentials page presents configured credentials as safe metadata. Secret values can be entered, replaced, and deleted, but never revealed. Location creation can attach a credential by selecting an existing credential id or creating one inline.

List view
Metadata only
Kind, label, status, configured field names, and timestamps.
Create / rotate
Write-only secrets
The client sends values once. The server returns the updated metadata record.
Location form
Credential picker
SSH locations reference a credential id. The location record does not store key bytes or passphrases.

8. Security model

Credential handling is designed around one trust rule: secret values enter through write-only paths and leave only through purpose-checked runtime resolution. Client views, logs, tool transcripts, probe results, and durable domain records outside the credential service never contain plaintext credential material.

RiskRuleEnforced by
RPC exfiltrationcredential.get and credential.list return metadata and configured field names only.RPC DTOs and app service redaction.
Log and error leakageValidation errors, probe errors, transport errors, HTTP tool results, and panic/log context contain no secret values.Redaction helpers and tests around error/result formatting.
Wrong-purpose usessh_key and ssh_agent resolve only for location_ssh; api_key resolves only for http_tool.Credential resolver purpose checks.
Over-broad HTTP injectionBearer and header credentials use exact or controlled wildcard hosts. Query credentials use exact hosts only.HTTP binding validation.
Query secret leakageQuery credentials require an explicit parameter name, are injected only at execution time, and are redacted before transcript capture.HTTP tool injection and capture policy.
Redirect leakageInjected credentials are not forwarded across redirects unless the redirected host independently matches a binding.HTTP tool redirect policy.
Transcript leakageTool cards never render injected headers, query params, env values, raw responses containing captured credentials, or secret-bearing command strings.MCP card formatting and activity payload tests.
Local key exposurelocal_encrypted stores its data key in a 0700 directory and 0600 file, and refuses symlinked key directories or key files.Local material store initialization.
SSH agent abusessh_agent credentials are valid only for location SSH resolution and do not expose agent socket values in client views.Credential kind validation and resolver policy.
Frontend retentionSecret form values are cleared after submit and never shown in toasts, summaries, or validation detail.Credentials UI behavior.
Execution boundary confusionCredentials resolve only inside the daemon/control-plane boundary that owns the credential record.Credential resolver identity and deployment boundary checks.
