Attention Service

The attention service is an ephemeral radar for harness sessions that need the human. It is presence state, not work memory: tasks, questions, and decisions remain the durable coordination primitives.

1. Purpose

internal/services/attention tracks which registered harness sessions are currently waiting on the human. It answers a narrow question: "which agent sessions need attention now?" It does not persist records, create graph nodes, or replace a task or future durable question primitive.

Harness hook
Claude Code and Codex hooks send raw lifecycle payloads with a short curl command.
Daemon ingest
POST /hooks/attention authenticates the bearer token, normalizes the payload, and acks quickly.
Attention service
Maintains in-memory entries keyed by native session ref, resolves member attribution, expires stale entries, and publishes lifecycle events.
SSE fan-out
The event bus publishes attention.lifecycle so dashboards refresh without polling as the primary path.

2. Lifecycle

An attention entry is created or refreshed when a harness reports waiting, needs_approval, or asking. It is removed when a newer cleared signal arrives for the same session. Entries also expire after the service TTL, which defaults to two hours.

KindMeaningTypical source
waitingThe agent ended its turn and is waiting at the prompt.Claude Stop or idle notification; Codex Stop.
needs_approvalThe agent is blocked on a permission or approval prompt.Claude permission notification; Codex PermissionRequest.
askingThe agent asked an interactive question and is waiting for an answer.Claude AskUserQuestion hook mapping; future harness parity can report the same kind.
clearedThe human engaged, the session resumed, or the session ended.User prompt submit, session start, session end, or question answer hook.

Repeated reports for the same session and same kind refresh UpdatedAt but keep the original Since. The dashboard can therefore show how long the session has been waiting instead of resetting the wait clock on every hook retry.

3. Member attribution

The service resolves a hook event to a project member by matching the authenticated user and native session ref against active project members. Attribution is best-effort: an unmatched event is still kept as an unattributed entry and appears in project reads so it is not invisible.

type Entry struct {
    SessionRef string
    ProjectID  string
    MemberID   string
    MemberName string
    Harness    string
    Kind       Kind
    Since      time.Time
    UpdatedAt  time.Time
}

If duplicate member rows share a session ref, attribution uses the earliest registered row. This matches project-service session resolution and avoids flicker when a harness label changes.

4. Hook ingest contract

The daemon exposes POST /hooks/attention. It accepts either a normalized attention.Event JSON body or raw harness hook JSON with harness and kind query parameters. Raw mode is the installed default.

curl -m 3 -s -o /dev/null -X POST \
  'http://127.0.0.1:7777/hooks/attention?harness=codex&kind=waiting' \
  -H 'Authorization: Bearer ak_...' \
  --data-binary @- || true

The hook body cap is intentionally small: maxAttentionHookBodyBytes is 16 KiB. Hook payloads carry lifecycle context, not artifacts. A bad payload returns a 4xx to the HTTP client, but installed hook commands still exit successfully so a slow or down agen8 daemon cannot break the agent's own hook chain.

Local project creation can best-effort call the hook installer and report whether hooks were installed, but hook installation failures never fail project creation. For hosted Claude clients, agen8 client setup installs hooks together with skills and MCP configuration; manual agen8 hooks install remains the lower-level repair path. Claude Code writes project-local .claude/settings.local.json; Codex writes user-level ~/.codex/hooks.json. Both files embed a bearer token.

5. Bus events

When an attributed entry is raised or cleared, the service publishes an eventbus.AttentionEvent on attention.lifecycle. The SSE hub forwards these as project-scoped events.

{
  "topic": "attention.lifecycle",
  "eventType": "attention.raised",
  "projectId": "project-example",
  "memberId": "member-...",
  "memberName": "Sora (Full Stack Engineer)",
  "harness": "codex",
  "kind": "waiting"
}

Unattributed entries are retained in memory but do not publish to a project room because there is no project id to route through SSE.

6. Invariants

  • Attention state is ephemeral and in-memory; it is not a task, question, note, decision, graph node, or audit log.
  • The native session ref is the primary key. Newer signals for the same session replace or clear older state.
  • The hook ingest path must ack quickly and must not block on dashboard consumers.
  • Member attribution is best-effort and must not make hook reporting fail when a session cannot be resolved.
  • Durable human questions belong to the question primitive; attention only says that a session is asking.
