Architecture · Runtime & protocol

Real-time events over SSE

Server-Sent Events are how agen8 pushes state changes to every open browser without polling. A domain or runtime lifecycle change is published to the in-process bus, the daemon's GET /events stream fans it out to connected clients for the resolved project as a JSON-RPC notification, and the React app turns notification traffic into query invalidation. The core realtime path is live for pin, task, mission, decision, member, KR, and attention lifecycle events with project-scoped fan-out and authenticated SSE.

Status: expanded live core. The in-process bus, browser client, and hub bridge are live. Section 3 reflects the currently subscribed domains, including the attention lifecycle raised by harness hooks.

1. Why SSE, not WebSockets or polling

The need is one-directional: the server tells the browser "something changed, re-fetch." Writes already have a transport — every mutation goes over POST /rpc. There is no client→server streaming requirement, so a full-duplex WebSocket would be infrastructure the product does not use.

OptionVerdictReason
PollingRejected as the baselineWastes requests, adds latency equal to the interval, and scales with client count × poll rate. Still used as a slow safety net (see §8), not as the primary path.
WebSocketRejectedFull duplex for a one-way need. Adds connection upgrade handling, framing, and heartbeat logic with no payoff — writes already ride POST /rpc.
SSE (chosen)ChosenOne-way server→browser over plain HTTP. EventSource gives automatic reconnect for free, rides the existing daemon and its auth, and degrades to a normal HTTP request on the wire.

2. End-to-end shape

A change flows through five hops. The service that owns the data never knows a browser is listening — it publishes a domain event and returns. Everything downstream is decoupled through the bus.

Publisher (app layer)
A service mutation finishes, then the app-layer publisher calls bus.Publish(topic, event). Publishing lives outside the domain service so services with a no-side-effects invariant (the pin service) stay pure — the publisher wraps them.
internal/eventbus
In-process Watermill GoChannel. Serializes the event to JSON and delivers it to subscribers of the topic. No network, no broker, no persistence.
GET /events hub (daemon)
Subscribes to the relevant topics once, holds the set of connected clients, filters each event by projectId, translates the domain event into a JSON-RPC notification, and writes an SSE frame to every matching client.
EventSource client + React Query
web/src/lib/rpc.ts parses each frame, dispatches by method to handlers registered with onNotification; hooks map the event to queryClient.invalidateQueries(...) so the affected view refetches.

4. Notification envelope and method convention

The wire contract is fixed by the client that already exists. rpc.ts reads e.data as one JSON object per SSE message frame, requires a method field, and dispatches to every handler registered for that method (plus a * wildcard). The daemon must produce exactly this shape.

{
  "jsonrpc": "2.0",
  "method": "event.append",
  "event": { "type": "pin.added", "projectId": "...", "nodeRef": "..." }
}

The house convention is a single notification method, not one method per domain. The live task consumer subscribes to event.append and then filters on the event's type prefix:

// useProjectTasks.ts — the established pattern
onNotification('event.append', (notif) => {
  const type = (notif?.event as any)?.type ?? ''
  if (type.startsWith('task.')) {
    queryClient.invalidateQueries({ queryKey: qk.tasksBoardAll })
  }
})

So new domains ride the same rail. Pins emit event.append notifications whose event.type is pin.added / pin.removed. Attention emits event.append notifications whose event.type is attention.raised / attention.cleared. Do not introduce bespoke pin.changed or attention.changed methods — that would fork the contract and force every consumer to learn a second dispatch scheme.

Why type-prefix filtering, not per-method routing. One method keeps the client dispatch table flat and the reconnect logic single-path. Consumers opt in to the slices they care about by prefix, and the daemon never has to know the React Query key space. The cost — every client wakes for every event and discards most — is negligible at single-daemon scale and is the right trade for a uniform contract.

5. The /events bridge

The SSE handler now implements all five responsibilities end-to-end: auth, project resolution, hub registration, stream loop, heartbeat, and teardown.

  1. Authenticate the request and resolve the caller's projectId from query and referer fallback.
  2. Register the connection with the fan-out hub under that projectId, receiving a per-client channel.
  3. Stream — loop on the client channel, write each notification as an SSE data: frame, and Flush after every write.
  4. Heartbeat — emit a comment frame on an interval so idle connections and intermediaries do not time out.
  5. Clean up — on ctx.Done() (client navigated away or reconnected), deregister from the hub so the channel is not leaked.

The fan-out hub is the daemon-side component. The bus delivers events into the process, then the hub keeps connected clients grouped by projectId and writes events only to matching clients. This keeps processing stable as browser tabs scale.

// Shape of the hub — one bus subscription, many client fan-outs.
type eventsHub struct {
    mu      sync.RWMutex
    clients map[string]map[*eventClient]struct{} // projectId -> set
}

// Register returns a channel of ready-to-write notifications and an
// unregister func the handler defers. Filtering by projectId happens
// in the hub's bus callback, before the notification reaches a client.
func (h *eventsHub) Register(projectID string) (<-chan []byte, func()) { /* ... */ }

The handler stays thin; the hub holds the concurrency. Because the bus is in-process, an event published anywhere in the daemon reaches the hub synchronously — there is no cross-process delivery to reason about at the single-daemon baseline.

6. Publishing new events: pins and attention

The pin service holds a hard invariant: pinning has no side effects and emits no events (see the Pin Service doc). That invariant stays. The publisher is added around the service at the app layer — the same place the mission and KR publishers already live — not inside the pin domain.

Publishing is implemented end-to-end for pin events:

  1. A topic constant and typed event in internal/eventbus/events.go, alongside the existing five topics: 
    const TopicPinLifecycle = "pin.lifecycle"

type PinLifecycleEvent struct {
    ProjectID string    `json:"projectId"`
    NodeRef   string    `json:"nodeRef"`
    NodeType  string    `json:"nodeType,omitempty"`
    EventType string    `json:"eventType"` // "pin.added" | "pin.removed"
    Timestamp time.Time `json:"timestamp"`
}
  2. An app-layer publisher that wraps PinSvc.Pin / Unpin: on success it publishes pin events with projectId for hub filtering.
  3. The bridge maps TopicPinLifecycle → an event.append notification whose event.type is the event's EventType.
Idempotency note. A re-pin is a no-op that preserves CreatedAt. The publisher should only emit when the pin set actually changed, so a redundant pin does not flood every client with a refetch. The service already returns enough to distinguish a real change from a no-op.

Attention lifecycle events follow the same event.append contract, but they are runtime presence signals rather than durable work records. Harness hooks post to POST /hooks/attention; the daemon normalizes the hook payload and calls the attention service; the service publishes attention.lifecycle when an attributed session starts or stops needing the human.

const TopicAttentionLifecycle = "attention.lifecycle"

const (
    AttentionEventRaised  = "attention.raised"
    AttentionEventCleared = "attention.cleared"
)

type AttentionEvent struct {
    ProjectID  string    `json:"projectId"`
    MemberID   string    `json:"memberId,omitempty"`
    MemberName string    `json:"memberName,omitempty"`
    Harness    string    `json:"harness,omitempty"`
    Kind       string    `json:"kind,omitempty"` // waiting | needs_approval | asking
    EventType  string    `json:"eventType"`      // attention.raised | attention.cleared
    Timestamp  time.Time `json:"timestamp"`
}
{
  "jsonrpc": "2.0",
  "method": "event.append",
  "event": {
    "type": "attention.raised",
    "eventType": "attention.raised",
    "projectId": "agen8-mcp-server-3333e627",
    "memberId": "member-...",
    "memberName": "Boreas (Daemon Refactorer)",
    "harness": "codex",
    "kind": "needs_approval"
  }
}

Hook setup is explicit: agen8 hooks install writes curl-based harness hooks that post raw payloads to /hooks/attention?harness=&kind=. The hook command exits successfully even when the daemon is slow or down, so attention reporting never blocks the harness. See Attention Service for the ingest and TTL details.

7. Authenticating the stream

EventSource cannot set custom headers, so SSE is currently authenticated through a session-cookie path.

  1. POST transport: POST /rpc requests remain bearer-based via Authorization: Bearer <token>.
  2. Cookie sync: web/src/lib/rpc.ts mirrors localStorage['agen8.sessionToken'] into document.cookie.
  3. Auth gate: GET /events validates sessionCookieName in httpIdentityFromSessionCookie before streaming.
  4. Project scope: eventProjectID resolves from projectId query first, with Referer fallback.

The mirror cookie is written client-side as SameSite=Lax, path=/. That keeps the read-only stream safe: the cookie is not sent on cross-site subresource requests, and /rpc still authenticates only via the Authorization header, so no cross-site request can drive a state change with it.

Residual hardening (tracked, not blocking). Two gaps are acceptable under the current single-user, single-daemon model and must close before multi-user or hosted deployment:
  • No Secure flag. The cookie is fine over localhost HTTP but must be marked Secure once served over HTTPS, so it is never sent in clear text.
  • Login-scoped, not membership-scoped. /events verifies the caller is an authenticated user, but does not check that the user is a member of the requested projectId. Harmless today — one account owns every project — but a real authorization gap the moment projects can belong to different users.

8. Reconnect and delivery semantics

EventSource reconnects on its own, and rpc.ts adds an explicit 2-second retry on onerror. The contract the daemon must honor:

PropertyGuaranteeConsequence
DeliveryAt-most-once, best-effortEvents are signals to refetch, not data. A dropped event is recovered by the next event or the polling safety net — never trust the payload as the source of truth.
OrderingPer-connection FIFO; no cross-event guarantee after a reconnectConsumers must be idempotent: invalidate-and-refetch is naturally so.
Reconnect gapEvents during a disconnect are lost (the bus is not persistent)Hooks keep a slow polling interval (e.g. tasks drop from 3s to 10s when SSE is healthy) so a missed event self-heals within one slow tick.

This "SSE accelerates, polling backstops" model is why the consumer treats the notification as a hint, not a record. It also means the bridge never needs replay, acknowledgements, or a durable log — deliberately, to keep the single-daemon path simple.

10. Invariants

  • Services do not know about browsers. A mutation or runtime lifecycle change publishes an event and returns. The bus, hub, and SSE layer are all downstream and removable without touching domain logic.
  • The pin service stays side-effect-free. Pin events are published by an app-layer wrapper, never from inside the pin domain. The no-events invariant in the pin service is preserved verbatim.
  • One notification method. Everything arrives as event.append; consumers filter on event.type prefixes. No per-domain methods.
  • Notifications are hints, not durable data. Consumers invalidate-and-refetch or refresh ephemeral presence; they never treat the event payload as the source of truth. This keeps delivery best-effort and the bridge replay-free.
  • Every stream is project-scoped. A client only ever receives events for its resolved projectId; cross-project leakage is structurally impossible in the hub.
  • No secrets in the URL. Stream auth uses a session cookie and no token-in-query strategy.
