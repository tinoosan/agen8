Architecture · MCP Project Tool

MCP project tool

The agent-facing coordination tool for projects and the members registered inside them.

Hard cutover. This tool replaces the retired space MCP tool. The coordination boundary is the project; members attach directly to a project. There is no space_id and no space-listing action.

Purpose

project is an MCP tool, not a service API. It exposes one product-facing coordination contract to member harnesses and maps each action to typed application service calls. The handler owns request decoding, role-aware tool policy, cross-service orchestration, and deterministic result shaping.

Boundary. Project tool behavior lives in internal/mcp/tools/project. The tool exposes project records and the member roster through composite actions. Work coordination happens through the retained mission, task, decision, graph, and HTTP tools. The project service owns project records, lifecycle, and the member roster subdomain. No service accepts raw project(...) tool JSON, and no service package defines a project-tool-specific service or port.

Control flow

Application wiring

The application composition root constructs ProjectSvc once. The same concrete service exposes project lifecycle methods and member roster methods. The daemon builds an MCP session from the authenticated token and supplies narrow handler-owned interfaces to the native project handler when the agent calls project(...).

// MCP session bootstrap
tokenStore.Register(token, agen8mcp.Session{
    ProjectID:       strings.TrimSpace(projectID),
    MemberID:        memberID,
    MemberDirectory: app.ProjectSvc,  // typed as project.MemberService
    MemberRegistrar: app.ProjectSvc,  // typed as project.MemberRegistrar
})

// internal/mcp/server.go
project.NewHandler().Handle(ctx, project.CallContext{
    Members:       session.MemberDirectory,
    Registrar:     session.MemberRegistrar,
    ProjectID:     session.ProjectID,
    ActorMemberID: session.MemberID,
}, arguments)

Handler contract

The handler interface is MCP-owned. Service interfaces are consumer-owned and narrow: the handler declares only the methods it needs for the member_* composite actions. The MCP session token is already bound to a member id and project id, so the handler first stamps a provisional member-scoped caller.Caller into context.Context. It then resolves ActorMemberID through the member roster interface, requires an active member, and restamps the shared caller with the resolved member id, user id, and project id before service calls.

Caller bootstrapping happens before actor lookup. Member roster reads are project-service methods and require caller identity themselves; calling GetMember on an unstamped context is a capture bug, not an authorization fallback. MCP tools may seed context from the authenticated session token, but they must still resolve the actor record and let service authorization enforce visibility.

Runtime-resolved identity

The agent supplies discovery intent. Agen8 supplies runtime identity. The MCP session token plus registration state binds the call to a project and member, so those values are not agent-required request fields after registration. The handler uses them to stamp caller context, resolve the active actor member, and authorize service calls.

MCP registration and delivery

project.register is the MCP-first entry point for harnesses. A harness can call it with only a working directory or project id. Agen8 resolves the project, creates or reuses the member identity, and returns the ids the harness needs for later tool calls.

When a harness exposes a stable native session or thread id in the MCP call metadata, the MCP server passes that value through the project tool call context. The daemon stores it as the harness session reference. For Codex, the server reads the top-level MCP metadata fields threadId, thread_id, sessionId, and session_id, plus the optional x-codex-turn-metadata object that Codex sends with thread_id and session_id.

Boundary. MCP registration does not recreate Codex or Claude thread management. Agen8 stores a native session reference only when the connected harness exposes one. Tool calls, member ids, task ids, decisions, and graph records remain the durable Agen8 coordination surface. Registration is explicit; Agen8 does not auto-promote terminal sessions.

After registration, the member can use retained MCP tools against the bound project. If no native session reference exists, the same durable Agen8 records remain available through MCP tools and the inspection UI.
