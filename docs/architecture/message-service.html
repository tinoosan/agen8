Architecture · Message Service

Message Service

The message service owns member-addressed channels, durable agent inbox messages, member conversation rows, conversation attachments, channel read state, and wake signals. Push wakes reduce polling, while persisted rows remain the delivery and timeline source of truth.

1. Architecture layers

The service follows the same structural shape as the task service: shared persisted DTOs live in pkg/types, domain aggregates own rules, app services orchestrate, and infra adapters persist through typed repository interfaces.

Protocol
RPC and MCP adapters validate transport DTOs and call the app service. They do not construct domain records directly.
App
app.Service publishes agent messages, stores conversation input, manages channels, marks reads, and emits member wake signals after persistence succeeds.
Domain
domain.Message owns queued-to-consumed inbox rules. channel.Channel owns member channel address and activity state. conversation.Message owns user/harness timeline state.
Infra
SQLiteRepository, PostgresRepository, and conversation repositories persist agent messages, channels, read markers, and conversation rows through domain repository contracts.
Wake
A typed wake payload is emitted after a queued message is durable. The wake nudges runtime delivery, which pushes the message to the agent.

3. Delivery flow

Publishing commits the queued row before notifying subscribers. If a process misses the wake, the durable inbox still contains the work. Publishing also ensures the destination member has a delivery loop when the production harness sender is wired, so system messages and agent messages can wake a newly registered member without waiting for a browser chat turn. Runtime delivery workers use wake signals to avoid hot polling, receive the queued message from the inbox, push it to the agent harness, and mark it consumed after handoff. If the destination harness is already running a turn, the queued row remains unconsumed and the worker retries after a short backoff instead of waiting for another message to trigger delivery.

4. Agent-directed messages

Agent-directed messages are durable inbox items addressed to a destination member. They are used for agent-to-agent communication and system-to-agent notifications. They are not browser chat rows. A publisher records intent, route, content, producer, and correlation; the message service persists the row as queued, starts the destination member delivery loop when production harness delivery is available, schedules a wake on an internal delivery queue, and returns to the caller. The runtime delivery path injects the message into the destination member's active harness context out of band, retrying queued delivery when the harness is temporarily busy.

The delivery worker converts an inbox row into a concise runtime message with source member id, source member label, producer, kind, subject, body, correlation id, causation id, and task reference. Agent-to-agent delivery is rendered as an Agen8 member message, not as a user chat turn. The destination agent sees who sent it and why it exists before it sees the body. query messages ask the destination agent to respond later with response using the same correlation id. ack records receipt or completion acknowledgement. system and task messages are service-authored instructions or facts, not peer chat.

Receiving a durable inbox message also creates a visible conversation activity in the destination member's channel. The activity renders as a message-received card in the chat timeline, so users can audit what woke the agent and distinguish it from user-authored conversation input. The activity is render state; the agent inbox row remains the source of truth for queued/consumed delivery.

5. Member conversations

Member conversations are member-scoped chat lanes. The message service owns durable conversation rows, channel activity updates, read-side history, and the send RPC. The harness service owns runtime handoff through a small consumer-side chat interface. A user send resolves the channel to spaceID and memberID, persists one inbound conversation row, then asks the harness service to send that same row to the member's active harness session.

type Message struct {
    ID         string
    ChannelID  string
    SpaceID    string
    MemberID   string
    SessionID  string
    TurnID     string
    Direction  Direction
    SenderType string
    SenderID   string
    Text       string
    Attachments []Attachment
    Delivery   DeliveryState
    Render     RenderState
    CreatedAt  time.Time
    UpdatedAt  time.Time
    Error      string
}

Direction and Delivery are separate. Inbound user input has delivery state because the harness still has to hand it to a runtime. Outbound harness text is already observed output, so it normally has no delivery state and renders as visible member output. SessionID and TurnID are empty when a user input is first saved and are bound when harness delivery claims the row.

Multiple harnesses are routed by member identity. The browser sends to a member channel, the message service resolves that channel to a member, and the harness service decides which runtime receives the text from the member's active session. A Codex-backed member and a Claude-backed member use the same conversation API; only the active managed-member runtime context behind the member differs.

The message service does not provision harness identity or tools. The harness service is responsible for turning spaceID and memberID into a managed-member runtime context: active session, member identity prompt, runtime-specific Agen8 MCP config, model, effort, and external session ref. The message service only persists the chat row, calls the consumer-side interface, and stores the returned delivery/output.

type HarnessChatSender interface {

}

    SessionID string

The interface is owned by the message app package because message is the caller and harness is the consumer. The concrete adapter is wired in the application composition root. This keeps the message service independent from runtime details while still making chat handoff synchronous and testable through message.conversation.send.

6. Conversation attachments

Conversation attachments are first-class message-owned records. The browser uploads pasted, dropped, or selected files before sending the chat row, including the route project id and member channel id, then passes stable attachment ids to message.conversation.send. Upload validates the project and channel, stores the bytes in the daemon data directory, and records the attachment against the project, space, and channel. The send handler validates that every attachment belongs to the same project, space, and caller-visible channel before the inbound row is persisted or delivered to harness. The conversation renderer lazy-loads stored image bytes through message.attachment.get so historical messages show previews after reload. Remote harness sessions receive runtime-local staged copies from the harness service rather than daemon-local file paths.

type AttachmentUploadParams struct {
    ChannelID  string `json:"channelId"`
    ProjectID  string `json:"projectId,omitempty"`
    Name       string `json:"name"`
    MediaType  string `json:"mediaType"`
    DataBase64 string `json:"dataBase64"`

type AttachmentGetParams struct {
    AttachmentID string `json:"attachmentId"`

Text is required only when the message has no attachments. Attachment-only sends are valid for image inspection workflows. Empty sends remain invalid. Upload validates file name, media type, decoded size, project existence, and channel ownership at the RPC boundary. Preview fetch validates the stable attachment id, reads the stored bytes, and returns base64 image data to the authenticated browser session. Image media types are explicit, such as image/png, image/jpeg, and image/webp; unsupported or oversized files fail before persistence and preview rendering.

7. RPC surface

The RPC adapter exposes the service as a small command/query surface. Handlers validate transport params, resolve caller identity, call app.Service, and return frontend-ready views. They do not construct types.AgentMessage or channel rows directly.

Frontend clients
Read channels and render timelines
The browser needs channel lists, paged message history, unread counts, read markers, and a push wake that tells it when to refresh a member or space view.
Runtime delivery
Push messages to agents
Agents do not poll or claim over RPC. The daemon subscribes to wakes, receives the durable inbox item internally, pushes it to the harness, and records consumption after handoff.
Service clients
Publish member-addressed messages
Internal services publish through the app interface. RPC exposes message.send for agent inbox messages and message.conversation.send for user-to-member chat.

8. Channels

A channel is a durable member-facing address and read-state lane. It is not a harness run and it does not own member display labels. Labels are resolved into read models from member identity.

func MemberChannelID(spaceID spacedomain.SpaceID, memberID member.ID) types.ChannelID {
    return "channel:" + spaceID + ":member:" + memberID
}

9. Repositories

The domain exposes Reader, Writer, and Repository contracts. Infrastructure provides SQL-backed adapters for agent inbox/channel storage and separate SQL-backed conversation repositories. Shared SQL mechanics stay private to infra.

internal/services/message/ domain/ message.go # Message aggregate and Consume transition new_message.go # NewMessage constructor and validation repository.go # message Reader, Writer, Repository channel/ channel.go # Channel aggregate new_channel.go # NewMemberChannel and MemberChannelID repository.go # channel Reader, Writer, Repository conversation/ message.go # conversation row, attachments, and direction/delivery/render state repository.go # conversation Reader, Writer, Repository app/ service.go # publish, consume, wake subscriptions channel_service.go # channel app methods infra/ sqlite_repository.go # SQLite adapter postgres_repository.go # Postgres adapter conversation_repository.go # SQL conversation adapter sql_store.go # private shared SQL mechanics sql_helpers.go # private schema, scan, filter helpers rpc/ doc.go # protocol adapter package
