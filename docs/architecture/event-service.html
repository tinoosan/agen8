Architecture · Event Service

Event Service

The event service owns append-only product activity facts, timeline queries, and activity streaming. It is the durable activity spine for Inspector, task history, run activity, and cross-domain audit views. It does not own conversation transcript text, domain aggregate state, or cross-service lifecycle semantics.

1. Boundary

The event service stores facts that already happened. Producing services own the domain meaning of those facts, validate their own state transitions, and call the event appender after the source state is durable. The event service validates that each event has a stable run, type, message, timestamp, severity, category, and structured data; it does not decide whether a task should complete, a message should steer, or a mission should advance.

The message service remains the canonical transcript owner. User messages, assistant messages, attachments, delivery state, read markers, queued rows, steering eligibility, and assistant deltas live in internal/services/message. Events may refer to message ids, channel ids, project ids, and member ids, but they do not duplicate transcript text as the source of truth.

2. Architecture layers

The package follows the standard service split: domain contracts define event persistence and query ports, the app service normalizes and validates append operations, infra owns SQL persistence, and RPC exposes user-facing read APIs.

3. Canonical storage

The events table is append-only. Each row has a monotonically increasing sequence for a run, durable event id, run id, timestamp, type, message, structured data, full event JSON, severity, category, and origin. Updates are not used to correct history. If a later fact changes the state of the world, the producer appends a new event.

Projection tables are read models. They can be rebuilt from events and never become the canonical owner of a domain aggregate. The event repository may update projections in the same transaction as the event append when the projection is part of the event service read model. Projection failures fail the append so the UI never sees a history event without its required read-model row.

4. Repository interfaces

The event repository is an event-service-private persistence contract. It is consumed by internal/services/events/app and implemented by internal/services/events/infra. Producing services do not import the event repository interface and do not receive the SQL repository. Each producer owns a narrow app-level event port that expresses the facts it can publish; the application composition root adapts those producer-owned ports to the event service.

package domain

type Appender interface {
    Append(ctx context.Context, event types.EventRecord) error
}

type Reader interface {
    ListPaginated(ctx context.Context, filter EventFilter) (EventPage, error)
    Count(ctx context.Context, filter EventFilter) (int, error)
    LatestSeq(ctx context.Context, runID string) (int64, error)
}

type Tailer interface {
    Tail(ctx context.Context, runID string, fromSeq int64) (<-chan TailedEvent, <-chan error)
}

type Repository interface {
    Appender
    Reader
    Tailer
}

EventFilter is run-scoped at the repository boundary. Project aggregation is application/RPC behavior: the handler resolves project member run ids, issues run-scoped repository queries, annotates events with project/member data when absent, and returns one sorted page. Keeping project semantics above the repository prevents the event store from learning project membership rules.

The append contract is atomic for the event row and event-owned projections. The SQL repository writes events and any configured event-service projection rows in one transaction. It does not mutate source-service tables such as messages or tasks. Source services write their own state through their own repositories before emitting a product event or through their own transactional outbox when the source event must be retried independently.

5. Event record

Event payloads are small, semantic records. The Type names what happened. Message is a concise human-readable summary. Data carries ids and typed display hints needed for filtering, correlation, and specialized UI cards. Large transcript text, file contents, raw tool dumps, and unbounded runtime payloads remain in their owning stores or artifact references.

type EventRecord struct {
    EventID   types.EventID
    RunID     types.RunID
    Timestamp time.Time
    Type      string
    Message   string
    Data      map[string]string
    Origin    string
}

Events that relate to conversation state reference message rows and channels. They do not copy the message body unless the event type is explicitly a display-only summary and the summary is safe to treat as non-canonical.

{
  "type": "harness.run.started",
  "message": "Run started",
  "data": {
    "projectId": "project-...",
    "channelId": "channel:project-...:member:member-...",
    "memberId": "member-...",
    "sessionId": "session_...",
    "runId": "run-agent_inbox_msg-...",
    "turnId": "019e..."
  }
}

7. Write and read flows

Writes are source-first. A producer persists its own canonical state, then appends the product-facing event. If the event is part of that service's contract, event append failure is returned to the caller. Queries are event-first for activity timelines. UI surfaces ask the event service for facts and use referenced ids to link back to canonical owners when deeper detail is needed.

9. Handlers

Event RPC handlers are read adapters. They authorize the caller through the shared RPC identity path, validate query scope, translate protocol filters into domain filters, call the event app service, and shape protocol results. They do not append events, mutate source services, or synthesize missing history.

type Handler struct {
    Events             eventdomain.EventService
    ProjectLister        ProjectLister
    ResolveProjectRoot ProjectRootResolverFunc
}

func (h *Handler) ListPaginated(
    ctx context.Context,
    p protocol.EventsListPaginatedParams,
) (protocol.EventsListPaginatedResult, error)

The handler has two query modes. A run query requires runId and maps directly to one run-scoped EventFilter. A project query requires projectRoot or a resolvable cwd; it loads the project, narrows by projectId when supplied, collects member and coordinator run ids, issues run-scoped event queries, annotates missing project/member metadata, and returns one sorted page.

Handler concernRule
Scope validationEvery list/count request supplies either runId or a resolvable project scope. Missing scope returns an invalid-params error.
Project aggregationThe handler resolves project member run ids through injected ports. The repository remains run-scoped.
Event appendNo public RPC handler appends arbitrary events. Event writes come from producer services through typed app ports.
AuthorizationRPC registration wraps handlers with caller identity and project/project access checks before event rows are returned.
ErrorsMissing event service, missing project lister, unknown project, invalid scope, and repository failures return visible RPC errors.

Producer-side handlers stay with their owning services. The message RPC handler owns message.conversation.send and message.conversation.steer; those methods persist conversation rows and then publish message lifecycle events through a message-owned event port. Task, mission, decision, operator, and human-input handlers follow the same pattern: handle the domain command first, then publish semantic event facts as part of that service's app contract.

SSE handling stays in the daemon. The daemon receives event append notifications from the event service broadcasting wrapper and emits event.append to browser subscribers. The SSE route never becomes a write handler, and it does not replay durable history; clients use RPC for history and SSE only to invalidate or tail.

10. RPC and streaming

RPC read methods are registered by the daemon from the production composition root. They expose durable event history, not browser notification state. The browser refreshes event queries when it receives event.append notifications over GET /events. A missed notification is harmless because the next query reads from the durable event table.

MethodPurposeRequired scope
events.listPaginatedReturn event rows with limit, cursor/offset, type, severity, category, origin, search, run, project, and project filters.runId or projectRoot; projectId narrows project queries.
events.countReturn count for the same filter shape used by timeline badges and tabs.runId or projectRoot.
events.latestSeqReturn the newest sequence for a run so clients can tail without replaying every row.runId.
event.appendSSE notification emitted after a durable append.Notification only; not a query or storage API.

11. Composition root

The application composition root constructs one event repository, one event app service, and one broadcasting wrapper. Producer services receive their own narrow event ports backed by composition-root adapters, never the event SQL repository. RPC receives the app service and project/project lister ports for project-wide aggregation.

eventRepo := eventinfra.NewSQLRepository(handle)
eventSvc := eventapp.NewService(eventRepo)
broadcastingEvents := eventapp.NewBroadcastingService(eventSvc, daemonEvents)

messageSvc.SetEventAppender(broadcastingEvents)
harnessSvc.SetActivityAppender(broadcastingEvents)
taskSvc.SetEventAppender(broadcastingEvents)

Daemon startup fails if a service that declares an event dependency is missing its production event appender. Tests mirror production wiring: composition-root tests register the event RPC handlers and drive them through the real RPC server; producer tests use spies that capture event type, ids, and structured data.
