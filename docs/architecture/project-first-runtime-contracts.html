Architecture · Runtime Model

Project-First Runtime Contracts

Agen8 is an OKR-based system of record for agentic work. It coordinates work through projects and members. A Project is the durable workspace and the live coordination boundary. A Member is one harness session registered into a project. Harness sessions and runs are execution details owned by members, not the product identity.

Hard cutover. The Space concept has been removed. There is no space_id, no SpaceMember, and no space service. Members attach directly to a project. This document supersedes the retired space-first runtime contracts; there are no transitional aliases.

1. Runtime model

Agen8 uses a project-first, managed-member model. Project is the durable coordination boundary that harnesses already think in: a location plus a root. Member is one live harness session registered into a project, identified by (project_id, harness_kind, native_session_ref). MemberType is structural and contains coordinator or worker. A transitional reviewer type may exist only as a dedicated review member while review policy moves into capabilities.

Identity rule. A coordinator remains a coordinator whether or not workers are currently present. Agen8 does not derive a separate lone-coordinator runtime identity, and it does not derive member identity from a run id.
Live boundary
Project
Owns identity (location + root), lifecycle, member roster, the work graph (missions, KRs, tasks, decisions, operator actions), and default execution preferences for new members. This is the team boundary for now.
Actor identity
Member
One harness session. Owns member id, channel id, display name, member type, lifecycle, harness kind, native session ref, and harness preferences.
Execution detail
Harness Session / Run
Stores the managed harness address, runtime settings, usage evidence, and lifecycle observations. A native session ref alone grants no control.
Optional setup
Template and Role
Provide project setup defaults, persona, capability preferences, and provenance without becoming runtime ownership.

2. Hierarchy

Project is the boundary. Member attaches directly to the project. Group is a documented future primitive (dashed) that can subdivide a project's members into sub-teams without changing member identity.

4. Registration contract

Registration is the boundary where Agen8 binds a harness session as a managed member of a project. The caller supplies an existing project (by project_root or project_id), the harness_kind, the native_session_ref, a requested member type, display name, optional role or ad hoc capability declaration, and desired execution settings. Registration is explicit; Agen8 does not auto-promote terminal sessions.

Member id and channel idStable actor identity and routing address channel:<project>:member:<id>.

Coordinator admission. A project has at most one active coordinator member. If an active coordinator already exists, another coordinator registration fails by policy. Type changes go through the member service rather than direct record mutation. When groups are introduced, coordinator uniqueness can be re-scoped from project to group additively.

5. Push messaging

Messaging is push-based: the system delivers coordination events to a member's harness session, rather than the member polling an inbox. Each member owns a deterministic channel addressed as channel:<project>:member:<id>. Routing authority comes from project identity and coordinator-member identity.

Each message carries source project/member, target project/member, kind, correlation id, causation id, optional structured context links, and delivery/ack state. Raw chat is allowed, but messages should link to missions, tasks, decisions, operator actions, or files when coordination produces structured work. The push model is deliberate — the strongest coordination features came from system-initiated async delivery.

6. Path to groups

The team primitive that spaces once provided — clustering agents into sub-teams — is preserved as a documented future Group aggregate. It is not built yet. The path stays open because every actor and work node keys off project_id:

  • A Group is a thin, additive aggregate inside a project: an optional, nullable group_id on members and (optionally) on missions.
  • Adding it changes no existing identity: a member is still (project_id, harness_kind, native_session_ref); group membership is an extra attribute, not a new boundary.
  • Project-scoped invariants (such as one active coordinator) can be re-scoped to group-scoped invariants when groups exist, without a second cutover.
Do not build groups now. The requirement here is only that the project-first model leaves a purely additive path to groups. Introducing a group boundary prematurely would reintroduce the space problem.
