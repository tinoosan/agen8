Release Notes

v0.1.0 MCP-first baseline

This release is the first clean local baseline after the MCP-first reset. Agen8 is a durable MCP work-context layer for harnesses, with the browser UI focused on setup, project state, strategy, and readable graph context.

1. Included

The baseline keeps the work-context pieces that are useful from normal AI harnesses:

AreaRelease behavior
Daemonagen8-mcp starts the local HTTP daemon, serves the web UI, exposes /healthz, and hosts the MCP endpoint.
Local setupFirst-run setup creates the local account, browser session, and initial API key.
MCP toolsproject, mission, task, decision, graph_query, and http are the retained tool surface.
Work contextProjects contain members, missions, key results, tasks, decisions, graph links, credentials, files, and locations.
VersioningBuild metadata is exposed through agen8-mcp version, /healthz, and MCP server info.
StorageRuntime data defaults to ~/.agen8. The repository does not own the live SQLite database.

2. Removed

The release intentionally excludes the old orchestration model. These are not active product promises in v0.1.0:

  • Harness supervision, launch, resume, or thread routing.
  • Message push, channel delivery, operator actions, escalations, and notification coordination.
  • Plan-phase and plan-todo task schema columns.
  • Chat UI replacement behavior for Codex, Claude Code, or other harnesses.

3. Setup expectations

A clean install starts from an empty data directory, not repository-local state. The daemon prints a setup URL with a one-time token. The created API key is the MCP token for local harness connections.

make dev remote
# or isolate a verification run
make dev remote DATA_DIR=/tmp/agen8-v010-check

A harness connects to the MCP endpoint and calls project.register with a readable display_name. Agen8 records that member label so tasks and decisions stay understandable in the graph.

Routine cleanup does not delete the active local database. Use an isolated DATA_DIR for repeatable setup checks, and use preserving migrations for development data until an explicit release-finalization reset is approved.

4. Preflight checklist

Before tagging v0.1.0, run the checks below from a clean working copy or carefully stage only release-scoped changes.

go test ./... -count=1
make build-go VERSION=v0.1.0 COMMIT=$(git rev-parse --short HEAD) BUILD_DATE=$(date -u +"%Y-%m-%dT%H:%M:%SZ")
./bin/agen8-mcp version
make dev remote DATA_DIR=/tmp/agen8-v010-check

Then verify the retained MCP tools through a real harness connection:

  1. Register the project with a readable member display name.
  2. Create or read a mission and key result.
  3. Create, claim, submit, and review one task linked to the mission and key result.
  4. Log a decision linked to the task or KR.
  5. Read the graph node and confirm the mission, KR, task, and decision links are visible.
  6. Use the HTTP tool to call GET http://127.0.0.1:7777/healthz.

5. Known constraints

The current baseline favors correctness and understandable work records over broad orchestration. The graph can already become dense around active missions, so the next readability work should focus on filtering, grouping, and clearer treatment of mission-level decisions before adding new relationship semantics.

See Release Baseline for the setup and verification contract behind these notes.
