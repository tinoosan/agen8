Release baseline setup and verification

This page describes the current releasable local baseline for agen8 MCP. It is a practical setup and verification checklist for the daemon, web UI, retained MCP tools, local data directory, and schema preservation policy.

For release-facing changes that have not been tagged, see Next Release Draft.

1. Current baseline

Agen8 is an MCP-first work-context layer. The active harness remains the work surface. Agen8 records durable project context through retained concepts: projects, members, missions, key results, tasks, decisions, graph links, credentials, files, locations, and bounded HTTP actions.

2. Data directory

Runtime state lives outside the repository. On macOS the default is ~/.agen8. The daemon accepts --data-dir, the environment accepts AGEN8_DATA_DIR, and the Makefile accepts DATA_DIR=... when a test run needs an isolated state directory.

make dev remote
make dev remote DATA_DIR=/tmp/agen8-release-check
agen8 daemon start --data-dir /tmp/agen8-release-check --listener http --http-addr 127.0.0.1:7777

The repository should not contain a live agen8.db. Local SQLite files belong in the resolved data directory; use an isolated DATA_DIR or AGEN8_DATA_DIR for clean setup checks.

On SQLite startup, the daemon creates the data directory with owner-only access and secures the database file as 0600. Startup refuses a symlinked database file or a database path that resolves to a directory or other non-regular file.

make clean removes build artifacts and logs only. It does not remove agen8.db, agen8.db-wal, or agen8.db-shm. Use isolated data directories for repeatable setup checks instead of resetting the active local database.

3. Build and version checks

The release version source is pkg/buildinfo. Builds set Version, Commit, and BuildDate with Go ldflags. Local development defaults to dev and none.

make build-go VERSION=vX.Y.Z COMMIT=$(git rev-parse --short HEAD) BUILD_DATE=$(date -u +"%Y-%m-%dT%H:%M:%SZ")
./bin/agen8 version
curl http://127.0.0.1:7777/healthz

/healthz returns ok, version, commit, and buildDate when the build date is set. The MCP server implementation advertises the same version.

4. First local setup

When the user repository is empty, the daemon exposes first-run setup. The daemon prints a setup URL with a one-time token. Setup creates the first local account, a browser session, and the initial daemon API key. That API key is also accepted as the MCP token after daemon restart. Setup does not create missions, KRs, tasks, decisions, or MCP members.

make dev remote
# Open the printed setup URL.
# Create the first local account.
# Create or open a project in the UI.

5. MCP connection

The daemon exposes the MCP server over HTTP. The token maps to the local user. A harness registers into a project with project.register. Use a readable display_name in Name (Role) form, such as Atlas (Backend Engineer), Iris (Frontend Reviewer), or Nova (Research Analyst), so graph records are understandable later.

{
  "mcpServers": {
    "agen8": {
      "type": "http",
      "url": "http://127.0.0.1:7777/mcp",
      "bearer_token_env_var": "AGEN8_MCP_TOKEN"
    }
  }
}

Use the repository .mcp.example.json as the public template. Copy it to a local .mcp.json or to the harness-specific MCP configuration location, then set AGEN8_MCP_TOKEN to the user's API key before starting the client. The real .mcp.json is ignored and should stay out of git because it is machine-specific and may contain local tokens.

Query-token MCP URLs remain a compatibility path for clients that cannot send headers and for project link-token flows, but bearer-token configuration is the public release default.

After registration, the response includes projectId, memberId, channelId, url, and token. It may also include memberType as compatibility metadata. Agents should use returned ids rather than inventing them.

6. Retained tool UAT

Before tagging a baseline, verify the retained tools through the actual MCP connection:

ToolRelease check
projectregister, member_get, and member_list return readable member labels.
missionCreate or read the release mission and KRs; update progress.
taskCreate, claim, submit, and review one small task linked to a mission and KR.
decisionLog a decision linked to the active task, mission, or KR.
graph_queryRead the task node and confirm links to decision, KR, and mission.
httpCall GET http://127.0.0.1:7777/healthz and confirm 200 OK.

7. Schema preservation policy

The local SQLite schema validates the current MCP-first baseline at startup. Schema version 5 is upgraded transactionally to version 6 with credential ownership preserved; an ambiguous multi-user credential owner rolls the migration back. Older incompatible schemas fail loudly with migration guidance. Startup never archives, deletes, or replaces the active database.

Schema validation rejects removed tables and legacy columns from removed concepts. The current task schema keeps mission and key-result references and rejects legacy task plan columns. A destructive reset is only a deliberate release-finalization or operator action, never the default startup or cleanup path.

8. Before tagging

Run these checks before creating a release tag:

make ci
make build-go VERSION=vX.Y.Z COMMIT=$(git rev-parse --short HEAD) BUILD_DATE=$(date -u +"%Y-%m-%dT%H:%M:%SZ")
./bin/agen8 version
make dev remote
# Run retained MCP tool UAT from a real harness connection.

Start and end with git status --short. The release candidate should be clean before tagging. The generated bundle in internal/web/dist is not committed (only the .gitkeep placeholder is tracked), so npm --prefix web run build leaves git status clean; the binary embeds the freshly built bundle at make build time. Keep the real local .mcp.json ignored; publish .mcp.example.json only.

The release workflow verifies strict SemVer tags, then builds agen8 archives for Linux and macOS before publishing the release and container image.
